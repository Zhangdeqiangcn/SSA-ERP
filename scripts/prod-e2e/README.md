# 生产端到端门禁（prod-e2e）· 编写规范

> 运行：`npm run test:prod-e2e`（全量）／`npm run test:prod-e2e -- --only=<套件id>`（单域）
> 报告：`test-reports/prod-e2e/latest.{md,json}`
> 目标环境：默认 `https://ssa-erp.pages.dev`，可用 `PROD_E2E_BASE` 覆盖。

## 一、★ 写断言之前，先过这三问（用真事故换来的）

### 第 1 问：这个故障在当前测试环境里**能不能被制造出来**？

**制造不出来的故障，不要写断言。** 它只会变成两种垃圾：

| 类型 | 表现 | 危害 |
| --- | --- | --- |
| **永不触发的空断言** | 永远绿，但什么都没防 | **假安全**：以为有护栏，其实没有 |
| **永远报错的错断言** | 永远红，天天喊狼来了 | **假警报**：最后所有人都无视红条 |

**真实翻车案例（V3.10.0 审批流域）**：曾写下「断言 `total ≥ 5`，因为生产库有 13 条系统流程，门禁用户应该看得见」。
**这条断言从原理上永远不可能通过** —— 因为它把两种作用域混为一谈：

| | 实际语义 |
| --- | --- |
| 权限登记的 `'all'` | 「**本公司内**全员可见」（相对 `'own'` = 仅建者可见） |
| 门禁用的组织 | **每轮新注册一个隔离组织**，公司码 `E2E-<runId>` |

隔离组织里本来就没有别的公司的数据。**权限机制拦住的正是它该拦的 —— 这是正确的安全行为，错的是断言。**

### 第 2 问：这个断言**要防的真故障**是什么？组织内能不能复现？

承接上例：真正要防的不是「看不到别的公司的流程」（那本来就该看不到），而是
**「张三配好的审批流，李四看不到」** —— 审批流是公司制度，必须全公司一致。

这个故障**在同一个组织内就能完整复现**，也只需要组织内复现：

```js
// ✅ 正确写法：同组织内两个身份互看
const peer = ctx.users.afpeer || await ctx.registerUser('afpeer', 'buyer', 'QA-采购部');
const mk = await req('POST', '/api/approval-flows', { token, body: { /* ... */ } });
const seen = await req('GET', '/api/approval-flows', { token: peer.token });
s.expectTrue('同组织内他人能看到 admin 建的流程', !!seen.data?.data?.find(f => f.id === sharedId));
// 若 RLS 误登 'own'，这一条立刻变红 —— 这才是有效护栏
```

### 第 3 问：**存量数据**的正确性该由谁守？

**答案：迁移脚本 + SQL 核对，不要放进接口套件。**

理由：门禁是**隔离组织 + 直连接口**的，它天然看不到生产存量数据。
把存量校验塞进套件，必然得到上面说的「空断言」或「错断言」。

```bash
# ✅ 存量数据核对的正确位置：迁移/核对脚本里，直接查库把「谁拥有数据」打出来
npx wrangler d1 execute ssa-erp-db --remote --json --command \
  "SELECT org_id, COUNT(*) FROM approval_flows GROUP BY org_id"
```

## 二、★ 返回形状：列表与单体**不一致是常态**

写断言前**必须先确认形状**，不能凭印象。

| 接口 | 返回形状 |
| --- | --- |
| 列表 `GET /api/xxx` | `{ data: [...], total, page, pageSize }` ← **有包层** |
| 单体 `GET /api/xxx/:id` | **扁平对象**（`json(parentToApi(...))`）← **无包层** |

**真实翻车案例**：单体 GET 误写成 `res.data?.data?.nodes`，多解了一层 →
`nodes` 恒 `undefined` → 套件**假报**「改开关把节点删光了」（实际一条没少）。

```js
// ❌ 错：单体接口多解一层
s.expectEq('节点数', (afterEdit.data?.data?.nodes || []).length, 1);

// ✅ 对：单体接口是扁平的
s.expectEq('节点数', (afterEdit.data?.nodes || []).length, 1);
```

**通用做法**：先断言 `expectStatus(..., 200)`，再打印一次真实响应体确认形状，然后写解构。

## 三、★ 排障铁律：**先量数据归属，再谈代码逻辑**

门禁变红时，不要先猜代码。**第一动作是查库，把「谁拥有这份数据」打出来。**

真实案例的定位过程：
1. 首轮 `FAIL 4`（本域全是「一条都查不到」）→ **我猜「表是空的」**，补了回填迁移 → **仍然 `FAIL 4`**。
2. 才去查库：`GROUP BY org_id` → 13 行同属一个组织（公司码 `xinguang`）。
3. 与「门禁每轮新建组织」这个已知事实一对照 → **矛盾自解**。

**教训：我在查库之前先猜了两轮。** 能实测的事实，不要用推理代替。

## 四、套件编写硬规矩

### 4.1 每个断言都要「写过之后必须再读一次」

POST / PUT 的回执**可能只是把请求体原样回显**，证明不了真的落到了 D1。
只有重新 GET 一次（打在数据库上）才能证明写入生效。

### 4.2 复用身份，不要重复注册

```js
// ✅ 与其它套件一致：优先复用，避免每轮重复注册僵尸账号
const peer = ctx.users.afpeer || await ctx.registerUser('afpeer', 'buyer', 'QA-采购部');
```

> 说明：`orgs` / `users` / `sessions` 无删除端点，重复注册会在生产库留下僵尸账号，不影响业务数据但要尽量少造。

### 4.3 子表语义逐张独立判断

「不传子数组 = 保持原样」／「传空数组 = 清空」—— 这条语义**必须逐张单独验证**，
不能因为 A 表对了就假定 B 表也对。多子表下尤其重要：
只改「里程碑」不得删掉「异常记录」。

### 4.4 用例失败也要清理

```js
const cleanup = [];
// ...建数据时登记
cleanup.push({ path: '/api/approval-flows', id: sharedId });
// 结尾统一清理（断言失败中断也不能把测试数据留在生产库）
for (const c of cleanup.splice(0)) {
  try { await req('DELETE', `${c.path}/${c.id}`, { token }); } catch { /* 尽力而为 */ }
}
```

### 4.5 断言名称要写「防的是什么」，不是「测了什么」

```js
// ❌ 只说了动作，看不出风险
s.expectEq('nodes 长度为 3', nodes.length, 3);

// ✅ 说出了防的回潮，红的时候一眼知道严重性
s.expectEq('★ 只拨开关后节点仍是 3 个（不传子数组 ≠ 清空）', nodes.length, 3);
```

### 4.6 ★ 「库里现在没有值的字段」必须**刻意写入**再断言读回（V3.11.0 采购域）

这是「登记列」这一类缺陷**唯一**能被护栏抓住的写法。

真实背景：`PurchaseRequest.remarks` / `projectNo` / `sourceType` / `sourceNo` /
`sourceName` 实测生产库 5 条申请里**一条数据都没有**。
按「现在没数据就不登记」写代码，未登记字段会被父表 `pickCols` **静默丢弃且返回 201 成功**。
**这个故障不会在存量数据上暴露** —— 只有在**有人第一次填这些字段**时才炸，而那时已经上线了。

```js
// ❌ 无效写法：只测存量数据的字段，永远绿
s.expectEq('备注未丢', String(got.remarks), '');   // 空对空，什么都没防

// ✅ 有效写法：刻意写入库里当前无数据的字段，断言读回一致
const body = { /* ... */ remarks: '请优先采购电机', sourceType: 'mrp', sourceNo: 'MRP-X' };
await req('POST', '/api/purchase-requests', { token, body });
const pg = await req('GET', `/api/purchase-requests/${body.id}`, { token });
s.expectEq('★★ 可选字段 sourceType 未丢（MRP 生成申请链路）', String(pg.data.sourceType), 'mrp');
```

> **判据是「前端类型契约里有没有这个字段」，不是「库里现在有没有值」。**
> 契约里有 → 必须在套件里写进去测一遍。

### 4.7 ★ 同一域内两张表 RLS 取值相反时，断言要写成「跨身份能否看见」

采购域是本项目第一个「同一业务域内两张表权限值刻意相反」的域：

| 表 | RLS | 业务语义 | 误设后的表现 |
| --- | --- | --- | --- |
| `purchase_requests` | `'own'` | 个人提报的单据 | 同事看到不该看的单据 |
| `vendor_quotes` | `'all'` | 比价用的公司级公共信息 | **采购员看不到别人录的报价 → 比价功能残废** |

第 2 种误设**界面上只是「列表少了几行」，没有任何报错** —— 必须靠跨身份断言抓：

```js
// ✅ 同组织内另一个身份（buyer）必须能读到 admin 建的报价
const bq = await req('GET', `/api/vendor-quotes/${quoteId}`, { token: buyer.token });
s.expectStatus('★★ 同事能读到他建的供应商报价 200（RLS=all 生效）', bq, 200);
// 若为 404 → 被误设成 own → 立刻变红
```

> **规则：权限值必须逐张按业务语义定，不能整批复制。** 也不能因为「上一个域整批用了 X」就跟着用 X。

### 4.8 ★ 「重复/冲突」类断言，前置条件必须是「被冲突的那条记录仍然存在」

V3.11.0 采购域踩过一次，**而且我第一反应是去怀疑产品代码**：

我把「重复 `request_no` 应返回 409」这条断言写在了「DELETE 采购申请」**之后**。
顺序反了 → 参照物已经不存在 → 唯一约束无冲突可报 → 接口正确返回 `201` → **断言误报为 FAIL**。

排查时我先去查了迁移、查了生产库索引，绕了一圈才回头看套件自己的执行顺序。
**其实只要先问一句「这条断言的前提还成立吗」，就能省掉整轮排查。**

```js
// ❌ 错：先删了原单据，再测「重复」
await req('DELETE', `/api/purchase-requests/${id}`, { token });
const dup = await req('POST', '/api/purchase-requests', { token, body: { ...body, id: `${id}-dup` } });
s.expectTrue('重复单号被拒', dup.status === 409);   // 永远 FAIL

// ✅ 对：原单据活着的时候测重复
const dup = await req('POST', '/api/purchase-requests', { token, body: { ...body, id: `${id}-dup` } });
s.expectTrue('重复单号被拒', dup.status === 409);
// 然后再删原单据
await req('DELETE', `/api/purchase-requests/${id}`, { token });
```

**配套两条：**

1. **冲突断言之后，补一条「删除后同一标识可再次使用」** —— 它同时反向验证了时序是对的：
   ```js
   const reuse = await req('POST', '/api/purchase-requests', { token, body: { ...body, id: `${id}-reuse`, items: [] } });
   s.expectStatus('原单据删除后同一 request_no 可再次使用（约束只在存在时生效）', reuse, 201);
   ```
2. **若冲突断言失败且真的建出了第二条，必须把它登记进 `cleanup`** —— 否则脏数据留在生产库：
   ```js
   if (dup.status === 201) cleanup.push({ path: '/api/purchase-requests', id: `${id}-dup` });
   ```

> **通用判据：任何「A 应该被 B 拒绝」的断言，先确认 A 与 B 的关系在断言那一刻仍然成立。**

### 4.9 ★ 想确认「数据库约束是否真的生效」，最直接的证据是让数据库自己报错

V3.11.0 验证唯一索引时，我用一条**直连 SQL** 拿到的证据，比任何接口断言都硬：

```bash
npx wrangler d1 execute ssa-erp-db --remote --command \
  "INSERT INTO purchase_requests (id, org_id, request_no)
   SELECT 'zz-uniq-probe', org_id, request_no FROM purchase_requests
    WHERE request_no IS NOT NULL LIMIT 1"
# → UNIQUE constraint failed: purchase_requests.org_id, purchase_requests.request_no
```

**为什么不能只靠接口断言**：接口返回 409 可能是**任何一层**拒绝的（入参校验、业务判重、数据库约束）。
只有让数据库直接报 `UNIQUE constraint failed`，才能把「约束到底建没建」这件事**从推测变成事实**。
（注意：这条探针 INSERT 会失败，所以**不会留下任何数据**，是安全的。）

### 4.10 ★★ 断言红了先问「它**以前绿过吗**」——区分「回归」与「一直裸奔的老缺陷」

V3.11.1 的起点是一条**看起来像回归**的红项：

```
❌ [13-hardening] 日期填 2026-13-45：被拒绝（4xx） — status=201
```

**第一反应是「本轮改动打破了它」。但真相完全相反：这条断言从来没绿过** ——
它要防的字段校验（`fieldSchema.ts` 里 `purchase_orders` 是空对象 `{}`）**从上线起就不存在**。

| | 回归（本轮改坏的） | 裸奔（一直没生效的） |
| --- | --- | --- |
| 处置方式 | 回滚 / 追查本轮改动 | **补全从未建立的能力** |
| 若判错 | 白回滚，根源一分未动 | 去翻历史提交，找不到东西 |

**判定手法（三条，缺一不可）**：
1. **查这条断言与真实数据的对应关系**：它防的东西在库里/代码里**存在吗**？（本例：字段根本没登记 → 校验不可能生效）
2. **用 `git status` / `git show HEAD:<file>` 对比**受影响文件，看是否真被本轮改过；
3. **量「以前会不会也返回同样结果」**：本例 `purchase_orders` 一直是空对象 → **以前同样返回 201** → 它一直红，只是被淹没在其它信号里。

> **★ 这条规矩的价值：定性错会修错方向。** 把「一直裸奔」当成「本轮回归」，会白回滚一轮，
> 而真正缺的那项能力仍然不存在——下次换个字段再裸奔一次。

**配套要求**：断言红的时候，**必须在最终汇报里明确说清是哪种**，并说明依据。
若发现是「我自己上一轮汇报有误」，**当面纠正，不要含糊带过**（记录里的一句错话比代码里的 bug 更危险，因为它不会被任何检查抓住）。

### 4.11 ★★ 「要不要新增字段校验」的评估顺序（防止把关变严后误伤）

V3.11.1 一次性新增登记了 355 个字段类型，属于**把关变严**。变严有两个风险：
**① 合法数据被误拦**；**② 老数据一旦被编辑就过不了关**。评估必须按序做完：

1. **量变化规模**：`git diff -U0 <产物> | grep -c '^+'` 这类**结构化**统计，**不要用自定义正则解析产物文件**
   （本项目踩过：正则失配导致「355 个新增字段」这个数字是假的）。
2. **查「怪列名」**：如驼峰列与蛇形列并存（`vouchers` 同时有 `totalDebit` 和 `total_debit`）。
   ★ 注意 `camelToSnake(key)` 会把驼峰 key 转成蛇形去查表 → 驼峰列**既不会误拒、也永远匹配不到**，
   属「登记了但无效」。**如实记录，不夸大成风险，也不当作无害忽略。**
3. **跑全量门禁，同时确认两件事**：该拦的**拦住了** + 不该拦的**没被拦住**。
   > **只验证「拦住脏数据」是不够的——那可能只是把所有人都拦住了。**

## 五、可用断言 API（`lib/harness.mjs`）

| 方法 | 用途 |
| --- | --- |
| `s.expectStatus(name, res, want, extra?)` | 校验 HTTP 状态码 |
| `s.expectTrue(name, cond, detail)` | 校验布尔条件，`detail` 打印实际值 |
| `s.expectEq(name, actual, expected, label?)` | 校验相等，`label` 说明比的是什么字段 |
| `s.expectListShape(name, res)` | 校验列表契约 `{data,total,page,pageSize}` |
| `s.fail(name, detail)` | 直接判失败（用于「找不到预期数据」这类分支） |
| `s.warn(name, detail)` | 记为 WARN，**不阻断**（如外部依赖不可用） |
| `s.info(name, detail)` | 仅记录信息 |

## 六、门禁结果的判读

```
结论：✅ 全绿 ／ ❌ N 条失败
断言：PASS xxx / FAIL x / WARN x / INFO x
```

- **FAIL 必修**。修完**必须跑全量**，不能只跑本域 —— 跨域回归只有全量抓得到
  （V3.9.0 改 `pcRemove` 返回值删掉旧字段，单跑本域是绿的，靠全量才抓到财务域的真回归）。
- **WARN 属外部依赖**（OCR / AI / 数电票 / 汇率刷新）不阻断。
- **INFO 仅记录**。

## 七、新增域套件的检查清单

- [ ] 过完「三问」（第 1~3 节）
- [ ] 端点可达 + 未登录返回 401 —— **★ 且必须顺带确认「这个 401 不会把用户踢到登录页」**（V3.10.1 事故：启动期请求 401 → 整页跳转 `/login` → 状态重置 → 无限刷新）
- [ ] 列表契约形状（`expectListShape`）
- [ ] 核心嵌套字段的**往返**（写进去 → 重新读回 → 逐项比对）
- [ ] **★ 契约里有、但库里当前无数据的可选字段，要刻意写一遍**（第 4.6 节）
- [ ] 「不传子数组 = 保持」与「传空数组 = 清空」双向
- [ ] **★ 多个子表时逐张独立验证**（只改 A 不得连带清空 B）
- [ ] **★ 子表主键来源要辨明**：前端自带 id（如 `PurchaseRequestItem`）vs 后端生成（如 `QuoteItem` 无 id）—— 两者都要断言「id 存在且非空」
- [ ] JSON 文本列读回是**真数组/真对象**（不是字符串）
- [ ] 权限语义（同组织内跨身份可见性，而非跨组织）；**同域内多表取值不同时逐张验**（第 4.7 节）
- [ ] 重复业务单号返回 **409 + 可读中文**（不是静默覆盖）
- [ ] 删除回执报告连带删除的行数
- [ ] 失败也清理（`cleanup` 数组 + 结尾统一删）
- [ ] **★ 注意 `ctx.cleanup()` 的 `pathOf` 只覆盖既有类型**（vendor / serial / subcontract / picking / state）；
      新域的资源**必须在套件内自行 DELETE**，并在删除后从 `cleanup` 数组里 `splice` 掉，否则会被兜底循环二次删除（得到 404，无害但不干净）
- [ ] 收尾：列表可读、无损坏行
- [ ] 跑**全量**确认 FAIL 0

## 七之二、★ 动 store 之前的三件套（不是套件规范，但每个域都要做）

每个域开工前必须量化这三项，**靠脚本、不靠目测**：

1. **消费方清单** —— `useXxxStore` 被多少个文件引用？其中业务消费方几个？
   （V3.8.0 财务域：35 个文件 / 业务 33 个 → 决定「接口形状必须一字不改」）
2. **真实体积** —— `app_state['ssa-erp-xxx']` 有多少字节？结构是 `{"state":{...}}` 还是裸对象？
   （**★ 先探明包裹层**：直接查顶层键会全部返回 `null`）
3. **CRUD 写入调用点** —— 每个写方法有多少处调用？**是否 `await` 返回值**？
   （V3.9.0 销售域：10 个写调用点全部不 await → 可放心改 async；
     V3.8.0 财务域：大量同步依赖返回值 → 必须保持同步签名）

**★ 两个「不做」的判据（与「做」同样重要）：**

| 情形 | 判据 | 先例 |
| --- | --- | --- |
| 零写入调用点 | **不够**。还要看「这份数据空了会怎样」 | 销售域 `marketData` 刻意不迁（报表种子常量）<br>采购域 `vendorQuotes` 必须迁（2 条真实比价数据） |
| 嵌套对象数组 | 看「将来会不会需要按内部字段做 SQL 统计」 | 采购域 `approvalRecords` 走父表 JSON 文本列（刻意不建子表） |

## 七之三、★ 生成类脚本（把库结构/配置变成代码）的三条硬规矩

本项目有三类这样的脚本：`_gen_schema_prod.mjs`（库结构 → 字段类型表）、
`_regen_fieldschema.mjs` 系列、以及各家的枚举/路由清单生成器。**它们有一个共同特征：出问题时不报错。**

V3.11.1 的教训（`fieldSchema.ts` 里 16 张表长期是空对象，校验悄悄失效）就是这三条全踩：

1. **★ 产物必须与「真实数据源」逐条机器比对，禁止目测与抽样。**
   让数据源自己报事实（SQLite/D1：`sqlite_master JOIN pragma_table_info(m.name)` **一次查多表**），
   以**不一致 = 0** 为门槛。参考实现：`scripts/_verify_schema_vs_db.mjs`（实测 92 表 / 1599 字段全对齐）。
   > **正是这个脚本抓出了「SQL 注释黏住下一列」这一层** —— 抽样或目测会永远漏掉它。

2. **★ 解析 DDL 必须「先剥注释、再按圆括号深度切顶层逗号」，顺序不可颠倒。**
   - 按**行**切分 → **单行 DDL 只解析出首列**（`sales_orders` 44 列只读出 1 列）；
   - 不先剥 `--` → 「注释行 + 下一列」黏成一段被整段跳过，**丢列指纹：该列前面恰有一个注释行**；
   - 深度切分才能兼容单行/多行，且不切断 `CHECK (x IN ('a','b'))` 里的逗号。

3. **★ 生成器必须内置「残缺即失败」自检，让「结果不合理」变成硬失败。**
   本项目判据：业务表（都有 `org_id`/`created_at`）**只解析出 `id` 一列即视为失败**，`exit(1)` 拒写。
   > 这类 Bug 的本质是**静默成功** —— 文件照样生成、console 照样 ✅、程序不报错。
   > **护栏必须卡在「产出」这一步。**

**附加一条（同样是 V3.11.1 的教训）**：两段式链路（取源 → 中间产物 → 发射最终文件）
**严禁只跑一半** —— 中间产物是新的、最终产物是旧的，这个组合必须专门核对。
**「表数对得上」不等于「内容对得上」。**

## 八、附：给「门禁之外的批量操作」的两条硬规矩（不是套件规范，但同源）

1. **删除类批量操作必须在循环里显式排除「要保留的那个名字」。**
   `for d in dist*` / `Get-ChildItem -Filter "dist*"` 都会把 `dist` **本体**一起匹配 ——
   清理 24 个 `dist-*` 垃圾目录（100 MB）时，当前构建产物被一并删掉（靠重新 `npm run build` 恢复）。
   **前缀通配 ≠ 安全前缀**：逐个列名，或显式 `-notlike "dist"` / `! -eq "dist"` 排除。
2. **删之前先 `du -sh` 量化，删之后立刻 `ls` 复核。**
   本轮若不是删完随手 `ls -d dist*` 核了一次，`dist` 缺失会一直潜伏到下一次 deploy 才炸。
   **破坏性操作的前后各一次事实核对，成本极低、收益极高。**
