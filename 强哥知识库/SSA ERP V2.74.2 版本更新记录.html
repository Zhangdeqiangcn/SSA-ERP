二、为什么新建 vendor_master 而不是复用 vendors 表

根因：V2.74.1 实测发现网关 vendors 端点 POST 直接 500。D1 里唯一的 vendors 表是「供应商门户登录账号表」——password_hash/salt 为 NOT NULL（门户登录凭据），且 SELECT * 会把登录凭据返回给 API 调用方。供应商主数据本身是供应链核心，当前存 app_state Blob、无独立关系表。
方案 A（本次采用）：新建 vendor_master 关系表，与另外 4 类网关资源（materials / customers / purchase_orders / sales_orders）架构完全一致。网关直接读写该表，与 materials 网关同构（前端 vendorStore 仍走 app_state Blob，两套来源并存）。既止血 500+凭据泄露，又给供应商主数据干净的关系表归宿。

三、vendor_master 表结构

  • org_id 隔离 + id 主键 + UNIQUE(org_id, vendor_code)
  • 主数据列：vendor_code / company_name / short_name / type / contact_name / contact_phone / contact_email / address / status / credit_level / credit_limit / used_credit / tax_id / bank_account / sales_org / reconciliation_account / tax_code / rating / blacklist_reason / blacklisted_at / qualification_expiry / remarks
  • RLS 预留：owner_id / dept_id（可空）
  • 审计列：created_at / updated_at / created_by / updated_by（NOT NULL，网关写操作由 PRAGMA table_info 探测补齐）
  • 不含 password_hash / salt / role / status(portal) —— 与门户账号表彻底解耦
