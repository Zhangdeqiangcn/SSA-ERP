① 库存预警 inventoryAlerts 迁真实 D1

变更内容

把库存预警从「本地存储块（单人不共享）」迁到 Cloudflare D1 云关系数据库，按 V2.80 双通道根治范式迁移，保留在 warehouseStore 内、最小化 API 面变动：

层改动
迁移migrations/0036_inventory_alerts.sql：建 inventory_alerts 表（org_id 隔离 + 审计列），字段全为标量（material_id / material_code / type / current_quantity / threshold / severity / created_at），无嵌套 JSON
后端functions/_shared/entities.ts 注册表加 inventoryAlert 资源，复用通用 /api/entities/inventoryAlert 端点，零新增后端函数
前端 storesrc/stores/warehouseStore.ts：新增 loadInventoryAlerts（EntityRepo 拉取、首次空库回填 mock、离线回退内存）；partialize 移除 inventoryAlerts（不再落 Blob）；启动期 src/App.tsx 接 loadInventoryAlerts

② 产成品入库 finishedGoodsInbounds 迁真实 D1

变更内容

把产成品入库单从「本地存储块」迁到 Cloudflare D1 云关系数据库，与入库 / 出库 / 盘点同款实体后端：

层改动
迁移migrations/0037_finished_goods_inbounds.sql：建 finished_goods_inbounds 表（org_id 隔离 + 审计列），字段全标量（inbound_no / work_order_* / product_* / *qty / batch_no / warehouse_* / status / operator / inspection_task_id 等），无嵌套 JSON
后端functions/_shared/entities.ts 注册表加 finishedGoodsInbound 资源，复用通用 /api/entities/finishedGoodsInbound 端点，零新增后端函数
前端 storesrc/stores/warehouseStore.ts：addFinishedGoodsInbound / updateFinishedGoodsInbound / deleteFinishedGoodsInbound 改乐观更新 + fire-and-forget 写回 D1；新增 loadFinishedGoodsInbounds（EntityRepo 拉取、首次空库回填 mock）；partialize 移除 finishedGoodsInbounds（不再落 Blob）；启动期 src/App.tsx 接 loadFinishedGoodsInbounds

为什么这样操作

V2.81.0 仅剩 inventoryAlerts / finishedGoodsInbounds 两块 Blob 残留。两块字段全为标量（无嵌套 JSON），比盘点 checkTask 更简单——迁移与实体注册直接对齐范式，无需 JSON 序列化辅助函数。至此仓库域双通道彻底根治：入库单 / 出库单 / 盘点任务 / 库存预警 / 产成品入库全部业务数组均去 Blob 直连真实 D1、跨端多人实时共享、无双源不一致。

变更内容

把 V2.81 深度对标报告（已归档 ima「强哥的知识库 → erp开发项目」）的结论与路线图正式沉淀进主计划单一权威文档 docs/ssa-erp-master-plan.md：

  • 同步状态表（消除代码已真落地但文档仍滞后的描述）：
    • 移动端 P2-20：🟡 壳 → ✅ 已真落地（V2.78 PWA 门户 + 真扫码 + 写回 D1）

为什么这样操作

强哥指令「对标计划写入主计划 + 更新状态表同步 + 迁 D1」。前两项把对标结论沉淀进主计划（单一权威），并消除过时描述——文档滞后会误导后续判断（移动端早在 V2.78 已真落地、数电票真实通道代码 V2.80 已就位，但主计划仍标「壳 / 桩」）。第三项迁 D1 是双通道根治收口，按 V2.80 同款范式落地，零新增后端函数。
