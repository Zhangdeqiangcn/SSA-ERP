第 0 期 4 条 P0 全部收口，但结论与上一轮评审报告并不相同 —— 因为这一轮全部改成了端到端实测，不再靠 grep 推断。
上一轮基于静态代码检索给出的 4 条 P0 结论，逐条实测后：1 条被推翻（委外发料本就通账）、1 条比原报告更严重（供应商门户实际有四处断裂）、2 条属实但范围需细化（合并账簿的列本就存在，缺陷在聚合维度；质量冻结的真漏洞不是台账不写，而是拦截漏了一个状态）。
★ 本轮最可复用的两条教训：
① 静态检索只能告诉你「某处没有这个字符串」，不能告诉你「链路是断的」。P0-1 若照原结论去改，最坏结果是把一条本来正确的过账链路重写一遍、改坏了反而更难查。
② 本地全绿 ≠ 生产正确。P0-4 首轮修复后本地 31/31 全绿，部署到生产只有 21/30 —— 差异点是注册端点靠「公司码前 3 位 LIKE + LIMIT 1」猜组织，而生产同前缀组织有 762 个（本地仅 58 个），LIMIT 1 在本地恰好挑中正确组织、在生产则静默落错。测试环境的规模差异会系统性地掩盖这类缺陷。

原报告根因：只 grep 了 functions/api/subcontracts/*.ts，未追通用出库端点。		 降级为 P2-6 凭证可追溯性增强（凭证 source='inventory' 缺委外单号回溯标记；委外单与过账无强绑定）。不需重写过账链路。
P0-2 合并报表无账簿条件
两套账混算		 属实，但需细化。vouchers.ledger_book / voucher_items.ledger_book 列本就存在（迁移 0065 加、0068 重建保留）；生产实测每组织确有 0000 法定 + 1000 管理两套账。真实缺陷是聚合 SQL 抹平了账簿维度（GROUP BY 不含 ledger_book）+ 抵消跨账簿进行。 ✅ 已修：聚合按账簿分组、抵消只在同账簿内、账簿白名单入参、结果带账簿清单；前端账簿多选 + 账套列 + 按账套分组切换 + 导出带账套列。
P0-3 质量扣留不写冻结量
判废的料可出库		 属实，且发现更深漏洞。① frozen_quantity 全链路无人写无人读；② 既有质量拦截（V3.63.0）只查 status IN ('pending','active')，漏掉 rejected → 「已判不合格但尚未报废/返工/退货」的料实物仍在库却能出库，这才是真漏洞；③ 前后端状态词表分裂（前端把后端 released 当扣留中 → 物料永久锁死）。 ✅ 已修：冻结量落台账 + 同步扣 available_quantity；放行/删除回冲（实际解冻量封顶防虚增）；出库按可用量硬拦截并留痕；新增共享状态词表 functions/_shared/qualityHoldStatus.ts 前后端统一；拦截补上 rejected。
P0-4 供应商门户无审核激活入口
整模块归零		 属实，实际比原报告更严重 —— 实测共四处断裂。① 前端调用的 6 个端点（待审/审核/拒绝/拉黑/解黑/评级）后端全部不存在；② 双供应商表断裂：vendors（门户账号表）15 行 vs vendor_master（主数据表）90 行，按 id 与 vendor_code 均零匹配 —— 审核写主数据表、登录读账号表，状态永不同步；③ 自助注册只写账号表 → 管理端根本看不到申请；④ 生产复验新发现：注册端点靠「公司码前 3 位 LIKE + LIMIT 1」猜组织，生产同前缀组织 762 个 → 供应商静默落到别的组织，管理端永远查不到。 ✅ 已修：补齐 7 个端点；新增共享 functions/_shared/vendorApproval.ts 做两表状态同步与状态归一（存量 active 幂等自愈为 approved）；注册双表写入；新增归属歧义守卫（多候选 409 明确拒绝）。

关键实现要点（供后续维护参考）：
  • 共享状态词表 functions/_shared/qualityHoldStatus.ts：HOLD_OCCUPYING_STATUSES = pending / active / rejected / open / inspecting。后端三处（扣留创建、扣留 PUT、扣留 DELETE）与库存拦截统一引用，前端 utils/supply.ts 的 isHoldActive 语义对齐（状态缺失 → 保守占用）。三处各写一份清单就一定会分叉，合并才防复发。
  • 共享双表同步 functions/_shared/vendorApproval.ts：syncVendorStatus 先按 id 定位两表、再按 vendor_code 跨表兜底，状态变更必须经它，避免「审核一百次、账号状态永不变」。
  • 路径纪律：前端调 POST /vendors/:id/rate（单数，写评级）与 GET /vendors/:id/ratings（复数，读记录）—— 必须分两个文件，否则会出现 405。
  • 归属判定：body.orgId 精确 → body.companyCode 精确 → 前缀匹配仅唯一命中才接受，多候选 409 拒绝。保留 V3.21.0 的 likePrefix 转义（用户输入前 3 位不能当通配符）。
