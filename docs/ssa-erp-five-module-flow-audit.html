二、结论速览

✅ 主干已真正打通：采购收货暂估、生产领料与完工、销售出库成本、盘点、委外拆账（1408/1405/2201）、V3.60.0 刚补齐的往来与收入（2201/2202/1122/6001/2221/1002）——这些主干链路的服务端算账、原子批次、幂等抢占都已正确实现，且经生产端到端回归（44 套件 PASS 32、 全量 PASS 1567 / FAIL 0）验证。
⚠️ 本轮核心结论：主干虽通，但「跨模块的边界」是薄弱环节——发现 3 个 P0。它们的共同特征是「单模块内看是对的，跨模块看就断了」：
  • 期末结账对库存链路完全失守：isPeriodClosed 只挂在凭证与折旧端点，入库/出库/调拨/盘点在已关账月份仍可过账 → 可任意制造跨期账（已生产坐实）
  • 应收收款链路完全缺失：全库无销售收款端点，1002 只出现在采购付款 → 应收 1122 只增不减，「应收账款周转率/账龄」永远失真
  • 行级三单比对键永不相等：发票明细与入库行的行锚点在前端从未传递 → 三单匹配把每一行都判成「欠交/欠票」→ 拦截所有付款（已在 V3.60.0 修44 号套件时被实测撞到并绕过，生产库数据显示行表19 行中 3 行有值而头表 79 单全为 0，反向印证链路不一致）

另一个值得强哥注意的结构性问题：「服务端写了但接口读不出来」是本轮反复出现的模式。采购订单已交量（delivered_quantity）列在库里存在、服务端也确实在回写，但 purchaseConfig 字段白名单零登记该字段 → parentToApi 不输出它 → 界面永远看不到。这解释了为什么生产库 79 张采购订单的已交量全部为 0，而行表却有 3 行有值（前端能写、因为前端不经过服务端白名单）。

四、P0 严重缺陷（3 项）

P0-1 · 期末结账对库存链路完全失守（跨期账）仓库↔财务已生产坐实

应有链路：会计期间关闭 → 该期间禁止一切过账与记账
实际：isPeriodClosed 只在凭证手工端点与折旧端点校验；入库/出库/调拨/盘点/倒冲的服务端过账与自动凭证一律无拦

危害：已关账月份仍可入库/出库并自动生成 status='posted' 凭证 → 报表跨期、期初与期末对不上、审计追溯失效。

inventoryPosting.ts:199, 321 ← postInbound/postOutbound 全程无 isPeriodClosed 校验 voucherWriter.ts:97-151 ← writeVoucher 自动凭证路径同样无拦 对照：fixed-assets/depreciate.ts:93← 唯一正确设防处
✅ 生产坐实（已实测）：探针在本轮隔离组织内先把 2026-08 关账（接口返回 {"status":"closed","issues":[]}），随即在 2026-08 建一张 completed 入库单 → 接口返回 201，入库被接受，未被拦截。该结论已由生产真实端点坐实，非静态推断。

P0-2 · 销售收款链路完全缺失，应收只增不减销售↔财务

应有链路：销售收款 → 借 1002 银行存款 / 贷 1122 应收账款
实际：全库不存在销售收款端点；1002 仅出现在采购付款（arapPosting.ts:146）

危害：销售订单的 received_amount 是可写字段但不产生任何凭证 → 1122 应收余额只增不减 → 「应收账款账龄」「周转率」「DSO」等全部财务指标永久失真；且与采购侧「付款会冲应付」形成不对称。

sales-orders/[id].ts:103 ← receivedAmount 是订单可写字段 arapPosting.ts:146 ← 1002 只在 generatePaymentVoucher（采购付款） 全库 grep：无 fin-receipts / sales-receipt 类端点 chatbi/index.ts:254 ← 前端智能问答直接用 total_amount − received_amount，口径已失真
⚠️ 与已修项的关系：V3.60.0 补齐的是「开票确认应收 1122」（应收增加侧），但收款冲减侧（应收减少）从未存在。这不是本轮新引入的缺陷，而是上一轮审计只覆盖了「业务→财务」单向量、遗留的另一条腿。

P0-3 · 行级三单比对键永不相等，付款闸门拦截所有付款财务↔采购/销售已被实测撞到

应有链路：订单行 ↔ 入库行 ↔ 发票行 通过行锚点（order_item_id）一一对应，逐行比对数量
实际：行锚点由前端传入，但前端全库零处传递（grep orderItemId 仅命中测试脚本，命中 0 个前端调用点）
threeWayLineMatch.ts:107-110, 145-147 keyOf(): 入库/发票行锚点取 order_item_id（空）→ 退回 mc:编码#单位 订单行锚点取自身 id → oi:xxx ⇒ 两侧键永不相等 ⇒ inboundQty=0 ⇒ 每行判 short threeWayMatch.ts:264-268 ← 汇总为 LINE_MISMATCH inbound-orders/index.ts:191 ← 服务端确实会写 order_item_id，前端不传则为空

危害：只要该组织存在任何一张带明细的发票，付款闸门就会把每一行都判成「欠交/欠票」→ 所有正常付款被 422 拦截，业务停摆。

✅ 已被生产实测撞到（V3.60.0 开发期）：本人在上一轮编写 44 号守护套件时，首跑即被这条闸门拦下（错误原文「1/1 行超差 —— 欠交/欠票 100件（入库 0、开票 0、订单 100）」）。当时按「测试造数问题」修正了套件（补传 orderItemId 行锚点），但并未修前端的真实链路——即界面正常操作时依然不传行锚点。本轮审计把它重新定性为 P0 缺陷（而非测试问题）。
⚠️ 诚实边界：该缺陷在生产是否已造成「实际付款被拦」，取决于生产组织内是否存在带明细行且已审发票。生产库 fin_invoices 本轮隔离组织内样本为 0，无法直接断言全量生产影响面，需专项统计后量化。
