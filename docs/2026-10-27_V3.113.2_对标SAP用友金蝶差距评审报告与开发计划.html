结论先行 三句话

① 差距不在「功能清单」，在「账实相符」。与三家标杆逐项比对后，SSA 在 MRP、有限产能排程、成本卷积、期末结账三闸、凭证自动生成、预算硬闸门、审批流、批次追溯、条码作业这些核心引擎上已达到「可演示、可运行、有真实运算」的水准，其中审批流与编码规则甚至优于国产三家。曾识别 4 个 P0 级断链让账实对不上：委外发料不写库存（1408 借方永不发生、借贷必不平）、合并报表无账簿条件（法定账套与管理账套凭证混算）、质量扣留不写冻结量（判不合格的料可出库）、供应商门户无审核激活入口（功能做了 95%，剩 5% 让整模块归零）。这四条是「差最后一公里」而非「差一代半」，修完账才敢谈生产可用。

【V3.113.3 更新 · 实测复验】这 4 条 P0 结论基于静态代码检索推断，端到端实测后：委外发料链路本就通账（结论推翻，降级为 P2-6 可追溯性）；合并账簿口径与质量冻结量已修复并验证（其中发现既有质量拦截漏掉「判不合格未处置」这一真漏洞，已补）；供应商门户审核链路已修复并验证（实际缺陷比原报告更严重：6 个端点缺失 + 双供应商表零匹配 + 注册只写单表）。端到端验证 30/30 断言全通过。
② 智能化的真实差距是「两代」，但原因不是模型。SAP 已部署 50+ 个 Joule 助手编排 200+ 个专职智能体、用友 YonClaw 可执行端到端流程、金蝶灵基配 70 个 ERP 连接器与 1127 个工具并有 3706 家付费用户。SSA 已有真大模型调用（functions/api/ai/chat.ts 直连 chat/completions，含服务商/模型/字符量审计）且 ChatBI 已是工具调用式（tool.run 路由 9 个真实只读 SQL 工具，非写死假对话）。缺的不是业务逻辑，而是「把业务逻辑暴露成智能体可调用工具」的那一层编排 + 治理。三家都在补的「AI 排产」也都建立在 APS + 工序数据之上——SSA 的底座不差。
③ 战略上不该跟 SAP 比平台，该跟用友比工艺。10–50 人制造区间，SAP 根本不是有效选项（S/4HANA 公有云首年 150–300 万、实施 3–6 个月，且中国区私有云路线图上要到 2026 Q3 才落地阿里云）；真实对手是用友系与金蝶系。SSA 唯一可防守的差异化战场是：云原生零升级 + 国产化开箱即用 + 制造工艺可计算。最该对标的不是金蝶的「小K 超级入口」叙事，而是用友 U9 cloud 2026 的智能裁切 + 工序级成本 + 废品成本多算法分摊——这三样都是可验收的具体工艺能力，而非平台叙事。

上表四条 P0 结论最初基于静态代码检索（grep）推断。V3.113.3 逐条做端到端实测后，结果为：1 条被推翻、1 条比原结论更严重、2 条属实但需细化范围。

#原结论实测结果修正动作
P0-1 委外发料不过账，库存不减、借贷必不平 结论推翻。实测链路：subcontractStore.issueMaterials → 通用出库端点 POST /api/outbound-orders（type=subcontract）→ 服务端扣库存 + 写流水 + 生成凭证 OUT-{outboundNo}，借 1408 委托加工物资 / 贷 1403 原材料。7/7 断言全过（库存 100→60、存货价值 0→600、凭证借贷平衡）。 降级为 P2-6 可追溯性增强：当前凭证 source='inventory'、无委外单号回溯标记；委外单与过账无强绑定（子单据可被单独删改）。不需要重写过账链路。
P0-2 合并报表无账簿条件，两套账混算 属实，需细化。vouchers.ledger_book / voucher_items.ledger_book 列本就存在（迁移 0065 加、0068 重建保留），生产实测每组织确有 0000 法定 + 1000 管理两套账。真实缺陷是聚合 SQL 抹平了账簿维度（GROUP BY 不含 ledger_book）+ 抵消跨账簿进行。 ✅ 已修：聚合按账簿分组、抵消只在同账簿内、账簿白名单入参、结果带账簿清单；前端账簿多选 + 分列 + 账套切换 + 导出带账套列。
P0-3 质量扣留不写冻结量，判废的料可出库 属实，且发现更深层漏洞。① frozen_quantity 全链路无人写无人读；② 既有质量拦截（V3.63.0）只查 status IN ('pending','active')，漏掉 rejected → 「已判不合格但尚未报废/返工/退货」的料照样能出库（这才是真漏洞）；③ 前后端状态词表分裂（前端把后端 released 当扣留中 → 物料永久锁死）。 ✅ 已修：冻结量落台账 + 同步扣 available_quantity；放行/删除回冲（实际解冻量防虚增）；出库按可用量硬拦截；词表前后端统一为共享模块 qualityHoldStatus.ts；拦截补上 rejected。
P0-4 供应商门户无审核激活入口，整模块归零 属实，且比原报告更严重。除缺审核端点外，实测发现三处额外断裂：① 前端调用的 6 个端点（pending-approvals/approve/reject/blacklist/unblacklist/ratings）后端全部不存在；② 双供应商表断裂——vendors（门户账号表）与 vendor_master（主数据表）生产实测各 15 / 90 行，按 id 与 vendor_code 均零匹配，审核写主数据表、登录读账号表，状态永不同步；③ 自助注册只写账号表 → 管理端根本看不到申请。 ✅ 已修：补齐 7 个端点；新增共享 vendorApproval.ts 做两表状态同步与状态归一（active → approved 幂等自愈）；注册同时双写两表；评级落 vendor_performance 并还原前端契约。

端到端验证结果：31/31 断言全通过（P0-2 合并账簿 7 项、P0-3 质量冻结 11 项、P0-4 门户激活 12 项、归属歧义守卫 1 项），脚本见 scripts/_verify_p0_fixes.mjs。本地与生产各跑一轮，均 31/31 通过。

★ 另一条可复用教训（生产复验才暴露）：本地全绿 ≠ 生产正确。P0-4 首轮修复后本地 31/31 全绿，部署到生产只有 21/30 —— 差异点是注册端点的组织归属：它靠「公司码前 3 位 LIKE 匹配 + LIMIT 1」猜组织，而生产同前缀组织有 762 个（本地仅 58 个），LIMIT 1 在本地恰好挑中正确组织、在生产则静默落错 → 申请进了别的组织，管理端永远看不到 → 症状与「审核端点缺失」一模一样，却完全是另一个根因。测试环境的规模差异会系统性地掩盖这类缺陷，故凡涉及「按某字段查唯一记录」的逻辑，必须在生产数据规模下复跑一次。

六、已具备的强项（勿破坏 · 对标确认）

以下能力经源码级核查确认有真实运算、不是页面壳，且在对应维度不弱于三家标杆，整改时不要误伤：
  • 审批流引擎　approvalFlowStore.ts 773 行，含条件组求值；服务端 approvalInstance.ts 支持委托路由 + 职责分离（SoD）、撤回、自动发起。深度接近 SAP Flexible Workflow，三家国产产品均未达到。
  • 编码规则引擎　编号规则中心化配置 + 前后缀 + 断号检查，领先于三家（三家均有编号规则，但国产两家多为简单流水）。
  • 质量域纵深　GB/T 2828.1 AQL 抽样（样本量 n / 接收数 Ac / 拒收数 Re 全部真算）、检验标准版本化、缺陷分级、NCR→CAPA（8D / PDCA）闭环、质量冻结在过账层硬拦截（checkQualityBlocked）、FMEA、SPC、COA。深度超过一般国产中型 ERP。
  • 期末结账三闸　试算平衡 + 跨期凭证 + 折旧未计提；反结账需更高权限 + 强制填原因（≥4 字）+ 审计；三态（开账 / 损益已结 / 已结账）。金蝶与用友的智能结账编排（可视化定义月结步骤 + 账证/账账/账实三一致 AI 校验 + 多组织多账簿并行结账）是值得抄的形态，但底座 SSA 已有。
  • 预算硬闸门　paymentGate.ts 服务端 fail-closed，读取失败按超预算拦截，超预算 422 拒写，管理员 override 留痕。旧版「假管控」已闭环。
  • 凭证四路自动生成　采购确认 / 付款 / 销售收款 / 库存入出库，服务端生成 + 金额复核 + 幂等键。旧版「业财一体化是打补丁」的判断已被推翻——单账套 R2R 闭环是真实的。
  • 批次正反向追溯　纯函数 buildTrace，上游可追到供应商、下游可追到客户，跨多层 BOM 与工单。三家都有，但金蝶/用友多数只在批次级。
  • 条码与扫码　自实现 Code39 编码 + 条形绘制 + 二维码；BarcodeScanner 用 zxing + 摄像头真实解码（旧版判定的「PDA 扫码是壳」已不成立）。
  • 真实大模型调用与 AI 审计　functions/api/ai/chat.ts 直连 chat/completions，审计记服务商 / 模型 / 消息条数 / 字符总量，刻意不记对话正文（数据出境合规的正确做法）。
  • 领域宽度　21 个业务域、253 页，覆盖三大标杆的绝大多数功能面且含 ESG、COPA、SOP、WIP、设备保养、寄售、三方代销、电商、售后 等长尾场景。

战场说明SSA 现状建议

  • 建议节奏　第 0 期 1.5 周、第 1 期 4 周、第 2 期 5 周、第 3 期 7 周，可并行推进第 1 与第 2 期（财务与制造互不冲突），总历时约 4 个月（两人并行）或 5.5 个月（单人串行）。
  • 取舍建议　若资源只够做一件事 → 做第 0 期（17 人天，直接把生产可用率从 62% 推到约 75%）。若目标是赢单而非自用 → 加第 1 期的「工序级成本 + 废品分摊 + 智能裁切」三件套（合计约 17–21 人天）。
  • 不推荐　不建议在本轮追第 3 期的平台化叙事。理由：智能化差距虽是两代，但本项目的瓶颈是生产可用率与制造工艺深度；先让系统敢上生产、能在制造客户现场算出准确成本，再谈智能体。
