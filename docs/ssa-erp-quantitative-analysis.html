二、生产 E2E 失败全景（77 条 → 5 类根因）

77 条 FAIL 不是 77 个独立 bug。量化归并后，约 58%（44 条）是「前置造数失败导致的连锁放大」——套件先建一张单据失败，后面所有依赖它的断言全挂，根因其实只有 1~2 个。真正独立的根因 5 类：

根因类占比/条数代表失败性质
① 前置造数连锁44/77（58%）28-work-order-backflush 44 条：建工单 400（缺 materialId）→ 完工/倒冲全 404测试数据契约问题，非代码缺陷
② 契约/期望过时7/7707-rls：期望 buyer 建供应商 201，但权限矩阵已定 vendor create=false → 403（fail-closed 是对的）守护套件期望值没跟上权限矩阵演进
③ 数据残留4/7725-consolidation-enhanced：账套编号撞号 DATA_UNIQUE（上轮残留未清）生产库脏数据，非代码缺陷
④ 我引入的回归2/7721-approval-flow：审批流 module=* 打断 buyer 协作改（P0 整改副作用）真需修，见根因 #R1
⑤ 真残留缺陷16/7717-bom-domain：嵌套 BOM 摊平只回 2 行期望 5 行（子树写入真有问题）真需修，服务端 36 条之一

★ 关键判断：代码的真实健康度被 ①②③ 放大低估了——58% 的失败是测试数据契约，2 条是我上版引入的、已知且给了解法的回归。扣除这些，真正待修的真缺陷是 ⑤ 的 16 条 + 服务端扫描出的 36 条（去重后），其中 P0 仅 3 条竞态。

四、根因收敛（36+2 → 6 个根因）

缺陷虽多，但收敛度很高——绝大多数源于少数几个根因。修根因比逐条打补丁高效得多：

#根因命中缺陷数统一解法
R1父子/多表写入未原子化（头+子、库存+流水+凭证分多步独立 .run()）约 14把「父表 + 全部子表 / 物料 + 流水 + 库存记录 + 凭证」收进同一 db.batch()，失败整批回滚。一处范式改动覆盖入/出库/调拨/销售/采购/工单多端点。
R2过账幂等标志 check-then-act 非原子（读到 0 → 过账 → 置 1，三步可并发穿透）3（全 P0）守卫条件并入 UPDATE：UPDATE … SET inventory_posted=1 WHERE id=? AND inventory_posted=0，读 affected_rows 判断是否本次过账（条件抢占，无锁即原子）。
R3删父不清子 / 删单据不回滚关联台账（孤儿引用）约 6删除端点统一 db.batch([删父, 删各子表, 回滚冻结数])；quality_holds 删除前 UPDATE inventory_records SET frozen_quantity=frozen_quantity-?。
R4吞错不回滚（异常 catch 后静默继续，返回成功）约 5把「过账失败」上抛到端点，端点回滚 status completed→pending 并在响应告知；凭证缺失与库存/流水同生共死（并入 R1 的 batch）。
R5fail-open 静默放行（异常/缺失时默认放行或默认 1/0）约 4逐分支区分「合法缺省」vs「配置损坏/查询故障」：前者可降级、后者一律 fail-closed 拦住（对齐已修的 guardBudget/isPeriodClosed 口径）。
R6写端点漏 guardOperation / 缺 org_id 过滤（越权写 + 跨组织）约 5给 fx/refresh、entities/[id] 通用路由 PUT、vouchers UPDATE/DELETE 补齐 guardOperation 与 AND org_id=?，与专用端点口径对齐。

★ 回归 R-REG（V3.47.0 新增 2 条失败）独立于上 6 因，解法单列：审批流的 module 归属从 * 改回具体协作模块（如 approval 或 sales），让 BUILTIN_ROLE_OPS 中本有「协作改审批流」权的角色通过；不要把 * 放宽，那会让只读角色也能改全公司管控逻辑（fail-closed 的初衷要保住）。

五、分级解决方案（按投入产出比排序）

第一步 · 止血（当天可做，最高 ROI） —— 修 R2 三个 P0 竞态（过账幂等改条件 UPDATE 抢占）+ R-REG 审批流 module 回归。改动小、直接消除「并发双过账」这种会真实做坏库存账的数字错误，并让 E2E 恢复全绿基线。约 0.5–1 天。
第二步 · 建原子底座（1–2 天） —— 落地 R1 + R3 + R4：抽一个 atomicParentChild / atomicPosting 范式，把入/出库/调拨/销售/采购/工单的「多表写 + 删除 + 过账」全部收进同一 batch。这是数据完整性维度从 C+ 提到 B+ 的关键，一次范式改动覆盖 ~20 条缺陷。约 1.5–2 天 + 生产守护。
第三步 · 堵放行后门 + 补越权面（1 天） —— R5 fail-open 收敛 + R6 守卫/组织隔离补齐。把剩余 fail-open 与缺 guardOperation/org_id 的点按已修口径对齐，消除跨组织与越权写残留。约 1 天。
第四步 · 性能与展示修正（0.5 天） —— 凭证列表 N+1 改批量查、列表 items 占位补齐、金额浮点累加口径统一。收尾。
第五步 · 测试数据契约治理（并行） —— 修 28 套件的前置造数（工单带 materialId）、清 25 残留、对齐 07-rls 的权限期望。让守护套件回到可信的「全绿基线」，否则以后每次回归都分不清真 bug 和数据脏。约 0.5 天，可与第一、二步并行。
诚实边界说明
本报告的静态面（门禁 / 单测 / 代码扫描）可以 100% 复核；但并发双过账、跨组织越权这类缺陷必须连真实数据库做并发与负例测试才坐实——静态扫描只能「指出风险点」，不能「证明生产上必然发生」。建议第一、二步修完后，重跑全量生产 E2E（届时 R-REG 与前置数据契约也应全绿），并拉生产库核对「流水重建余额 = 库存余额、无重复凭证、无孤儿子行」三项，才算把数据完整性真正验穿。
