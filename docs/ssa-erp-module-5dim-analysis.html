一、五维评分口径（先看怎么打分的）

本次比 V3.47 的「四维」多两个维度：易用性（操作路径、认知负担、反馈及时性、菜单组织、搜索与空状态）与逻辑合理性（状态机/业务规则是否贴合行业惯例、会不会产出违背常识的结果）。评分沿用 V3.47 量化报告的四维基线做对照，保证数字可比。

可用性 A
功能能不能真正端到端用起来（接口在、行级权限已登记、不是死链/占位）
数据完整性 B−
多表写是否原子、删单据是否清子表（不留孤儿引用）
准确性 B
金额/计算对不对、有没有静默放行、口径是否唯一
易用性 C+
菜单过载、认知负担、反馈及时性（本次最薄弱）
逻辑合理性 B+
状态机与业务规则是否贴合 SAP/金蝶/用友惯例

字母级：A 优 / B 良好 / C 及格偏下 / D 危险。± 半档。数据完整性、易用性为全系统两个短板。

三、各模块五维详解与改善建议（按域）

① 仓储物流域 —— 核心最稳、菜单最挤、删不清子

维度评分证据与说明
可用性B+入/出/调/盘/查核心全通。库存流水重建余额 == 库存表余额（最新 E2E 套 35 断言全绿）。
数据完整性B−（域内最低）删单据不清子表：采购单删了头表不清子项、调拨/盘点/盘亏单据删了不清关联台账。删父先于删子是两次独立执行，子删失败=头已删、孤儿子行残留（R3 未收口）。
准确性B+成本双轨已消除（V3.47 第3批）、移动均价服务端唯一滚动、过账竞态 V3.48 已修（条件 UPDATE 抢占）。残留：金额浮点累加口径 ≤0.01 元漂移。
易用性C+（全系统扣分大头）仓储物流一个分组下挂 16 个子菜单（报检/入库/成品入库/出库/盘点/查询/批次/库龄/条码/仓库主数据/跨组织转储/调整/序列号/批次追溯/寄售/波次RFID），非仓管专业用户很难记住谁归谁。
逻辑合理性B+倒冲、批次、库龄逻辑贴合 SAP 301。质检扣留删除不回滚冻结库存，逻辑上会造成「可用库存虚高、出库绕过冻结」。
改善建议（按 ROI）：
  • 【高·数据完整性】把「删单据」统一收口：删父 + 删全部子表 + 回滚冻结数，进同一原子批次，失败整批回滚（一次范式改动覆盖采购/调拨/盘点/质检扣留多处，对应 R3 约 6 条）。
  • 【中·易用性】菜单分「常用 / 进阶」两层：默认只露出 入库/出库/盘点/库存查询/批次 5 个高频，其余（寄售/波次RFID/序列号/跨组织转储）折叠进「更多」。强哥已有工作台，可再按使用频率排序置顶高频操作。
  • 【中·可用性】列表接口把明细从「恒空占位」改成随列表带出（或前端统一懒加载），避免列表看着「无明细」实际有。

② 生产域 —— 逻辑最规范、菜单 21 项最重、删工单不清领料

维度评分证据与说明
可用性B+工单/MRP/工艺路线/委外主链路完整，倒冲发料已服务端权威化。高端排程（APS/CRP/甘特/MES/S&OP/重复制造）落地度需逐个核实（C 档）。

  • 【中】出一份「高端排程功能落地度核实清单」，逐个标注 真库/mock/演示，把「看着能用其实没接后端」的项标出来（对应教训㊲：界面点得动≠动作已落库）。

五、高端功能落地度核实清单（U2 核实完成 · 2026-10-08，V3.53.0）

六、采购/财务 数据对齐专项审计（41 号审计套件 · 2026-10-08，V3.55.0）

针对「采购域 + 财务域是否存在数据不对齐 / 不准确 / 缺失项」，不靠历史结论、逐项回代码走查 + 打真实生产接口取证（新增 41 号审计套件，隔离组织自动清理、可复跑）。结论分「坐实正常」与「发现缺口」两组。

先说「没问题的」—— 这些是资金重灾区、已实测坐实扎实：
  • 凭证借贷平衡：手工凭证 Σ借≠Σ贷 被服务端拒绝（400），不平绝不落库（41 号 G5 坐实）。
  • 三单匹配付款闸门：开票超订单 / 入库不足 / 无发票 / 付款超发票 四类各拦，且被拦后不写库、通用实体路由后门也拦（27 号 44 断言全绿）。
  • 累计超付守卫：同一发票拆多笔小额付款，超发票额即 422（V3.49 已 fail-closed 收口，33 号坐实）。
  • 预算闸门：按会计期间取数、查不到已发生额时 fail-closed 拦住（V3.47 根治 voucher_items 无 org_id 列的假累计）。
  • 入库金额自算：入库单金额按「实收数量 × 单价」服务端实算、单价缺失回物料主数据兜底（V3.45 根治「入库金额恒为 0」，41 号 G2/G4 佐证兜底路径）。
逐项坐实的 4 个缺口（按严重度排序）：
  1. 【不对齐·中等】采购/销售订单头金额 = 客户端自报，服务端不勾稽 Σ明细。41 号 G1 坐实：故意传头金额 99999、明细合计 3000，服务端照写 99999。销售侧 sales-orders POST 同构（走查确认）。后果：用户在界面看到的「订单总额」可能和明细加起来对不上；但不影响付款核算——三单匹配取数用的是 SUM(明细.amount)（41 号 G2 坐实），所以这是「展示值失真」而非「资金判定错误」。修法：建单时服务端把 totalAmount 改写为 SUM(items.amount)（或建后校验差异>容差即 400），一行改动堵住。
  2. 【缺失项·中高】发票主表路由建单不自动拆明细行，行级三单匹配实战拿不到发票数量。41 号 G3 坐实：主表路由 /api/entities/finInvoice 建发票后 fin_invoice_items 明细行=0；明细表通道存在（单独 POST finInvoiceItem 能写 201）、三单匹配的行级比对也支持读它，但「随发票录明细」的主流程没接——所以实战中发票基本都没有明细行，行级比对会走「明细为空即跳过」的兜底（如实标注、不误拦）。后果：行级「某物料既没到货也没开票」的精细识破能力，在没录发票明细时形同虚设。修法：发票表单加明细录入并随主表原子写 fin_invoice_items（表/RLS/读侧均已就绪，只缺写入通道）。
  3. 【不准确·边缘】入库单「无单价 + 物料无主数据」时金额退化为 0。41 号 G4 坐实：明细不传单价、物料编码查无主数据时，兜底取不到单价、金额落回 0，三单匹配「入库金额」侧失真（到货率 0%、正常付款可能被误拦）。注意：这是数据治理缺口不是计算 bug——只要物料主数据维护了移动均价/标准价/采购价、或入库单填了单价，就正常；只有「新物料没建档 + 入库没填价」这个交叉场景才触发。修法：把「无主数据物料」建单时强制要求填单价（或建档），或至少入库金额=0 时打醒目提示。
  4. 【不准确·轻微·待量化】采购订单信用占用 / 收款等「自报累计字段」缺服务端校验。销售侧走查发现信用额度校验依赖 body.grandTotal（客户端传值），若头金额失真会连带信用判断失真；采购侧 deliveredQuantity、creditOccupied 等累计字段也是客户端回写、服务端不复核。影响面待生产库存量量化（见下方诚实边界）。

诚实说明：以上 4 项均为「读代码 + 打真实接口复现」坐实的机制；它们在生产真实存量数据里影响多少条记录（例如实际有多少张头金额≠明细合计的订单、多少张无明细的发票），需连生产库做 COUNT 聚合统计，本轮因直连库工具在 Windows 沙箱下派生进程报 EBUSY、未能取到存量数字，不编造影响面，列为待办。41 号审计套件已固化进 scripts/prod-e2e/suites/，可随全量回归复跑（PASS 8 / WARN 3 / FAIL 0，缺口以 WARN 记录不阻断）。
