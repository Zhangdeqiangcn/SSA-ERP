本轮真正做到了什么

  • 修掉了 8 处生产系统错误（500）：全部落在「提交内容不完整」的写入请求上。根因统一——单号等「不允许为空」的列收到空值后直接写库，数据库拒绝、接口没人接住、被兜底成一句笼统的「请求处理失败」。现在全部变成「请填写「入库单号」后再提交」这类能照着做的话。
  • 顺带挖出一个更隐蔽的问题：工单领料原先什么都不填也能建单成功（返回成功并生成单号）。一条数量为 0 的空记录会占住「该物料已领料」这个判断位，导致后面真正要领料时反而被挡住——业务被自己造出来的空记录卡死，还会让完工倒冲发料算错应补的差额。已拦下。
  • 零误伤：五个端点用完整入参实测，全部正常建成，五条测试数据全部清理干净。新增生产端到端套件 31（26 条断言），并把「完整入参仍要能建成」写成了断言——防止将来出现「为了不报错而把功能拦死」的假修复。

最该知道的三件事

  1. 功能面已经不输中小厂商，输在深度。16 个域里「完全没有」的只有少数几项（界面多语言、真实税务通道、实施方法论），而「明显偏弱」的有 9 项，集中在成本精细度、智能体自主执行、实施与运维工具链。
  2. 历史文档里有失实结论，本轮纠正了一条。旧记录曾写「入库单 / 出库单创建必 500 是误报」，实测证明只对一半：字段名填错时是正常的 400，但空载荷确实是 500。教训是侦察结论要按「入参形态」分档复现，只试一种形态就会得出片面结论。
  3. 有 3 件事我不能替你拍板（字段级权限的「只读 / 必填」两个维度、操作权限开关怎么处置、要不要做必填通用化），已列在第七章，附三条路径与代价对比。

1 · 财务与会计表 vouchers / voucher_items / fin_chart_of_accounts · 接口 vouchers · 页面 Finance
优势
服务端借贷平衡强制校验（科目必填、借贷合计相等、容差半分），且合计由服务端从分录反推，杜绝「分录改了合计没跟着改」；会计期间与期末结账管控；合并报表与多账簿已落地；折旧计提服务端化并生成权威凭证、同一期间幂等。
劣势
只有一套会计准则口径，无法多准则并行出表；税务申报未一体化（数电票核验目前是模拟桩，需企业税号与服务商密钥才能启用真实通道）；没有凭证模板与常用凭证，重复分录靠手工。
缺失
外部合规认证（三家都有各自的合规背书）；财务共享与全球司库这类集团级能力。
机会
思爱普 2608 的「凭证生成智能体」是最好抄的一课：从非结构化信息（发票、邮件）推荐会计科目与金额、生成待审凭证。本系统已接通大模型且有审核流程，只需补「生成草稿 → 人工确认 → 过账」这一条链路，风险可控。
改进
① 补凭证模板与常用凭证（小、见效快）；② 启用数电票真实核验（需你提供企业税号与服务商密钥，属外部依赖）；③ 凭证草稿智能生成（需先定「哪些单据允许智能体起草」的口径）。
2 · 采购与付款表 purchase_orders / three_way_match / fin_payment_plans · 接口 purchase-orders / three-way-match · 页面 Purchase
优势
三单匹配超差硬拦，且被拦后不写库（拦而不住等于假拦截），超差返回 422 与中文原因及差额；判定口径收敛为唯一来源（不含税金额 + 1% 相对容差），消除了此前三套互相矛盾的口径；供应商门户已能确认订单、报价、变更资料。
劣势
没有寻源与招投标；没有采购合同全生命周期（签订、变更、履约、结算）。金蝶星空的采购云已含智能寻源与货源清单经营。
缺失
供应商自助对账门户（目前对账靠人工发出）。
机会
采购执行智能体：自动比价、异常交期预警、报价异常识别。本系统已有比价加权评分与货源清单，数据基础现成。
改进
① 补采购合同管理（中）；② 交期风险预警（小，复用现有预警框架）；③ 采购执行智能体（需先定「智能体能替采购员做哪些决定」的边界）。
3 · 库存与成本核算表 inventory_records / materials · 接口 inventory-records / stock-transfers / inventory-adjustments · 共享模块 inventoryPosting
优势
移动均价滚动；出入库成本凭证由服务端权威生成（金额取服务端计算值，不接受前端传值）；批次与序列号双向穿透追溯（成品批次 → 工单 → 原料批次 → 供应商）；库存调整与调拨齐备。
劣势
只有移动均价一种计价方式，缺标准成本 / 先进先出 / 个别计价并存；没有标准成本与实际成本的差异分析，也就没法回答「这个月成本为什么高了」。
缺失
成本还原（用友在高科技制造方案里主推的能力）。
机会
成本差异自动归因——把「材料价差 / 量差 / 制造费用差异」拆出来，再用自然语言解释波动原因。这是三家都在讲但中小企业用不起的能力，本系统架构轻，做成内置功能有差异化。
改进
① 补标准成本与差异分析（中，需先定成本口径，属需你拍板的业务口径）；② 成本波动归因（依赖 ①）。

11 · 权限与审计共享模块 rls / fieldAccess / auditLog · 接口 protected-data · 页面 Settings

12 · 智能与自动化接口 ai / chatbi / ocr / tax-gateway
优势

机会
架构上最可能弯道超车的一域：本系统后端是 117 个接口文件、边界清晰，接工具调用的改造面远小于三家那种庞大内核。建议从「只读类工具」（查库存、查订单进度、查应收款）起步，天然安全，再逐步放开写入并强制人工确认。
改进
① 只读工具调用（中，建议第一步）；② 写入类工具 + 人工确认闸门（需先定「哪些动作允许智能体发起」的口径，需你拍板）。
13 · 移动端与离线路由 /m（渐进式网页应用）· 移动作业：入库 / 出库 / 盘点 / 质检
优势

七、待你拍板的事项

为什么这些不能替你决定：以下三项都涉及「业务上应该由谁对什么数据做什么」的口径选择。这个口径与你们的实际分工强相关，我给的是建议和代价对比，但不能替你选——选错会让一线干不了活，而这种错误的代价通常比「先不做」更高。

决策 1 · 字段级权限的「只读」清单认不认

背景：「可见 / 不可见」已在上一版落地，「只读」这一维目前完全空白——看得见但不该改的字段没有任何管控。例如库管能看到物料采购价，也能改。

建议清单（按「业务口径应该由谁维护」推出）：

模块字段建议只读的角色理由
物料采购价库管、质检、班长、物流进价是采购谈下来的结果 真缺口
物料当前库存全部业务角色（含采购员）库存只能由单据变动，手改会让账实不符且找不到是哪张单造成的 风险最高
其余（标准价、移动均价、授信额度、凭证金额等）——已被「不可见」覆盖，再配只读只是把规则写完整，不改变行为

我的建议：至少把「当前库存」这一行纳入。库存数字能被手工改写，账实就不一致。本维度的默认方向是「未登记 = 允许改」，所以不主动勾就不改变任何现有行为，风险可以压到最低。

三条路径：① 只做只读（推荐，风险低、收益占大头）｜② 只读 + 必填窄做（需逐字段核口径，中风险）｜③ 全做含创建必填（不建议，几乎必然出现「该拦的没拦、不该拦的拦了」）。

决策 2 · 「能勾但不生效」的操作权限开关怎么处置

背景：系统里有一个模块级操作权限矩阵（谁能建单、谁能删除、谁能审批），界面上可以勾选，但全项目零调用点——勾的每一个权限都不会被执行。

选项做法与代价适合什么情况
① 标注为「未启用」
我的建议		界面上明确标成未启用（或直接隐藏），等有明确需求再接。改动小诚实优先，先消除误导
② 真正接上把模块级权限接进各写入接口的判定（建单 / 删除 / 审批）。改动中到大，且要定「哪个角色能建哪种单」的口径当你确实需要限制某些角色建单 / 删除时
③ 暂时不动留在待办里，但请知道这个开关现在不生效近期无管控需求

注意：选项 ② 要拍的口径，和决策 1 的「只读」是同一类问题（哪个角色能对这个数据做什么）。如果打算接，建议和只读一起做，一次把口径定齐，避免分两次打扰业务部门。

决策 3 · 「必填」要不要做

建议：暂不做。理由是必填最危险的地方在于——它会把「历史数据缺失」变成「这张单永远存不了」。例如某张历史工单的仓库字段是空的，某天你给「仓库」配了必填，这张单从此一动就报错，而且改的是别的字段也会被一起拦下。

相比之下，「只读」出事最多是「某个字段改不了，去找管理员放开」；「必填」出事是「这张单一动就报错」，排查更绕。目前各接口已有针对性的必填校验，基本够用。

如果确实要做：建议只做「更新时不可清空」（不做创建时必填的通用化），只挑几个天然不该空的字段（已过账凭证的金额、已有库存的物料编码、已完工工单的完工数量），且只对新单据生效、历史单据不受影响。

你只需要回一句：「决策 1 选__、决策 2 选__、决策 3 选__」即可开工，不需要再解释细节。例如「1 只做库存那行、2 标注未启用、3 暂不做」。
