2V3.19.0 — 付款闸门真正接通

问题实况：闸门从未接线

V3.18.0 时这一项被记为「已修」，但复核发现那只是准备好了标记，闸门根本没接上：端点前端零调用、真实路径还带 /create 后缀（写 POST /api/three-way-match 会得到 405），付款的三个页面也从不读那个标记。

修法

采购订单+ 入库单+ 发票 → 服务端统一判定
不含税金额 + 1% 相对容差 → 超差 → 422 并拒绝写库

关键决策（四条）

  1. 判定只有一个来源。原先三套算法给出三个不同答案——后端 create.ts 用 1% 相对容差、界面 ThreeWayMatch.tsx 用金额绝对 0.01 元、OrderDetail.tsx 用数量精确相等。现在统一为「不含税金额 + 1% 相对容差」，写在 functions/_shared/threeWayMatch.ts。
  2. 四个写入点共用同一守卫。fin-payment-plans 的 POST / PUT，以及通用实体路由 finPaymentPlan 的 POST / PUT。只堵前两个等于留一条现成后门——这是本项目反复验证过的判据：绕开界面还成不成立。
  3. 闸门要精准。只有「状态改成已付款」或「已付金额增加」才算付款动作；改备注、改到期日一律不拦。闸门不精准就会被人要求关掉，那比没有更糟。
  4. 超差返 422 而不是 409。前端对 409 有一条统一覆盖文案，会把真实原因冲掉；同时被拦后绝不写库——拦而不住等于假拦截。

顺带补齐的两处缺口

  • 补上 GET /api/three-way-match：使用手册声称有 GET，实际目录里只有 create.ts。
  • 补上 /check 付款前预检，且与真闸门调用同一个函数——否则会出现「预检说能付、提交却被拦」的荒唐局面。

自造缺陷（改动过程中自己引入又修掉的）

付款额是含税口径，与不含税发票额直接相减会凭空造出 13% 差异 第一版实现里，付款额（含税）直接和不含税发票额比，结果每一笔都会显示「超差 13%」。改为同口径比较（付款额 vs 发票价税合计），但两个口径都写进返回的明细里，方便对账。

界面侧的两处静默问题

  • 财务域的失败提示传不出来。原先失败只写进 syncError，而财务域没有任何一个页面渲染这个字段，所以数据回滚了用户也看不到。新增 paymentGateError 通道，付款页直接展示拦截明细与差异。
  • OrderDetail 的 hooks 违规。它在提前 return 之后才调用 useWarehouseStore，属于 React 钩子调用顺序违规，同时修掉。

3V3.20.0 — 生产倒冲发料

问题实况：完工不扣原料

这项同样早前被记为「已修」，复核发现从未接通：

  • 完工动作实际上只做三件事：回写工单状态/数量/成本、生成成品入库单、生成成品入库台账——对原料库存零动作。
  • 唯一能扣料的通路要靠人手动点「生成领料出库」；完工不会自动触发。
  • 重复制造模块里那个已经叫 backflush 的报工，也只累加台账、不扣账。

修法

新建 functions/_shared/backflush.ts，核心逻辑四条：

  1. 多级展开：子件递归、child_product_code 子装配引用、source=phantom 虚项透传，并计入废品率。
    耗用量 = 单位用量 × 实际完工数 × (1 + 废品率)
  2. 只补差额：应耗用 − 已手工领用（读 work_order_pickings，按物料标识匹配、料号兜底）。这样「先领料再完工」与「直接完工」的总耗用一致。
  3. 不自己写库存：复用既有的出库记账模块，把「扣减、超发夹零、移动均价、出库凭证、序列号」这一整套现成能力接过来。单据真落 outbound_orders，保证有库存变动就有单据。
  4. 两个写入点都堵：单条更新与新建接口。建单即完工同样倒冲——判据还是那句「绕开界面还成不成立」，只堵更新接口等于留后门。触发收窄为「状态从非完工变为完工」那一次，避免每次改备注都重跑。

失败分类（一律不阻断完工）

结论码含义是否阻断
NO_BOM该成品没有物料清单不阻断
NO_ITEMS有清单但无明细行不阻断
NO_MATERIAL全部料号都缺主数据不阻断
NO_REMAINDER已被手工领料覆盖，属正常业务不阻断
missing_material个别料号缺主数据（逐行标记，不静默丢料）不阻断
missing_bom引用了子装配但该装配的清单不存在——最危险的静默少扣料不阻断
为什么失败也不阻断完工 倒冲是补账动作，不是完工的前置条件。如果把它做成完工门槛，现场第一反应就是要求把它关掉，那比没做更糟。所以以上情况一律返回 200 并照常完工，只把结论如实标出来。

★ 本版修出的两处真缺陷（只有真跑才发现）

缺陷一：完工响应回传的是「倒冲前」的旧快照 接口里的 updated 行是在倒冲之前取好的，倒冲写进去的「已倒冲」标记不进响应，于是前端误报「原料未倒冲」——明明扣了，界面说没扣。修法：执行过倒冲就重读一次再返回（两个写入点都修）。
缺陷二：完工状态从不上服务端（点完工没生效） completeWorkOrder 原来只改内存，刷新页面完工状态就丢了。修法：先把完工提交服务端（失败则不改内存、不生成入库单、给出可读原因），再由服务端倒冲并回传结果。顺序必须是「先落库、后改界面」，因为完工不可逆（状态机锁死完工态）。

同口径两处实现对齐

界面上的物料清单展开逻辑同步补上「虚项不领料」与「子装配引用展开」——原来会把虚项当成物料去领。现在与物料清单详情页的既有口径三处统一。

4V3.20.1 — 搜索关键词超长不再报错

故障现象

GET /api/outbound-orders?keyword=OUT-WO-BF-WO-E2E-260923061623-MAIN-0923061623
→ HTTP 500

本地跑同一个套件全绿，生产却有 2 条红。

根因

D1 把模糊搜索的模式长度上限设成了 50 SQLite 原生默认是 50000，Cloudflare D1 平台把它调小了一千倍，设为 50。关键词超过 48 字符时，拼出的匹配模式 %关键词% 就超限，数据库直接报 LIKE or GLOB pattern too complex（错误码 7500）。端点没捕获这个错误，被中间件兜底成了 500。

生产真机二分实测：48 字符通过 / 49 字符崩。

为什么这个缺陷特别值得重视

触发它的是一个再自然不过的操作——把单号复制粘贴进搜索框。本项目的单据编号普遍在 50 字符以上（倒冲生成的出库单号 53 字符）。也就是说，任何用户只要认真用一次搜索，就会撞上。

定位方法（可复用）

本地绿、生产红→ 先怀疑环境/平台差异→ 把失败请求翻译成等价 SQL
直接打生产库→ 单变量二分定阈值→ 48 过 / 49 崩

修法

新建 functions/_shared/searchKeyword.ts，两道闸门：

  • safeKeyword()——在取值处把关键词截断到 40 字符。这是主力闸门，覆盖了项目里三种不同的取值写法（含用 q 参数的变体）。
  • likePattern()——把 %${keyword}% 这种模式拼接收口。这是第二道保险，防止将来新写的端点漏改。

合计接入 23 个后端文件、64 处替换点。

两个设计取舍

为什么静默截断，而不是返回 400 报错？ 因为这个功能的高频场景就是粘贴单号。返回错误会拦住正当操作。截断后前 40 个字符已经足以区分单据，实测仍然能搜到目标——可用性优先。

为什么余量留到 40，而不是贴着 48？ 留出余量给「端点自己再包一层 %」的情况，避免刚好卡在上限。

已知未修（刻意留的） 模糊搜索里的 % 和 _ 通配符没有转义。搜索「100%」会被当成通配符处理。要修需要给 33 处 SQL 补 ESCAPE '\'。这属于精度类问题（不报错，只影响匹配范围），已列入待办，不与本次的 500 修复混在一起。

6本轮修出的真缺陷与定位方法

这一章是本报告最有长期价值的部分——把「只有真跑才能发现」的缺陷和排查套路固化下来。

缺陷清单

归属缺陷为什么静态检查抓不到
V3.20.1 关键词超长导致接口 500（D1 模糊搜索模式上限 50） 本地环境的数据库没有这个限制，本地怎么测都是绿的
V3.20.0 完工响应回传倒冲前旧快照 → 界面误报「原料未倒冲」 类型完全正确，只有比对响应内容与数据库真实状态才看得出
V3.20.0 完工状态从不上服务端 → 点完工刷新即丢 内存里的状态看起来是对的，不刷新就发现不了
V3.19.0 付款额含税 vs 发票不含税 → 每笔凭空多出 13% 差异 两个数字类型都对，错在口径
V3.19.0 财务域失败提示无人渲染 → 数据静默回滚 字段存在、赋值成功，只是没有任何页面读它
工具 端到端测试批次号只到秒 → 并行时撞车，报告「通过 0 条」 这是最危险的一类失败：既不红也不绿，等于压根没跑
最危险的一种失败：报告「通过 0 条」 并行跑三个套件时，27 和 28 都报「引导失败：公司已存在」，报告显示断言汇总：通过 0。这种情况看起来不像失败（没有红色），实际上测试压根没执行。已定下判据：只要看到「通过 0 条」，一律按「没跑」处理，先查是不是批次号撞车。根因已修（批次号加随机后缀），并写进测试脚手架的说明文档。

沉淀的两条硬规矩

㊵ D1 的模糊搜索模式长度上限是 50（生产专有，本地查不出）

  • 原生 SQLite 默认 50000，D1 调小到 50。关键词上限 = 48 字符。
  • 这类「本地绿、生产红」的问题，第一反应应该是环境/平台差异，而不是怀疑自己的代码。
  • 定位手段：把失败的请求翻译成等价 SQL 直接打生产库，一次复现；再用单变量二分（改关键词长度）定出确切阈值。

推论：凡是「生产才现形」的平台限制，都必须用真实端点往返去验，不能靠本地推断。

「功能有没有」必须再问「在哪一层拦」

这是本项目反复吃到教训的一条。判定功能是否真的生效，不能看界面有没有提示、也不能看代码里有没有这个逻辑，而要问：它在哪一层拦的？绕开界面还成不成立？付款闸门只堵专用端点不堵通用实体路由、倒冲只堵更新接口不堵新建接口——都是同一个坑。

另一个反复踩到的坑（本轮再验证一次）

仓库加密导致 git diff 显示整文件重写，是假象 项目对 functions/、src/stores/ 等目录设置了透明加密。这些目录只配了加密规则、没配对比驱动，所以 git diff 拿到的是「仓库里的密文 vs 工作区的明文」，看起来整个文件重写了。判据：只要 diff 里出现 U2FsdGVkX1… 这样的密文，就是假象，不能据此判断改动量。正确做法是回读磁盘上的原文来核对。

7门禁升级与工具修复

门禁第 ④ 步：后端端点全量真实巡检

把原先的一次性侦察脚本提升为常驻检查工具，接入一致性核对脚本作为第 ④ 步。

检查项说明
500 错误含漏引用导致的运行时错误（已被中间件包成 JSON 500）
鉴权缺失未带凭证却返回 200，或带了凭证却返回 403 的异常
入参未校验空请求体 / 缺字段却返回 200、201、500，而不是 400
错误返回不规范不是 JSON、没有 error 字段、泄露堆栈或数据库原文
两条使用注意 ① 它必须显式加 --live 才跑——因为会创建再删除线上测试数据，默认门禁必须无副作用；
② 检出任一 500 就整体失败退出，可以当阻断项用。报告固定落在 test-reports/api-sweep/latest.md。

这次正好印证了它的价值：V3.20.1 修的那个 500，正是这类只有真打端点才看得见的缺陷。

端到端测试脚手架修复

10未完成项与后续建议

未开工：字段级只读 / 必填机制（差距 19）

这是「其他剩余几个问题」里唯一还没动工的一项。调研结论如下：

环节现状
表格列配置不支持「只读 / 必填」属性
表单配置没有统一的表单配置对象，界面上有 1009 处输入框、分布在 170 个文件
后端字段白名单15 个以上端点各自手写了一份字段白名单——这是天然的抓手。当前语义是「传了就更新」，不区分角色
推荐做法（先做一步、跑通再迭代） 不要一次性改 170 个文件。建议：
第一步——在后端把「按角色过滤字段白名单」做出来（那 15 个手写白名单是现成锚点），再挑一个业务域做试点，本地跑通、部署、生产真实端点复验；
第二步——确认机制没问题后，再按域逐个铺开，每铺一个域跑一次回归。

这样风险可控，而且第一个域跑完就能看到真实效果，不用等到全部改完才知道对不对。
