2字段级权限：从「界面装饰」到「服务端真拦」

2.1 先摸清家底：这件事其实「做了很多」，但一处都没生效

开始之前我先把现状量了一遍，结果和预期相反——系统里不是没有字段权限，而是有五层家底、五个缺口，彼此抵消：

已有的家底它做了什么为什么没生效
前端 dataPermissionStore定义了「真实角色 × 9 个业务模块 × 字段」的可见性矩阵全部只作用在显示层——值仍完整躺在接口响应体里
配置界面 Platform/FieldPermissions.tsx让管理员能勾选「谁看不到什么」
组件 <SecureField>被 15 个页面用来把无权字段显示成 ***
后端 protected-data/[type].ts有真的脱敏逻辑全项目零消费方（唯一引用是它自己），业务页面从不走它
端到端用例覆盖了「界面显示 ***」验的是显示，不是「数据拿不到」

五个缺口（这才是真问题）

#缺口具体是什么
a遮蔽只在展示层 无权时字段显示 ***，值完整地留在接口响应里。打开浏览器开发者工具就能读到。
b脱敏接口是死的 + 角色词表不匹配 protected-data 零消费方，且它用的角色名是 admin / manager / staff ——manager 和 staff 在系统的 14 个真实角色里根本不存在（死档）。同一个字段，两套规则可以给出相反答案。
c业务主通道裸奔（最要命） /api/vendors、/api/customers、/api/materials 一律 SELECT * 返回全列、零脱敏。
d写入侧零管控 供应商更新接口是一张平铺的字段白名单，角色引用 0 处、只读 0 处、必填 0 处，语义是「传了就更新」。
e模块级权限是死接口 hasOperation 只有定义、全项目零调用点。配置界面里能勾的权限，没有任何地方执行。
实测确认的后果（这是本轮最要紧的发现） 一个界面上看不到「授信额度」的库管，只要打开浏览器开发者工具查一下 /api/vendors 的响应，银行账号、税号、授信额度全是明文。写入方向更是零管控——把授信额度改一下直接提交，系统照收。
也就是说：界面上的字段权限是装饰性的。

2.2 改法：三段式（读 / 写 / 建，各有各的处理）

新建 functions/_shared/fieldAccess.ts 作为唯一权威策略来源。关键设计：策略来源就是管理员在「设置 → 字段级权限」页面上配的那份（存在 app_state 里），服务端直接读它——不再自己硬编码第四份。

场景现在的行为为什么这样定
读取
列表 / 详情		 该字段整条不返回（不是返回空值），并附一个 _hiddenFields 清单说明「有字段因权限被移除」 附清单是为了避免前端把「无权查看」误判成「字段不存在」——这两件事对用户含义完全不同
修改 值确有变化时拦下：403 + 错误码 FIELD_FORBIDDEN + 具体字段名 + 中文原因，库里数据不动 判据是「值变了」而不是「字段出现了」。因为编辑页保存时通常回传完整对象（含它自己都看不到的字段原值），若「出现即拒绝」，库管改自己的联系电话都会被拦——功能直接不可用
新建 不拦你建单，但敏感字段静默剔除、不写入 新建表单往往带着默认值，拦成 403 会让无权角色永远建不了供应商。剔除后等同「他没填过」，业务能继续，越权也没发生
关键：默认值的「方向」和上一个版本相反 读取策略在读不到配置时回退到内置默认矩阵（宁可多遮不可少遮）—— 这个方向对「保密」是对的。但要注意：「只读」和「必填」维度的默认方向必须反过来（没登记就放开），否则一上线就是全员改不了字段。这一点直接决定了第 9 节的建议方案。

2.3 试点域为什么选「物料 + 供应商」

选试点域不是随便挑的，判据是行级权限范围会不会让字段权限根本没机会触发：

表行级范围含义选它的理由
materials 'all' 全员可见 主战场：字段权限在这里必被触发——库管打开物料列表就能看到成本价，这才是真实业务风险
vendor_master 'own' 只有负责人能看自己名下的行 次战场：必须改用「库管自己创建的行」才走得到字段门禁（详见 5.1，这里踩过一个坑）

2.4 两个方向的对照（防止改过头）

角色能看到标准价？能改标准价？为什么这样定
库管 warehouse_keeper否（键不返回）否（403）成本口径不归他管
采购员 buyer能能刻意不遮——采购员看不到进价就没法工作
管理员 admin能能证明 403 来自字段权限，不是「把功能写坏了」

采购员那一行是反向对照：如果只测「库管被遮住了」，无法区分「按角色精确遮蔽」和「非管理员一律遮掉」。后者会让采购业务直接瘫痪，是本改造最容易犯的错。

3搜索通配符转义：搜「100%」不再匹配一切

3.1 问题是什么

数据库的模糊搜索里有两个特殊字符：% 表示「任意长度」，_ 表示「任意单个字符」。用户并不知道这一点，于是：

你输入你以为的意思系统实际做的
100%找包含「100%」这三个字样的记录找「以 100 开头的一切」——大量无关记录
_找包含下划线的记录匹配任意单个字符 → 几乎等于没筛选
规格里的 M8×100%按规格搜这个物料搜出的是一堆不相关的

本轮的修法：进搜索模式前把 %、_、\ 三个字符加反斜杠转义，并在 SQL 里声明 ESCAPE '\'。转义后它们就是普通字符，按字面匹配。

3.2 ★ 为什么这两个动作必须成对做

两种错法都很隐蔽，且都不会报错
  • 只转义、不声明 ESCAPE → 模式里的 \% 被理解成「字面的反斜杠 + 通配符」，搜索会去找数据里根本不存在的反斜杠 → 连本来该搜到的都搜不到，而且不报任何错。「搜不到」会被当成「没这条数据」，比不改更糟。
  • 只声明、不转义 → 通配符照旧生效（＝这个缺陷根本没修）。
正因为两种错法都不报错，本版把它做成了一道自动检查（见第 6 节），只要将来有人新写搜索接口时漏了其中一半，检查会直接失败。

3.3 另一个容易漏的连锁反应：转义会让模式「变长」

上一版为了绕开数据库的「搜索模式最长 50 字符」限制，把关键词截断到 40 个字符。但转义会让模式膨胀（一个 % 变成 \%，长度翻倍）——如果只截断不复查：

40 个 % → 转义后 80 字符 → 模式 82 字符 → 反而更容易报错

所以本版按转义之后的长度重新收口一次，超限时从原始关键词上截断（不能在已经转义的串上再截，那会造成二次转义）。已用「60 个 %」实测：返回 200、且 0 条结果（证明它被当成一串字面 %）。

3.4 覆盖范围

项目数量说明
后端文件25 个含通用父子表工厂、通用实体路由、以及全部专用列表端点
SQL 模式76 处逐条补 ESCAPE '\'（一条 SQL 里常有多列 OR 匹配）
刻意不动2 个文件backupSchema.ts（'sqlite_%'）与 mailer.ts（'mail.%'）——这两个是内置固定模式，它们的 % 是故意的通配符，加了 ESCAPE 反而会改变行为

4顺带修出的两处隐患

这两处都不是本轮计划内的工作，是做前两件事时顺带发现的。

4.1 工单领料搜索：上一版的「漏网之鱼」

现象：上一版（V3.20.1）给 23 个搜索接口加了「关键词过长就截断」的保护，但这个接口没被覆盖到——粘一个超长的物料名进去，仍然会报「请求处理失败」。

根因：上一版是按参数名 keyword 去找的，而这个接口的参数名叫 materialName，于是被整条跳过。

教训：「按变量名扫描」一定会漏。本轮改成按 SQL 里出现 LIKE ? 来找，凡占位符驱动的模糊匹配一律纳入（这条也写进了门禁）。

4.2 供应商注册：可用通配符把自己注册进别人的组织

现象：供应商自助注册时，系统按「供应商代码前 3 位」去匹配所属公司的公司码。而这段代码是注册人自己填的，且拼进查询时没有转义。

后果：只要填一个以 % 开头的代码，前 3 位就成了通配符，可以匹配到任意公司的公司码 → 供应商把自己注册进不属于自己的组织。这是一条越权路径。

修法：用户输入的片段先转义，前缀通配符由系统自己加（likePrefix()），并配 ESCAPE。

5★ 修出的真缺陷与定位方法

5.1 我的测试本身先出了缺陷：一类「空跑假绿」

字段权限套件第一次跑，7 条红。但排查后发现根因不在被测代码，而在测试设计——而这个过程中暴露了一类比红字更危险的东西。

现象：7 条红 + 一批「看起来通过但其实没跑」的绿

红的原因：套件用超管建了一条锚点供应商，然后让库管去读它。但供应商的行级权限是「只有负责人能看自己名下的行」——库管的读被行级权限先拦住了（列表 total=0、详情 403「无权限查看他人供应商」），根本没走到字段门禁那一步。

更危险的地方：「库管看不到授信额度」这几条断言显示为绿色——因为它们写在 if (行存在) { … } 里面，行不存在时整块没执行，却也不记失败。这种绿比红还坏：红字会有人去查，假绿不会，而且它会让人得出「这个能力已经验证过了」的错误结论。

修法（两层）

层次做法
换对战场主战场改到物料域（行级范围是「全员可见」，字段权限必被触发）；供应商域改用「库管自己创建的行」（负责人是自己，行级放行，才走得到字段门禁）
堵住假绿每处锚点前加一条显式锚点断言：取不到被测行时直接记失败，并打印「该组断言未执行（这是失败，不是通过）」，然后终止。绝不静默跳过
这条已经写进项目硬规矩（㊸） 规则原文的意思：测试的锚点缺失＝失败，绝不是通过。而且选锚点行之前要先确认行级权限范围——范围为「按负责人」的表，用管理员建的行无权角色根本读不到，「字段级权限有没有生效」这件事其实从未被验证。这与项目里另一条既有判据是同构的：「在哪一层拦、绕开界面还成不成立」。

5.2 本轮沉淀的定位套路（可复用）

  1. 先证伪自己的假设。本轮排查「为什么只有生产红」时，先后提出并推翻了两个假设（生产库缺列 → 直查表结构证明 31 列齐全；权限分支问题 → 用两种身份分别实测都是 200），才找到真因。
  2. 把失败的请求翻译成等价的 SQL 直打生产库，一次复现真实错误，再二分变量定阈值。这比在应用层猜快得多。
  3. 对「看起来通过」的断言保持警惕。本轮 7 条红背后那批假绿，是比红字更大的收获。

6门禁升级（现六步）

本轮的教训是「两处必须对齐的约定，靠人记一定会漏」。所以新增两步机器核对，并接入统一门禁链：

步检查项它防的是什么阻断
①登记表 ↔ 生产库平台配置里登记的清单与真实数据库不一致（僵尸登记 / 漏登记）是
②前端调用 ↔ 后端路由前端调了一个不存在的接口（上线才 404）是
③生产端点存在性探针端点是否真的在线--strict
④后端端点全量真实巡检500 / 鉴权缺失 / 入参不校验 / 错误返回不规范是（需 --live）
⑤LIKE 转义一致性 新增 凡 LIKE ? 必带 ESCAPE。判据刻意不含「所有 LIKE」——内置固定模式（'sqlite_%'）不应加 ESCAPE，加了反而改变行为。脚本内建 反例自证（4 个用例），证明检查逻辑本身没被改松 是
⑥字段权限矩阵一致性 新增 前端存储与后端兜底两份默认矩阵逐条三元组核对（67 条 角色|模块|字段），防「同一口径两处实现走偏」 是

本轮最有价值的两条生产证据

① 「搜 100% 能搜到含字面 100% 的记录」这条断言，是专门用来证明ESCAPE 真的声明了的。因为「转义但不声明」的错误会导致「搜什么都搜不到」——如果只测「搜不到 100X 的」，那种错误反而会让测试变绿。两条断言缺一不可。
