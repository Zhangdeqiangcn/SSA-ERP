一、审计结论（先看这里）

一句话结论：SSA ERP 的 "货"（存货 / 成本）这条财务线已经基本打通——采购收货、生产领料完工、销售发货出库、仓库盘点，都能自动生成存货类凭证。 但 "钱"（往来 + 收入 + 收付款）这条财务主干完全没接上：应付账款、应收账款、主营业务收入、银行存款这四个核心科目，在整个后端代码里从没有任何一张业务单据去写它。 结果就是：总账里只有"货从哪来、货到哪去"，没有"钱欠谁、钱收谁、钱花哪了"。 此外还有两处记错科目的缺陷：库存调拨被错记成销售成本、生产成本只含材料没含工费折旧。

报告里几个会计词，用大白话解释一下：
· 应收（1122）= 应收账款：货卖出去了、票开了，客户还没付的钱 → 别人欠我的。
· 应付（2202）= 应付账款：货买了、票收了，我还没付供应商的钱 → 我欠别人的。
· 暂估（2201）= 物资采购（GR/IR）：货到了、发票还没到，先按估计金额记一笔"欠供应商的"，等发票来了再冲掉、换成正式的应付。
· 结转成本（6401/1405）：卖出去的货，它的进货成本从"库存"搬到"成本"。
· 收入（6001）= 主营业务收入：卖货该确认的收入。
· 生产成本（5001）：生产一件产品花掉的 材料 + 人工 + 制造费用（含设备折旧）。
· 折旧（1602）= 累计折旧：设备用旧了，价值逐月减少，对应一笔费用。

二、审计方法

本次审计不依赖旧报告结论，而是直接核对当前代码。重点查了这些"联动心脏"文件与端点：

  • functions/_shared/inventoryPosting.ts —— 库存过账 + 自动业务凭证生成的总闸（入库/出库/调拨/盘点都走这）。
  • functions/_shared/backflush.ts —— 生产完工倒冲发料（领料扣账）。
  • functions/_shared/voucherWriter.ts —— 所有凭证的唯一写入通道，含借贷平衡校验。
  • functions/_shared/threeWayMatch.ts / threeWayLineMatch.ts —— 采购三单匹配（订单/收货/发票）。
  • 端点：fin-invoices（发票）、fin-payment-plans（付款计划）、shipments（发货）、stock-transfers（调拨）、inventory-adjustments（盘点）、fixed-assets/depreciate（折旧）、finance/closing-periods（结账）。
  • 全局检索 1122 / 2202 / 6001 / 主营业务收入 / 应收账款 / 应付账款 / 应收 / 应付 在 functions/ 中的写入情况。

五、缺陷详单（按严重度）

P0-1 采购发票不冲暂估、不确认应付（2202 永不入账）

现象：供应商发票端点 fin-invoices 的 POST 只把发票头+明细落库（pcCreate），完全不写凭证。系统已经做了"收货暂估（贷2201）"，但发票来了之后应该"冲掉暂估、确认正式应付（贷2202）"这一步从未实现。

后果：① 暂估科目 2201 会越积越大、永远结不平；② 应付账款 2202 永远是 0，等于公司"从不欠供应商钱"的假象；③ 发票与应付脱节，无法做账龄分析、无法对账。

证据：fin-invoices/index.ts:23-54（仅 pcCreate，无 writeVoucher）；finConfig.ts:64-115（发票配置有 invoice_type 进/销方向，但无记账逻辑）。

正确做法：采购发票过账应生成 借2201暂估 / 贷2202应付账款（如含税还需拆进项税 2221）。

P0-2 付款不记账（不记银行存款 1002、不冲应付/暂估）

现象：付款计划端点 fin-payment-plans/[id].ts 的 PUT 在"付款动作"时只累加 paid_amount、改 status=paid，不生成任何凭证。虽经三单匹配闸门（拦风险），但闸门只管"能不能付"，付完之后钱从哪出、欠谁的账消没消，财务侧一无所知。

后果：银行存款 1002 不动、应付 2202/暂估 2201 不冲减 → 付款越付，账面"欠供应商的钱"还是那么多，现金却没少，资金账完全失真。

证据：fin-payment-plans/[id].ts:28-52（guardPaymentRow 只判闸门，随后 pcUpdate 仅改状态/金额）；paymentGate.ts 无 writeVoucher。

正确做法：付款过账应生成 借2202应付账款 / 贷1002银行存款。

P0-3 销售无收入确认、无应收（6001 / 1122 缺失）

现象：销售侧只做到"发货→出库结转成本（借6401/贷1405）"，但收入（6001）和应收（1122）在整个后端零写入（全局检索 6001 / 1122 / 主营业务收入 / 应收账款 在 functions/ 中无任何业务单据落账）。即便录入了销售发票（fin-invoices 支持 invoice_type 销售方向），也不会确认收入与应收。

后果：① 卖了货只在账上记了"成本"，没记"收入" → 总账层面越卖越亏，毛利虚亏；② 应收账款 1122 永远为 0 → 公司"从没有人欠我钱"的假象，无法做应收账龄、无法催款；③ 前端毛利报表若基于订单金额估算，与总账口径不一致，两份数对不上。

证据：shipments/[id].ts:115（仅 postOutbound 结转成本）；fin-invoices/index.ts（销售发票也不记账）；全局 grep 零命中写入。

正确做法：销售开票应生成 借1122应收账款 / 贷6001主营业务收入（及 贷2221应交增值税-销项）；收款时 借1002 / 贷1122。

P0-4 根因：应收 / 应付 / 收入 台账为空（主干断裂）

现象：系统没有 accounts_receivable / accounts_payable 实体表，所有往来都依赖从 vouchers 凭证按科目派生。由于 P0-1~P0-3，没有任何业务单据产生 1122/2202/6001 凭证，所以往来与收入台账实质为空。

后果：这是 P0-1~P0-3 的共同根因——业务单据与财务总账之间"往来+收入"这条主干完全没有自动记账通道。采购、销售两条业务线都变成了"只动货、不动钱"。

证据：全局检索 1122|2202|6001|主营业务收入|应收账款|应付账款 在 functions/ 仅出现在注释/只读（合并报表抵消、ChatBI 应收账龄、三单匹配文案），无任何 writeVoucher 调用。

P1-1 库存调拨被错记成"销售成本"（6401/1405）

现象：stock-transfers/[id].ts 调拨时调 postOutbound({type:'transfer'}) 做调出仓扣减，但 generateOutboundVouchers 里没有 transfer 分支，会掉进 else 被当成销售出库，错误生成 借6401主营业务成本 / 贷1405库存商品。而调入侧的 type:'transfer' 在 generateInboundVouchers 正确 return（不生成凭证）。

后果：调拨只是"货在公司内部从 A 仓搬到 B 仓"，经济上没有销售、不该产生成本。现在每次调拨都会凭空在总账上：库存（1405）被贷记减少、成本（6401）被借记虚增 → 成本虚高、库存账虚低。仓库越多、调拨越频繁，偏差越大。

证据：stock-transfers/[id].ts:157,169（传 type:'transfer'）；inventoryPosting.ts:645-682（出库凭证函数无 transfer 分支，else 兜底记 6401/1405）；inventoryPosting.ts:615-616（入库侧 transfer 正确 return）。

修复建议：在 generateOutboundVouchers 增加 order.type === 'transfer' 分支——调拨出库不生成损益类凭证（库存价值已由 postInbound 的 costPriceOverride 按调出仓成本结转保留，无需进 6401）。

P1-2 生产成本只含材料，缺人工 / 制造费用 / 折旧归集（5001 不完整）

现象：生产成本（5001）目前只能从"生产领料"进来（借5001/贷1403）。系统里没有任何"人工工资、制造费用、设备折旧归集进 5001"的通路。完工入库（贷5001）时，5001 里只有材料成本，没有工费。

后果：完工产品的成本被低估 → 后续销售出库结转的 COGS（6401）偏低 → 毛利虚高；真实的人工与制造费用没有归宿，要么进了费用（见 P1-3 折旧），要么干脆没记账。

证据：inventoryPosting.ts:671-673（仅领料进 5001）；全仓无"工资/制造费用→5001"的写入代码；backflush.ts 只算材料。

修复建议：建立"工费归集"通道（借5001生产成本-直接人工/制造费用 / 贷应付职工薪酬、累计折旧等），月末将制造费用分摊进 5001，使完工成本完整。

P1-3 固定资产折旧全进"管理费用"，不进生产成本

现象：折旧计提端点 fixed-assets/depreciate.ts 一律生成 借6602管理费用 / 贷1602累计折旧，不论资产是生产用还是管理用。制造型企业生产设备折旧应归集到制造费用/生产成本，而非直接费用化。

后果：与生产 P1-2 同源——生产设备的折旧没有进 5001，进一步加剧完工成本低估；且所有折旧一刀切进管理费用，费用结构失真。

证据：fixed-assets/depreciate.ts:205-206（固定 借6602/贷1602，无按资产用途分流）。

修复建议：按资产"使用部门/用途"区分：生产用设备折旧 借5101制造费用（再分摊进 5001）；管理用 借6602。可加资产字段 cost_center 或 depreciation_account 控制。

P2-1 自动业务凭证均为 draft，无系统自动过账机制

现象：库存过账自动生成的凭证（采购暂估、出库成本、生产、调拨等） status 一律写 draft（见 inventoryPosting.ts:629,700）；唯独盘点凭证直接写 posted（inventory-adjustments/[id].ts:201）。两套状态不一致。系统没有"自动把业务凭证过账"的环节，依赖人工在凭证界面逐张过账。

后果：若业务凭证长期停在 draft 未过账，即便记账逻辑正确，总账也收不到这些分录（试算平衡、结账、合并报表都基于已过账凭证）。盘点凭证却自动 posted —— 同一系统两种口径，易乱。

证据：inventoryPosting.ts:629,700 vs inventory-adjustments/[id].ts:201。

修复建议：统一策略——业务联动凭证要么自动 posted（推荐，减少人工漏过账），要么全部 draft 并加"批量过账/结账自动收口"机制；禁止两套并存。

P2-2 无"库存账面价值 ↔ 总账"对账作业

现象：结账端点 finance/closing-periods 只查试算平衡、跨期凭证、折旧是否计提，没有把 inventory_records/materials.stock_value 的存货价值与总账 1403/1405 余额做勾稽。

后果：一旦库存过账与凭证任一侧出错（如 P1-1 调拨错记、或凭证 draft 未过账），存货实物账与财务账偏离却无任何预警，月底才发现对不上，排查困难。

证据：finance/closing-periods/index.ts:81-97（仅折旧/凭证检查）；结合 inventory_transactions 流水已存在（可对账底座）。

修复建议：结账时增加"存货余额（按物料汇总 stock_value）vs 总账 1403/1405 已记账发生额"的差异校验，超阈值告警。

P2-3 "凭证已生成"标记位形同虚设（voucher_generated）

现象：发票表（fin_invoices）和付款计划表（fin_payment_plans）都定义了 voucher_generated 字段（见 finConfig.ts:47,110、entities.ts:84,103），但全代码无任何地方把它置 1。即便将来修了 P0 让发票/付款生成凭证，也无法从单据上反查"这张发票的财务凭证是否已出"。

后果：业务与财务之间缺少"已联动/未联动"的可视化标记，审计、对账、防重复记账都失去抓手。

证据：grep voucher_generated|voucherGenerated 在 functions/ 仅出现在配置/字段定义，无写入点。

修复建议：在发票/付款生成凭证处回填 voucher_generated=1 与 voucher_no，前端据此显示"已入账/未入账"徽标。

P2-4 三单匹配只做"付款闸门"，未串联"发票→应付→付款"记账链

现象：threeWayMatch.ts 的匹配逻辑本身很完善（金额+行级数量、容差、欠货拦截），但它纯只读、不写账。发票录入、匹配判定、付款执行三件事各干各的，没有把"发票确认应付""付款冲应付"串成自动记账链。

后果：有了好闸门却没接后端记账，导致 P0-1/P0-2。匹配数据（应付金额已算出）其实可以直接驱动应付凭证，目前白白浪费。

证据：threeWayMatch.ts:118-119（注释明确"只读，不写库"）；recordThreeWayMatch 仅留档。

修复建议：修复 P0 时，让发票过账与付款过账在匹配通过的前提下自动触发，把闸门结论直接变成记账动作。
