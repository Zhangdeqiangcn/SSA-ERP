审计纪律（遵守项目铁律）：

  • 每条结论均以文件路径:行号为证据，不采信任何历史审计报告的旧结论（旧结论会过期，必须回代码复核）。

  • 系统性结论用代码取证 + 生产/仓库真实表清单 + 端点引用链三重坐实，不靠单路判断。
范围说明：你本次列的七模块未含「仓库」，但仓库是采购/生产/销售的出入库执行方。本轮仓库作为被动被联动方在相关配对（采购×仓库、生产×仓库、销售×仓库）中顺带核查——这三对在五模块审计（V3.61）已修复并验证，本轮复查确认仍正确，详见第八章。

二、结论速览

✅ 主干业务已真正打通：采购收货暂估、生产领料与完工、销售出库成本、发票/付款/收款的财务联动、结账守卫、行级三单匹配——这些主干链路的服务端算账、原子批次、幂等抢占在 V3.60–V3.62 已正确实现，并经生产端到端回归（45 套件 PASS 1586 / FAIL 0）验证。
⚠️ 但存在两个系统性孤岛，是本轮最重大发现：
  1. 质量模块数据孤岛（P0）：质量的核心业务单据（检验批、检验任务、不合格品、质量成本、供应商质量反馈、八D、PDCA、SPC、实验室设备、检验标准）完全没有后端持久化，仅以浏览器本地存储 + 模拟数据驱动；连唯一有后端的「质量冻结（quality_holds）」也不被任何下游端点消费，冻结形同虚设。质量结果与采购收货、生产完工、销售退货、财务质量成本、供应商绩效系统性断裂。
  2. 系统设置配置孤岛（P0）：凭证模板、打印模板、系统配置完全不被业务端点消费；审批流、单位换算、数据权限、编号规则消费面极窄。系统设置模块的配置项大量「建了但不生效」，形成配置孤岛。

五、P0 严重系统性缺陷（2 项）

P0-质量-1　质量模块核心单据零后端，与六模块系统性断裂

问题：质量模块页面丰富（检验批、检验任务、不合格品、质量成本、供应商质量反馈、八D、PDCA、SPC、实验室设备、检验标准、质量冻结），但其核心业务单据完全没有后端持久化——仅以浏览器本地存储 + 模拟数据驱动，与采购、生产、销售、财务、系统设置、供应商平台六大模块无任何真实单据联动。

证据链：

① 真实表清单 migrations/*.sql 去重后，质量相关表仅 quality_holds 一张。 ② 前端存储范式 src/stores/qualityStore.ts:2-3 import { persist } from 'zustand/middleware'; import { backendStorage } :5 import type { VendorQualityIssue } from '@/mocks/data/flowData'（直接引用模拟数据） grep 'api.|axios|fetch(' 于 qualityStore.ts → 无任何后端调用（No matches） ③ 通用实体路由 functions/_shared/entities.ts:32 ENTITY_RESOURCES 注册表仅含财务域切片 （finInvoice/finInvoiceItem/finPaymentPlan/finAccountEntry/finTaxRecord/finProjectAccount/copa/op 等），无质量资源。 ④ 类型与表脱节 src/types/quality.ts 定义 InspectionTask/UnqualifiedItem/COQRecord/QmVendorFeedback/... 等十余实体； src/types/supplyChain.ts 另定义 InspectionLot/QualityHold/COQRecord/QmVendorFeedback —— 均无对应真实表。

联动影响（6 组配对全断）：

  • 质量×采购：来料检验不合格 → 应触发不合格品处置 + 采购退货 + 供应商质量反馈；实际检验无后端、冻结不阻入库（见 P0-质量-2），退货无独立单据，供应商反馈无后端 → 断裂。
  • 质量×生产：过程检/终检不合格 → 应返工/报废并计入生产成本；实际检验无后端、完工入库不校验检验结果 → 断裂。
  • 质量×销售：客诉/退货 → 应质量分析（不合格品）+ 质量索赔；实际不合格品无后端、退货靠前端红字入库单（见 P1-VP-2） → 断裂。
  • 质量×财务：不合格品损失/返工成本/质量成本（COQ）→ 应生成财务凭证；实际 COQRecord 无后端 → 断裂。
  • 质量×系统设置：检验标准（AQL 抽样、数据字典）应驱动检验；实际 InspectionStandard 无后端 → 断裂。
  • 质量×供应商平台：来料合格率/质量反馈应更新供应商绩效；实际 QmVendorFeedback 与 VendorPerformance 均零后端 → 断裂。

修复方向：为检验批/任务/不合格品/质量成本/供应商质量反馈建立真实表 + 端点 + 与上下游的写回链路（来料检→冻结+退货、过程检→返工/报废成本、质量损失→财务凭证、质量反馈→供应商绩效）。属重大工程，需立项。

P0-ST-1　系统设置模块配置孤岛（建了但不被业务消费）

问题：系统设置模块的多个配置项已建后端表，但业务端点基本不消费，配置形同虚设，无法真正驱动/约束业务单据。这是「配置不联动」的系统性根因。

① 凭证模板 voucher_templates grep 'voucher_template' functions/api → 仅 voucher-templates/{index,[id]}.ts 自身； 无任何业务端点（采购/销售/生产/财务自动凭证）消费。自动凭证走 voucherWriter.ts/arapPosting.ts 硬编码科目。 ② 打印模板 print_templates grep 'print_template' functions/api → 仅 print-templates/{index,[id]}.ts 自身； 发货单/发票/采购单打印均不读此表。 ③ 系统配置 system_config / org_settings grep 'system_config|org_settings' functions/api → 仅 system/mail-config.ts、system/notify.ts； 业务单据不读税率默认/币种默认/会计政策等。 ④ 审批流 approval grep 'approval' functions/api → 仅 purchase-requests/[id].ts、vendor-quotes/index.ts、approval-* 自身； 采购订单/销售订单/工单/入库/发票等提交均不自动触发审批。 ⑤ 单位换算 unit_conversions grep 'unit_conversion' functions/api → 仅 materials/*、system/migrate-materials、unit-conversions 自身； 出入库/生产/销售业务端点不调用单位换算。 ⑥ 数据权限/字段权限 grep 'dataPermission|fieldPermission' functions/api → 仅 customers/[id]、materials/[id]、vendors/[id]； 列表查询与其他模块未覆盖。 ⑦ 编号规则 numbering 后端仅 approval-instances/[id].ts 引用；前端 useNumberingStore.nextNo() 被部分页面消费， 但 RepetitiveMfgList.tsx:18 注释明示「本模块编号未纳入统一编号规则，按本地生成」——纳管不全。

影响配对：财务×系统设置（凭证模板/打印模板/系统配置不生效 → 红）；采购/销售/生产/财务/质量×系统设置（审批/单位换算/数据权限/编号消费不全 → 黄）。

修复方向：让自动凭证读取凭证模板、业务打印读取打印模板、单据提交按审批流配置触发、业务数量按单位换算表转换、列表与详情统一应用数据权限、编号规则纳管全部单据类型。属系统性配置引擎补齐，需立项。
