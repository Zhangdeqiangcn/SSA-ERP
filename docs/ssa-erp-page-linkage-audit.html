3. P0 错位 —— 数据地基断裂（最优先）

🔴 仓库↔质量：检验批台账与冻结拦截「不同源」
服务端 checkQualityBlocked 拦截出库时读 D1 的 quality_holds / unqualified_items（关系化，已坐实）。 但检验批台账 inspectionLots 仍 Blob 化（qualityAdvancedStore 的 persist(backendStorage)，无 entityRepo/api/fetch 通道）。 后果：质检员在「检验批」页判定不合格，台账改了本地 Blob， 而服务端拦截读的是另一张 D1 表 —— 两边数据同源风险高， 可能出现「台账显示已闭环、拦截仍拦」或反之的错位。
定位：qualityAdvancedStore.inspectionLots 关系化到 inspection_lots 表（0090 已建该表、已登记 entities/rls，只差 store 接入）。
🔴 系统设置：编号规则 / 订单模板 / 数据字典 Blob 化，服务端不消费
系统设置页（NumberingTab / OrderTemplateTab / DataDictTab）读写的 numberingStore / orderTemplateStore / dataDictStore 均无 D1 通道（纯 Blob）。但服务端各单据端点建单时若按「编号规则/订单模板」 取号/取字段，实际读不到这些配置（配置只活在浏览器 Blob 里，D1 侧无表）。 多终端/重新部署后配置会漂移，编号可能撞号。
定位：三张表（numbering_rules / order_templates / data_dict）建 D1 + entities/rls 登记 + store 关系化，服务端建单端点改读 D1 侧配置。
🔴 供应商平台↔生产：生产投诉 → 供应商追责无回流链路
供应商门户有 addVendorQualityIssue + portalIssueId 消费面 （质量反馈→门户已通），但生产侧投诉（生产报告页 ProductionReport） 没有对应「投诉推供应商门户」的动作。供应商平台只承接来料质检反馈， 生产投诉追责供应商这条链是断的。
定位：ProductionReport 增加投诉入口，经 qualityStore.addVendorQualityIssue （issueType='production'）推门户，或独立建 production_issue→供应商链路。
🔴 销售↔供应商：客户退货追责未直连供应商门户
销售退货质量回流走的是「建客户侧 NCR」（qualityStore）， 但没直接推给供应商平台门户做追责协同。追责链要人工在供应商页补 issue。
定位：salesReturnStore.completeReturn 质量原因退货时， 同步 addVendorQualityIssue(issueType='customer_return')。
🔴 财务↔仓库：批次/库位仍 Blob 内联，成本回写口径不完整
inventory_records 已关系化（有 dept_id、可用量、冻结量）， 但批次台账（batch）前端派生、库位 JSON 内联在单据里，无独立 batch_records 表。批次级成本/库位级对账走不动， 财务「批次成本 ↔ 库存」只能按物料粒度近似。
定位：建 batch_records 表（批次号+物料+数量+成本+库位）， 出库/完工按批次回写成本，财务对账口径细化到批次。

4. P1 不流畅 / 不稳定 —— 体验与一致性风险

🟡 生产排程 Blob 化（productionSchedulingStore 无 D1）
CRP / GanttSchedule / FiniteCapacity 等排程页排产结果只在 Blob， 工单/报工跨终端看不到同一版排程，多用户排产互不可见（不稳定）。
🟡 返利 / 销售合同 Blob 化（rebateStore / salesContractStore 无 D1）
RebateManager / SalesContractList 的返利与合同数据纯 Blob， 财务对返利计提、合同履约跟踪无法按行引用（错位）。
🟡 跨 store 联动多为「即时读 getState」而非订阅
扫描显示仅 warehouseStore 被 subscribe（质量/仓库高级）， 其余（purchaseReturn/salesReturn/production 等）跨模块取数多是 getState() 即时快照。并发编辑下存在读到旧值窗口（不流畅/不稳定）。 建议关键联动（退货信用、完工成本）改用事件驱动或读服务端权威值。
🟡 服务端 MRP 触发已建，但 MRP 计划订单「转正式单」仍是手动
V3.65 立项② 已让销售订单自动算缺口落计划订单（建议）， 但「计划订单 → 采购申请/工单」的转换仍需在 MRP 页面手动点。 属刻意保留的人工闸门（建议非命令，对标 SAP），非缺陷， 但需在报告标注为「半自动」而非全自动。
🟡 生产投诉 / 客户退货 双入口未统一到供应商门户 issue 模型
见 §3 P0 两条。统一后供应商门户 issue 才有完整来源（来料/生产/客户退货三类）。
🟡 系统设置配置面「建了不消费」的残余
条件技术(ConditionTab) / 单位换算 / 打印模板部分仍有 「配置存在但业务未读取」的尾巴（V3.64 已修凭证模板/检验标准， 条件/单位/打印未全量接消费面）。需逐项确认消费点，避免配置形同虚设。
🟡 仓库高级「乐观写 + 服务端同步失败只 toast」不阻断
warehouseAdvancedStore.addQualityHold 等是 set 本地 → .create().catch(toast)。网络失败时本地先变了、 服务端没同步成功，用户可能以为已保存（不稳定）。建议失败时回滚本地或明确标脏。

5. 六类诊断归因 + 修复优先级路线图

诊断类发现代表位置
遗漏生产投诉/客户退货 → 供应商门户追责链路缺失ProductionReport、salesReturnStore
错位检验批台账(Blob) 与 冻结拦截(D1) 不同源qualityAdvancedStore.inspectionLots vs checkQualityBlocked
错位编号/模板/字典配置 Blob，服务端建单读不到Numbering/OrderTemplate/DataDict Tab
不合理批次/库位无独立表，财务成本只能按物料近似库存批次/库位内联单据 JSON
不稳定跨 store 即时 getState 读旧值；乐观写失败只 toast 不回滚purchaseReturn/salesReturn、warehouseAdvanced
不流畅MRP 自动算缺口但转正式单仍手动；多终端排程/合同/返利不可见MRPPlan、排程/返利/合同页
修复优先级路线图（先地基后体验）： ① P0 数据地基（检验批关系化 / 编号·模板·字典 D1 化 / 批次表 / 投诉回流 / 客户退货追责）—— 影响账实一致与多端协同； ② P1 稳定与体验（即时读改事件驱动 / 乐观写失败回滚 / 排程·合同·返利关系化 / 配置消费面收尾）； ③ 每步 npm run check -- --no-probe 门禁 + 生产 E2E 回归，避免回归。
本轮坐实「已正确实现、无需动」的连线（20 对 ✅）： 销售退货→采购追责(0093)、销售订单→自动MRP(V3.65②)、发货→出库幂等、 采购收货→入库回写、采购→来料检事件驱动、采购交期→供应商绩效、 付款→协议价核验(V3.65④)、框架协议→审批(V3.65①)、 完工→成本结转含人工、质量→检验标准配置引擎(V3.65③)、 质量反馈→供应商扣分、盘盈亏→存货凭证+结账守卫、多仓指定 等。 这些是前面几轮真 bug 换来的闭环，不建议回改。
诚实边界：本报告基于 217 页面 / 88 store / 131 路由实读， 数据流方向靠代码 import/订阅关系坐实；「并发读旧值窗口」「多终端不可见」 类结论为静态推断（未做并发压测），已在对应条目标注「需运行验证」。 未逐一打开 217 页做像素级走查，按「落库通道 + 跨模块订阅」两条主线索定位错位， 个别装饰/报表页（COPA/ESG/BI/资金）仅确认存储层已关系化、未深究其业务消费面。

6. V3.66.0 修复落地状态（逐项坐实前提后动手）

审计项结果落地说明
P0-1 检验批台账 vs 拦截不同源✅ 已修 坐实修正：报告误标「0090 已建 inspection_lots」，该表实际不存在。迁移 0095 新建；qualityAdvancedStore 检验批改 entityRepo 主源 + 启动水合（judgeLot/自动建批均同步 D1），与服务端 checkQualityBlocked 读源真正同源。
P0-2 编号/模板/字典 Blob 化✅ 已修 0095 建 numbering_rules/order_templates/data_dict；numberingStore 序号自增同步 D1（多终端不再漂移撞号），模板/字典关系化。诚实边界：服务端建单端点消费 nextNo 取号留后续立项（避免一次改 9+ 端点）。
P0-3 生产投诉追责链缺失✅ 已修 报工弹窗加「责任供应商」（可选，不选不误伤正常报废）；报废选了供应商则双写：供应商门户 issue（production 类型）+ 质量 NCR（production_complaint 来源，带供应商归属落 0095 新列）+ 供应商绩效自动扣分。
P0-4 客户退货追责未直连门户✅ 已修 质量原因退货按物料溯源「最近采购订单供应商」（销售订单行无供应商字段，走真实溯源路径；无采购记录只建 NCR 不造假）→ 门户 issue（customer_return）+ NCR 带供应商归属 + 绩效扣分。
P0-5 批次/成本口径不完整✅ 已修(入库口径) 0095 建 batch_records（含 cost 列）；入库过账自动快照批次成本（单价×数量累加）；批次台账 CRUD 同步 D1 + 水合。诚实残余：出库/完工按批次结转成本未接（目前批次成本只含入库快照）。
P1-1 排程 Blob 化✅ 已修 0096 建 scheduling_locks；排程锁 toggle/锚定/清除全同步 D1 + 启动水合（多用户排产互不可见 → 共享真源）。
P1-2 返利/合同 Blob 化✅ 已修 0096 建 rebate_rules/rebate_settlements/sales_contracts；返利/合同 store 关系化（合同明细/付款计划/附件封 extra_json），财务可按行引用。
P1-3 并发读旧值窗口✅ 已修(真修) 新增服务端相对原子端点 POST /api/vendors/:id/credit-delta（数据库内 used_credit += delta，超限 409 拒绝）；信用联动保持同步本地语义（6 处调用方零改），在线走原子端点 + 回读权威值，失败回滚本地。根治「读旧值→算→整字段写」丢更新竞态。
P1-4 MRP 转正式单手动⚪ 坐实不改 刻意保留的人工闸门（建议非命令，对标 SAP MRP 设计），非缺陷，标注即可。
