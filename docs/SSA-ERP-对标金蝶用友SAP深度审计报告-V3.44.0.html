一、结论先行：最该立刻修的 12 个硬伤

这 12 条不是"最严重"的排名，而是「会导致数字算错、且用户完全不知情」的集合——即最违背 ERP 信任前提的问题。每条我都标注了确切的断链位置。

1

预算闸门P0数据准确性+业务使用超预算永不触发（闸门造好了没接线）

断链处functions/_shared/voucherWriter.ts:114 把凭证行的 project_id、cost_center_id 硬编码为 null，币种/汇率硬编码 'CNY', 1。

后果paymentGate.ts:179 的 SUM(debit) WHERE project_id = ? 恒匹配 0 行 → 实际发生额恒为 0 → 单笔付款不超预算就放行。V3.29.0 声称的"预算硬拦+安全阀"实际从未生效，用户却以为有管控（假管控比没管控更危险）。

修复成本极低（两处 INSERT 补字段，前端 toVoucherPayload 已在传值），但必须补守护测试防回归。

2

凭证行维度丢失 → 报表金额按科目名匹配后静默消失P0数据准确性

断链处写侧 voucherWriter.ts:110-115 写死币种/汇率/项目/成本中心；存侧 functions/api/vouchers/[id].ts:110 的 PUT 连这几列都不写（先 DELETE 再全量 INSERT，任何编辑都清空）；读侧 src/utils/financialStatements.ts:83-84,104-105 用科目名称字符串匹配科目表。

后果链科目一改名 → 历史分录匹配不到 → 资产负债表/利润表/现金流量表同时少这笔钱且不报错。SAP 的科目编号是唯一核算维度，改名只影响显示。

对标SAP SKT0 主数据 + 凭证行存科目号；金蝶/用友同理强制记科目编码。

3

入库单金额恒为 0 → 三单匹配形同虚设、付款闸门 100% 拦截正常采购付款P0两者

断链处functions/api/inbound-orders/index.ts:124 写 Number(item.amount) || 0，而前端 src/pages/Warehouse/InboundForm.tsx:112-134 建单只传数量、根本不传单价与金额；三单匹配 threeWayMatch.ts:191 按 SUM(i.amount) 算入库金额。

修复三处小改：表单带出单价、SQL 改 SUM(actual_quantity * unit_price)、服务端补 UPDATE。

对标SAP 分录行过账后受凭证头锁定，只能整体冲销；金蝶/用友无此接口语义。

S5 · 「无流水台账」：只存余额快照，差异不可追溯

本轮最深的结构性发现：inventory_records 是当前余额快照，每次过账只做 quantity = quantity + ? 原地累加（inventoryPosting.ts:106），没有库存变动流水表（迁移全目录确认）。同样地，rep_mfg_periods.backflush_items 与 subcontract_orders.receipt_inbound_nos 用 TEXT JSON 存数组（catch { return [] } 静默吞脏数据）。
