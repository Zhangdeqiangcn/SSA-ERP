2. P0 缺陷（数据一致性 / 死锁 / 账务缺口，5 项）

P0-1 · 质量 ↔ 仓库：检验批与检验任务两套数据源，冻结解除可能死锁 需运行验证 实读坐实：质量侧并存两条链路——① qualityStore 走关系表 inspection_tasks（判定 failed）；② qualityAdvancedStore.autoCreateLotsFromInbound 写 inspectionLots（仍为 Blob 持久化，未关系化）并派生 quality_holds。 而仓库 checkQualityBlocked 拦截的是 quality_holds（冻结）+ inspection_tasks 的 failed 分支，不读 inspection_lots。 风险：来料检不合格若只写了 inspection_lots.failed 而未同步生成 inspection_task(failed) 与 quality_hold，则仓库放行；反之若冻结已 release 但 inspection_task 的 failed 闭环未置 completed，failedInspection 分支会持续拦截 → 死锁。 改善：统一检验判定的唯一权威表；releaseQualityHold 时联动置 inspection_tasks.disposition_status， 两源同生同灭。
P0-2 · 仓库 ↔ 财务：调拨 / 盘盈盘亏的凭证与结账守卫缺口 需运行验证 实读坐实：generateOutboundVouchers 的 transfer 分支直接 continue（不挂成本，正确——同公司位置移动不产生损益）。但 调账/盘盈盘亏 （adjust_gain / adjust_loss，经 postCheckAdjustment → /api/inventory-adjustments PUT completed）当前未见生成存货跌价 / 管理费用凭证， 盘亏只减库存不动账 → 账面与实物差异无会计反映。 同时 assertPeriodOpen 需确认是否也覆盖调拨、调整两条过账路径（此前只坐实入库/出库）。 改善：盘亏生成 借 6602 管理费用 / 贷 1403/1405 凭证；盘盈 红冲；结账守卫下沉到调整/调拨端点。
P0-3 · 销售 ↔ 采购：销售退货与采购退货无 source_no 串联，供应商追责链断裂 实读坐实 实读坐实：sales_returns 与 purchase_returns 是两张独立表（0092）， 各自有 credit_note_no / voucher_no，但无共同 source_no 字段把 「客户退货 → 对应供应商赔付/采购退货」串起来。质量抽检不合格 → 客户退货 → 应向供应商追责， 这条链路无自动单据，需人工补录。 改善：sales_returns 增 linked_purchase_return_no；退货完成时按物料反查采购来源， 自动推送供应商平台协商单。
P0-4 · 仓库 ↔ 供应商平台：供应商信用额度仅按入库释放，缺出库/退货冲减对称 实读坐实 实读坐实：writeBackPurchaseReceipt 已实现按交货进度 applyVendorCreditDelta(-delta) 释放信用额度（B1 点，幂等水位 creditReleasedAmount）。 但退货/红冲（purchaseReturn）时未见对称地占回信用额度，会导致「退货后额度虚占不释放」或「重复释放」。 改善：采购退货完成时 applyVendorCreditDelta(+占回)，与入库释放成对。
P0-5 · 系统设置 ↔ 全模块：审批流只覆盖采购/销售/工单，质量/仓库/供应商单据未纳入 实读坐实 实读坐实：autoApproval.startApprovalForDoc 已接入采购单/销售单/工单 POST。 但 approval_flows.module 枚举含 inbound / outbound / invoice， 而仓库出入库、质量不合格品处置（unqualified_items 报废/让步）、供应商协议 落库后 未调用 startApprovalForDoc → 审批流对这些模块仍形同虚设（V3.63 待办①的延续）。 改善：在 inbound-orders / outbound-orders 端点及不合格品处置、供应商协议端点注入自动审批。

3. P1 待加强（联动缺口 / 口径不齐，8 项）

  • P1-1 供应商 ↔ 仓库/采购：交期分（deliveryScore）未自动回写 实读坐实 vendor_performance.deliveryScore 目前靠人工季度评估；实际入库日期 vs 订单交付期的达成率已在 purchaseReceiptWriteback 回写了 actualDeliveryDate，但未聚合成交期分写回。建议每日聚合任务算 deliveryScore。
  • P1-2 销售 ↔ 生产：销售订单未自动触发 MRP → 生产工单 需运行验证 mrp_recommendations 表已建，但销售订单确认 → MRP 缺口计算 → 建议工单 的自动链路未见注入。建议 SO 落库后触发 MRP 引擎。
  • P1-3 生产 ↔ 销售：完工入库未回写销售订单备货状态 需运行验证 finished_goods_inbounds 过账后未更新对应销售订单的备货/可发状态，销售无法实时掌握出货节奏。
  • P1-4 财务 ↔ 供应商：付款前未核验供应商结算价偏离 实读坐实 arapPosting.generatePaymentVoucher 按实付金额生成凭证，但未比对供应商协议价浮动区间。异常价格无拦截。
  • P1-5 系统设置 ↔ 质量：检验标准未纳入配置引擎统一管理 实读坐实 inspection_standards 直连 D1，但 settingsStore 未消费它；不同组织/物料标准缺版本控制与继承。建议纳入 voucherTemplate 同款配置引擎。
  • P1-6 质量 ↔ 销售：客户投诉/退货未回流质量模块建不合格品 实读坐实 销售退货（sales_returns）原因若为质量，未自动在 unqualified_items 建客户侧不合格品并关联 PDCA。
  • P1-7 生产/销售 ↔ 供应商：内部投诉未回传供应商平台 实读坐实 unqualified_items.portal_issue_id 字段已预留（供应商门户 issue），但生产领料异常、销售退货的质量责任判定未自动推送供应商门户。
  • P1-8 仓库 ↔ 系统设置：多仓库降级取「首个仓库」，无法指定目标仓 实读坐实 shipmentOutboundLink 无 warehouseId 时回退 ORDER BY created_at LIMIT 1（V3.62 边界④已知）。多仓场景仍可能发错仓，建议发货单强制指定仓库 + 校验。

4. 一致性与合理性专项（已做对的 / 需警惕的）

✅ 已坐实的优质联动（不建议改）： ① 发货→出库 shipmentOutboundLink：POST 建单即发货 + PUT 状态推进共用同一助手， source_no 查重 + inventory_posted=0 条件抢占保证幂等，无仓库时显式降级回传 postingError 不假成功； ② 收货回写 writeBackPurchaseReceipt：行锚点 orderItemId 累加 + 状态推进 + 供应商信用释放水位幂等； ③ 过账中枢 inventoryPosting：物料余额+流水+库存记录收进同一 db.batch 原子提交， 相对原子 UPDATE 消除并发丢更新，COALESCE 兜 NULL； ④ 凭证 arapPosting：模板优先+内置兜底、source+source_no 幂等查重、借贷平衡闸； ⑤ 自动审批 autoApproval：委托路由+SoD 自审拦截+幂等，失败静默不阻断主单据。
⚠️ 一致性风险点（同一事实多处口径，易分叉）： ① 检验三表并存（inspection_lots 在 Blob / inspection_tasks 关系表 / quality_holds 关系表）， 判定与拦截读不同表 → P0-1； ② 退货三套（sales_returns / purchase_returns / 入库 return 红冲凭证）各自独立，无 source 串联 → P0-3； ③ 库存成本双口径：前端 postOutboundCost 仍留 unitCost 快照，但权威成本以服务端移动均价为准 （V3.45 已去前端双写，前端仅留痕）—— 需确认界面展示取哪套； ④ 批次无独立表：batchRecords 由单据派生（recomputeBatchRecordsFromOrders），非权威源， 盘点/调整不重算批次 → 批次库存可能与实物分叉。
合理性判断：RLS 登记基本对齐——仓储域 inbound/outbound/inventory_records 登 dept， 质量/供应商绩效/退货登 all，供应商主数据登 own。语义合理。 唯一需复核：quality_holds（all）vs inspection_tasks（all）同源不同表，跨角色可见性一致，OK。
