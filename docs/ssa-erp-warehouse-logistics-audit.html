三、逐项发现（含证据与修复建议）

W1 · 盘点过账是纯前端假动作CRITICAL
类别：逻辑错位 / 不准确  |  代码位置：src/stores/warehouseStore.ts postCheckAdjustment 第 803–865 行

现象：「库存盘点」完成后，系统显示库存已按差异调整，但真实后端库存账（inventory_records / materials / inventory_transactions）完全未变，也不生成任何库存调整单与凭证。

证据（回代码走查）：postCheckAdjustment 只做两件事——① 在浏览器内存里直接改写 state.inventoryRecords 数组（第 816–850 行，纯前端数学加减）；② 把盘点任务状态 status:'completed' 通过 entityRepo.update('checkTask', …) 写回 D1（第 859–863 行）。全程没有任何一步调用后端库存过账接口：不调 /api/inventory-adjustments（而该端点本身已有完整的盘盈入/盘亏出 + 凭证过账逻辑），也不调 inventoryPosting.postInbound/postOutbound。

影响：盘点本是企业用来「修正账实差异」的核心动作，在此实现下它只改了一个浏览器内存投影，刷新页面或从库存查询接口（W5 指向的后端 inventory_records）取数，差异立即消失。等于「盘点功能形同虚设」，且因为不生成调整单/凭证，连审计线索都没有。这是本模块最严重的逻辑错位。

修复建议：盘点完成后应改为调用后端 POST /api/inventory-adjustments 创建调整单并 PUT …/completed 触发 inventoryPosting 真实过账（该端点的盘盈/盘亏/凭证逻辑已就绪，可复用）；前端只保留「派发差异 → 展示回执」的薄层，不再自行改库存数组。同时补齐一条 E2E 守护「盘点→调整单→库存_records 真的变」。

W2 · 物料余额字段可直接改写，绕过过账权威HIGH
类别：不准确 / 账实分叉  |  代码位置：functions/api/materials/[id].ts 第 109、114 行；functions/_shared/fieldAccess.ts 第 164–169、254–255 行

现象：PUT /api/materials/:id 用 current_stock = COALESCE(?, current_stock)、stock_value = COALESCE(?, stock_value) 直接写余额字段，任何拥有物料写权的角色都能绕过唯一过账权威 inventoryPosting，手工改库存余额。

证据（回代码走查）：物料字段级门禁 findForbiddenFieldWrites 仅拦截「隐藏集合内且值有变化」的字段。而隐藏集合对模块 material 只登记了 standardPrice / movingAvgPrice（成本价）。currentStock（current_stock）与 stockValue（stock_value）根本不在隐藏集合里——前者是库存数量、后者虽在列映射中却未进默认策略。于是任何有 material.update 写权的角色都能在 PUT 体里带 currentStock 直接改写库存数量，造成 materials.current_stock 与 inventory_records / inventory_transactions 账实分叉。

影响：这是「账实分叉」的高危面。过账权威精心维护的库存余额，可被一个 PUT 请求静默推翻，且字段门禁对此毫无察觉（它只挡成本价）。

修复建议：在物料 PUT 中彻底移除 current_stock / stock_value / moving_avg_price 的可写性，余额只能由 inventoryPosting 过账产生；即便要保留「期初建账」入口，也应走独立、带审计的初始化端点而非通用 PUT。并把这些余额字段加入字段级隐藏集合（至少非特权角色不可见、不可写）。

W3 · 调拨跨组织过账用错组织隔离键HIGH
类别：逻辑错位 / 对不准  |  代码位置：functions/api/stock-transfers/[id].ts 第 156、168 行

现象：库存调拨（stock-transfer）的「调出过账」与「调入过账」两条腿都使用 user.org_id 作为库存记录的组织键，完全忽略单据头上的 to_org_id。

证据（回代码走查）：第 156 行 postOutbound(db, user.org_id, …) 与第 168 行 postInbound(db, user.org_id, …) 均传入 user.org_id。而 inventory_records / inventory_transactions / materials 均按 org_id 隔离（rlsCondition 用 org_id = ?）。当 from_org_id ≠ to_org_id 时，调入仓的库存被记到调出方组织下，接收组织（to_org）永远看不到这批货，造成跨组织库存对不准。

影响：同组织内调拨正确（两仓同 org）；但跨组织调拨会让调入方库存「消失在错误的组织里」。种子数据里已有 ORG-001 与 ORG-002（wh-201 属 ORG-002），该路径一旦被使用即产生组织间账实错位。

修复建议：调入腿应改用 to_org_id 作为组织键（postInbound(db, head.to_org_id, …)）；并明确「跨组织调拨是否允许、以及是否需要组织间往来凭证」的产品口径，再补一条跨组织调拨 E2E。

W4 · 仓库主数据纯前端，零后端 / 零 RLS / 零守卫HIGH
类别：一致性 / 缺失项  |  代码位置：src/stores/warehouseMasterStore.ts 全文；后端 functions/api/ 无 warehouse 相关目录

现象：仓库与库位主数据（wh-001 主仓库、wh-002 辅料仓、wh-003 成品仓、wh-201 华东原料库）是纯前端 zustand persist 字典，只存在浏览器 localStorage，没有后端表、没有 RLS 行级隔离、没有操作守卫、没有审计、没有并发保护。

证据（回代码走查）：① warehouseMasterStore.ts 用 persist(…, { storage: backendStorage, name: 'ssa-erp-warehouse-master' })，种子数据硬编码在文件里（第 35–107 行）；② 后端 functions/api/ 下无任何 warehouse* 端点目录（已用 GLOB 确认）；③ 仓库的 orgId 仅是前端字段，跨组织可见性仅由前端 selectWarehousesByOrg（第 217 行）过滤，后端 rlsCondition 对仓库维度无约束点；④ 入库/出库/调拨单据引用的 from_warehouse_id / to_warehouse_id 是前端生成的 wh-*，后端无任何参照完整性校验。

影响：① 仓库定义不共享、不权威——不同浏览器/用户各自一套，清空浏览器存储即丢失；② 后端无法对「仓库」维度做隔离或审计，调拨/入库引用了一个不存在或属于别组织的仓库也不报错；③ 仓库增删改零审计，舞弊风险高。

修复建议：将仓库主数据下沉为后端实体（建表 + 端点 + RLS + 守卫 + 审计），至少保证仓库编码/组织归属的权威与参照完整性；前端字典改为从后端拉取。这是多组织正确性的基础，建议与 W3 一并立项。

W5 · 库存查询接口仅支持 keywordMEDIUM
类别：对不准 / 契约不符  |  代码位置：functions/api/inventory-records/index.ts 第 12–14、25–28 行

现象：库存查询接口 GET /api/inventory-records 只读 page / pageSize / keyword 三个参数，完全忽略 materialId / warehouseId。

证据（回代码走查）：第 12–14 行仅解析这三个参数；SQL 的过滤条件只有 org_id + 可选的 material_code/name LIKE（第 18–28 行）。任何调用方传入 materialId / warehouseId 都会被静默忽略、返回该组织全量记录。旧前端 src/services/warehouse.ts 的 getInventory 就传了这两个参数（W9 指出该文件是死代码，但接口契约缺口本身独立于调用方）。

影响：物料多、仓库多的组织无法在后端按物料或仓库过滤库存，只能全量拉回前端再筛（性能与带宽浪费），或误以为已过滤实则拿到全量。属于「接口契约与前端预期对不准」。

修复建议：在后端接口补 materialId / warehouseId（及 locationId / batchNo）服务端过滤参数；可一并补齐批次维度查询（见 W7）。

W6 · 前端双轨派生库存与后端权威账并存且分叉MEDIUM
类别：一致性 / 逻辑错位  |  代码位置：src/stores/warehouseStore.ts postInboundToInventory(104) / postOutboundToInventory(191) / recomputeInventoryFromOrders(442)，调用点 696 / 738 / 947

现象：前端保留了一套在浏览器里用纯函数重算库存的逻辑，与后端 inventoryPosting 维护的权威库存账是双轨，二者没有收敛断言。

证据（回代码走查）：① recomputeInventoryFromOrders（第 442–460 行）仅遍历 inbounds / outbounds 两个数组做加减，未纳入 stock_transfers（调拨）、inventory_adjustments（盘点/调整）、production（生产入库）；② 该派生数组被 loadWarehouseOrders（第 947 行）当作「库存」展示；③ W1 的盘点假过账正是建立在这套派生之上——改它而不改后端。结果：前端展示的库存（只含入/出库）与后端权威账（含调拨/调整/生产）在存在这些业务时必然不一致。

影响：用户看到的库存数字与库存查询接口（后端 inventory_records）可能不同；盘点又只改前端这套，进一步加剧分叉。这是 W1 能「假成功」的结构性根因。

修复建议：前端库存展示直接消费后端 inventory_records，下线浏览器内的 recomputeInventoryFromOrders 双轨（或仅作为离线兜底且明确标注「非权威」）；W1 修复后此双轨即无存在必要。

W7 · 批次无独立实体 / 端点MEDIUM
类别：缺失项  |  代码位置：批次仅作列承载于 inbound_order_items / outbound_order_items / stock_transfer_items 的 batch_no / location_id

现象：批次（lot/batch）不是独立实体，只是各单据上的列，没有批次台账查询端点，也没有批次维度余额重建 / 批次级成本滚动的专门守护。

证据（回代码走查）：① 无 batch 表与端点（GLOB 已确认）；② 过账时批次随单据写入 inventory_records.batch_no 与 inventory_transactions.batch_no（数据层有批次维度），但没有任何后端接口按批次聚合查询；③ 批次追溯（TraceBatch.tsx）依赖前端从单据重算，已核实为「真数据上的真计算」，但无后端批次账支撑，且前端派生与后端权威账同样有 W6 的分叉风险。

影响：按批次查库存、批次级成本追溯、批次效期管理等制造业高频场景缺乏后端能力；批次数据散落在各单据明细，难以做批次维度的对账与召回。

修复建议：提供批次维度查询接口（可复用 W5 的过滤扩展，按 batch_no 聚合 inventory_records）；并补一条批次级余额重建的 E2E，与流水底座对账。

W8 · 销售出库→COGS→财务对账端到端守护偏弱MEDIUM
类别：缺失项  |  代码位置：functions/_shared/inventoryPosting.ts generateOutboundVouchers 第 645–704 行

现象：出库过账已正确生成 COGS 凭证（借 6401 主营业务成本 / 贷 1405 库存商品，按服务端 unitCost×qty），但「销售出库→成本结转→财务对账」全链路缺乏专门 E2E 守护，仅由 19/41 套件间接覆盖。

证据（回代码走查）：凭证逻辑本身完整且幂等（source_no 查重）；但现有守护套件未端到端断言「一笔销售出库后，对应 COGS 凭证金额 = 库存减少金额 × 移动均价」。这是财务与库存对账的关键闭环，目前靠间接覆盖，回归时易被漏。

影响：库存模块与财务模块的数据对齐（成本口径）缺少机器护栏，未来改动过账逻辑可能 silently 破坏对账而未被发现。

修复建议：新增一条 E2E，创建销售出库→completed→断言 inventory_transactions 的出库 value_delta 绝对值 = 对应 OUT- 凭证的借贷合计；纳入 41 号审计套件或独立守护。

W9 · 死代码 src/services/warehouse.tsLOW
类别：缺失项 / 整洁  |  代码位置：src/services/warehouse.ts 全文

现象：该文件仅被 services/index.ts 桶导出，全工程无实际调用方；其请求路径（/inventory、/inventory/alerts、/:id/complete、/check-tasks）与真实后端（/inventory-records、complete 在 inbound/outbound 端点下、checkTask 走 entities 或前端）全对不上，属实质死代码。

影响：误导维护者、增加阅读成本；其「传 materialId/warehouseId」的契约（W5 相关）是陈旧假设。

修复建议：确认无调用方后删除该文件及其桶导出项；如确有按维度过滤库存的需求，改在 W5 的真实接口上实现。

W10 · 前端派生库存漏算调拨/调整/生产LOW
类别：不准确  |  代码位置：src/stores/warehouseStore.ts recomputeInventoryFromOrders 第 442–460 行

现象：前端派生库存函数只遍历入/出库单据，未纳入调拨、库存调整、生产入库等会改变库存的来源。

证据（回代码走查）：第 445–457 行仅对 inbounds / outbounds 循环重算。在有调拨/调整/生产业务的组织里，前端展示的库存天然与后端权威账不符（详见 W6）。

影响：与 W6 同源，是双轨分叉的具体表现之一；单独列出以便修复时一并处理。

修复建议：随 W6 一并下线前端双轨；若需离线兜底，必须把调拨/调整/生产来源也纳入重算口径。

四、已坐实扎实的部分（正面确认）

以下部分经走查确认实现正确、与全量 E2E 全绿（42 套件 0 FAIL）一致，不属于问题，仅供参考与信心建立：
  • 过账权威 inventoryPosting.ts：入/出库过账为「物料余额 + 库存流水 + 库存记录」三句 db.batch 原子提交；移动均价口径统一（移动均价 > 标准价 > 采购价）；超发两账本 Math.max(0,…) 卡 0；凭证按 source_no 幂等查重。
  • 调拨过账：双过账 + costPriceOverride 防成本漂移 + 反假成功回读校验 + 并发条件 UPDATE 抢占（杜绝双过账），逻辑严密（仅 W3 的跨组织组织键需修）。
  • 库存调整过账：盘盈 postInbound / 盘亏 postOutbound + 盘盈盘亏凭证 + 反假成功校验，逻辑完整（仅入口未被盘点链路调用，见 W1）。
  • 序列号管理：状态枚举统一（in_stock/shipped/scrapped/in_transit），出库前校验「在库 + 同物料」防重复发货与串号，符合 SAP/金蝶对标。
  • 四端点守卫到位：入库/出库/调拨/调整在 completed 时正确触发服务端过账；操作权限守卫（guardOperation）、状态机（guardStatusTransition）、乐观锁（withVersionGuard）均已接入。
  • 既有 E2E 守护：07-rls（库存记录隔离）、09-audit-match（入库三单匹配）、30/31/32/33/34/35/39 等已覆盖入出库/序列号/过账权威，且全量回归零失败。
