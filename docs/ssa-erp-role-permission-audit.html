对标 金蝶 KIS / 用友 U8 / SAP，逐条核对当前默认角色设计的合理性，列出不合理项并给完善方案
基准版本 V3.50.0 → 实施为 V3.51.0 日期 2026-10-07 ~ 10-08 范围：默认角色 · 操作矩阵 · 行级权限 · 审批制衡 · 角色词表一致性 定位：诊断结论 + 完善方案（强哥已拍板 4 决策点，P0/P1 已实施，本地 6 门禁全绿，待生产 E2E 坐实后部署）

一、先说结论

总体判断：底座扎实、角色集偏「菜单视角」、对标三大 ERP 暴露 4 处 P0 不合理 当前系统已经把「行级隔离（组织 / 负责人 / 部门）」「字段级脱敏」「默认拒绝」「审批委托 / 撤回 / 催办」「操作守卫」这些硬地基打得很完整， 属于同类自研系统里少见的水准。但默认角色矩阵的设计停留在「界面给不给按钮」的菜单视角，没有真正对标金蝶 / 用友 / SAP 的「业务职责分离」。 核心问题不在"谁不能看什么"，而在 四个会伤及资金与内控的红线缺口（见第三节），以及角色词表在 5 处定义已经断裂（第三节 R1）。
做得对、可保留（对标后仍是加分项）
  • 组织级隔离（org_id 强制写入 WHERE）+ 负责人 / 部门行级范围（RLS all / own / dept）；
  • 未登记表默认 1=0 拒绝 + 机器核对（不静默放行，这点比多数系统强）；
  • 字段脱敏「读侧剥离 + 写侧拒写」+ 硬敏感基线（银行账号 / 税号不可被界面放开）；
  • 审批委托 / 撤回 / 催办的服务端闸 + 委托不允许转给自己（防空转）；
  • 特权角色（超管 / 管理员）统一豁免，口径一致。
对标三大 ERP 后，不合理项集中在 4 类
  • 制单与审核未分离（SoD，职责分离）：提交人可指定自己当审批人，系统无制衡；
  • 财务对采购 / 销售 / 供应商零写权：财务能制凭证却不能管采购付款、不能建供应商，财务监督形同虚设；
  • 采购员可建 / 删供应商：把「选供应商」和「录采购单」都交给同一人，违背供应商制衡；
  • 角色词表 5 处断裂：销售角色在后端悬空、生产主管 / 研发 / 工艺在操作矩阵里"能创建却被拒"。

⚠️ 交叉核对顺带暴露 15 处历史遗留结构性缺口（前端 defaultRoleModuleOps 缺 * 兜底行 + approval 协作维护 + serial/purchase-request 条目，V3.45~V3.48 该同步没同步）——方向是"界面少给按钮"、不造成越权（后端兜底守住），属本批范围外，建议单独立项，未夹带。

四、不合理项清单（按严重度 P0 → P3）

P0 = 伤及资金 / 内控红线，建议优先修；P1 = 合法用户被误拒或明显口径冲突；P2 = 一致性 / 可维护性；P3 = 体验增强。

级别问题依据（代码事实，非推测）
P0 R-SoD · 制单与审核未分离
提交审批时 approverId 由前端传入，服务端没有校验"提交人 ≠ 审批人"。一个人能建采购单、再把审批人填成自己、再点批准，闭环自审。供应商同理可走通。		 functions/api/approval-instances/index.ts onRequestPost：只做了委托路由，未做 submitter_id ≠ approver_id 校验；[id].ts 的 approve/reject 只认"当前审批人"，但若当前审批人本来就是提交人自己，仍会通过。
P0 R-FIN · 财务对采购 / 销售 / 供应商零写权，监督失效
财务主管 / 会计只有财务模块写权，不能改采购付款计划、不能建 / 改供应商、不能动销售收款。三大 ERP 里财务是收付款的最终闸门，当前设计让财务对资金流出（采购付款）完全没有抓手，采购员可独立"下单 + 收货 + 触发付款"。		 operationGuard.ts BUILTIN_ROLE_OPS 中 finance_manager / accountant 仅有 finance 全权 + approval 读改；采购、销售、供应商模块均无对应写权限条目（默认拒绝）。
P0 R-VEN · 供应商建档权只归特权角色 + 供应商门户改不了自己（倒挂）
供应商主数据建档权被收紧为「只有 admin / super_admin（* 特权）能建，采购员 vendor.create=false」——但菜单 ROLE_DEFINITIONS 仍给采购员 vendor.create 按钮（点了会 403，又是一处菜单 vs 矩阵矛盾），且系统没有一个中立的"供应商建档"专职角色。同时 供应商门户改不了自己资质（矩阵 vendor 模块对门户只读、无 update），资质维护反而要等特权角色代管，逻辑倒挂。		 operationGuard.ts 第 91 行 buyer 对 vendor 是 create=false/update=true；供应商门户（vendor）对 vendor 模块只读无 update；07 号 E2E 实测「buyer 建供应商 → 403 OPERATION_FORBIDDEN」坐实菜单与矩阵口径相反。
P1 R-WD · 生产主管 / 工艺工程师「能创建却被拒」
菜单给了 production.create / edit 按钮，但矩阵生产模块只读 → 点新建工单 / 改工单被 403。合法用户被挡在自己日常操作外。		 settings.ts prod_manager / process_engineer 的 permissions 含 production.create/edit；operationGuard.ts 二者走 * 兜底只读，无 production 写条目。
P1 R-ROL · 角色词表 5 处断裂（最隐蔽、最伤维护）
同一套角色在 5 个文件里各自定义、且不一致：① 前端类型（13 角色，无销售）；② 前端菜单 ROLE_DEFINITIONS（13，无销售）；③ 后端权威词表 fieldAccess.REAL_ROLES（14，多 sales_manager）；④ 后端操作矩阵（15，又加 salesperson）；⑤ 用户角色白名单 users/[id].ts VALID_ROLES（13，无销售）。结果：sales_manager / salesperson 是"悬空角色"——后端矩阵有它们、但管理员界面根本授不出来（不在白名单）、前端类型也不认。		 5 处文件角色集互有出入：settings.ts、roleOperation.ts 无销售角色；fieldAccess.ts REAL_ROLES 含 sales_manager；operationGuard.ts 另含 salesperson；users/[id].ts VALID_ROLES 不含任何销售角色。
P2 R-DEL · 删除权过宽
采购员对采购订单有「删除」、财务对凭证有「删除」、销售主管对销售订单有「删除」。三大 ERP 里删除制单据一般收口给更高角色，且历史单据应「作废 / 冲销」而非物理删除，便于留痕与追溯。		 operationGuard.ts buyer.purchase.delete=true、accountant/finance_manager.finance.delete=true、sales_manager.sales.delete=true。
P3 R-DEF · 供应商门户默认全模块只读偏宽
外部供应商按当前矩阵对几乎所有模块都"只读"。对标 SAP 门户，供应商通常只能看"与己相关"的单据（自己的订单 / 报价 / 发货），不应默认看全组织数据。		 operationGuard.ts vendor 走 * 兜底只读（全模块可读），未收敛到"仅自身相关单据"。

五、完善方案（等拍板，未改代码）

P0-1 · 上"制单与审核分离"服务端硬闸（SoD） 在 approval-instances 提交与审批两处各加一条校验：
  • 提交时：approver_id === submitter_id 直接 403 拒（提示"审批人不能是提交人本人，请指定其他责任人"）；
  • 推进到下一节点时（approve 后填 nextApproverId）：下一审批人 === 提交人 同样拒；
  • 委托路由仍保留，但委托后实际审批人若等于提交人，也要拒。
改动点集中在 functions/_shared/approvalInstance.ts 加一个纯函数 assertSoD(submitterId, approverId) + 两个端点各调一次，配 2 条单测（"自审被拦" + "他人审通过"成对，遵守项目"加闸门必配合法路径不断"铁律㊹）。
P0-2 · 财务补"收付款闸门"写权，让财务真正管到资金 给 finance_manager / accountant 在 purchase 模块补「付款计划（fin-payment-plans）写 + 供应商对账读」、sales 模块补「收款计划读 / 写」——注意是精准给到资金相关端点，不是把整个采购 / 销售模块写权放开（否则又违反最小权限）。 具体：purchase 模块的 fin-payment-plans 端点按财务放行，采购订单 / 供应商主数据本身仍不给财务写权（选商下单权保留在采购）。
P0-3 · 供应商建档权拆分，把"选商"与"下单"分开
  • 先消除菜单 vs 矩阵的 403 矛盾：现状矩阵已把 buyer.vendor.create 收成 false（建档权只归特权），但菜单还留着"新建供应商"按钮 → 二选一：撤菜单按钮（建档权留在特权角色，采购员只"提议 / 维护已有"）或放开矩阵（采购员可建供应商）。建议前者（更合内控），撤按钮。
  • 供应商门户：把 vendor 模块从"全组织只读"改成"仅自身相关单据只读"，自身资质改（vendor.self.edit）放行（对应现在 P3 的倒挂）；
  • 新增"供应商申请"轻量流程：供应商在门户提报资质 → 由财务 / 管理员审核建档。这样"选商权"与"建档权"分离，符合三大 ERP 的主数据管控，且给"中立建档权"补上当前缺失的专职角色。
P1 · 修"能创建却被拒"的合法用户 + 统一角色词表
  • 给 prod_manager / process_engineer 在生产模块补 create / update 写权（与菜单对齐，班长保留读 + 改，主管 / 工艺加 create）；
  • 把销售角色收敛：要么正式把 sales_manager / salesperson 纳入 5 处词表（类型、菜单、后端词表、操作矩阵、用户白名单 5 处一起加），要么从后端矩阵移除这两条悬空角色。建议前者（销售域确实需要），但必须 5 处同步，并加一条机器核对（仿 check-field-policy.mjs 的做法，做一个"角色词表一致性"门禁）。
P2 · 删除权收口 + 历史单据走作废 / 冲销 采购订单 / 财务凭证 / 销售订单的 delete 默认收紧（业务角色不给物理删除，改给「作废 / 冲销」状态切换；物理删除只留特权角色或后台运维）。与项目已有"凭证红冲合法、已过账禁改"的既有口径保持一致。
