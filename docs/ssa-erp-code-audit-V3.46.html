二、确证缺陷清单（带证据）

P0-A 通用父子框架写端点漏接操作权限守卫——只读角色可直接调接口越权写

「操作权限守卫」的模块映射表已为 9 组业务声明了对应关系，代码注释也白纸黑字写着「配套：父子框架创建/更新/删除要按模块统一守卫」，但这句承诺没落地。父子框架的三个写函数全文没有任何一处调用守卫。后果：界面里被禁用写权限的「普通用户」角色，绕过界面直接调这些接口就能写数据。

证据：functions/_shared/operationGuard.ts:42-48（注释自认「配套…未落地」）；functions/_shared/parentChild.ts（pcCreate/pcUpdate/pcRemove 无 guardOperation）； 实例 functions/api/process-routes/index.ts:20（直接 pcCreate 无守卫）。 受影响的 9 组端点：process-routes、vendor-quotes、purchase-requests、fin-payment-plans、fin-project-accounts、shipments、sales-prospects、projects、approval-flows；外加 4 组专用端点 fixed-assets、three-way-match/create、unit-conversions、entities 通用资源。 对照组（已正确处理）：work-orders、vouchers、materials、customers、vendors、入库/出库/调拨/库存调整等单表端点均已正确接守卫——说明团队知道写法，唯独通用框架这条线漏了。

P0-B 敏感字段脱敏只对 2 类端点生效，客户/销售/采购主通道明文返回

项目定义了一张 67 条的「敏感字段矩阵」（哪些角色不能看信用额度、税号、银行账号、单价金额等），但服务端只在「供应商」和「物料」两类接口真正执行脱敏。客户、销售订单、采购订单这三条主通道都是整行明文返回——界面上做了字段隐藏是「装饰性的」，改动前端代码或直接调接口即可读到全部敏感数据。

证据：functions/_shared/fieldAccess.ts（矩阵已建，但客户/销售/采购三组规则无端点消费）； 明文返回点 functions/api/customers/[id].ts:128-146（creditLimit/taxId/bankAccount 等明文）、functions/api/sales-orders/[id].ts:24-35（unit_price/amount 明文）。 对照：vendors、materials、protected-data 三类端点已正确接脱敏。

P0-C 库存过账非原子 + 幂等标志可被客户端直写 + 无对账作业

过账是「写物料主数据 → 写库存流水 → 写库存余额」三步独立操作、无事务包裹；写流水那一步出错时被吞掉、不回滚（代码注释自己承认「需对账修复」），但全项目没有对账作业去发现这种漂移。更严重的是：防止重复过账的「已记账」标志在改单接口的白名单里，客户端可以自己把它置 1 让系统以为已记账、实际库存从没动过；并发改单还有「读后写」的重复过账窗口。

证据：functions/_shared/inventoryPosting.ts:104-109（写流水吞错不回滚，注释「余额已变动，需对账修复」）； :186→197→210（三步无事务）；functions/api/inbound-orders/[id].ts:68,77（白名单含 inventoryPosted，可被直写）； 4 个删除端点（inbound/outbound/调拨/盘点 [id].ts）直接删、审计只写「需人工核对冲销」，作废标志建了表却无任何代码去置位。

P0-D 固定资产折旧可并发双计提，资产台账与凭证跨事务非原子

折旧的「同期间只提一次」靠的是「先查有没有凭证、没有就全量重提」，没有锁、没有抢占。而且「更新资产台账」和「生成凭证」是两个独立的批量写、不在同一事务里。后果链：第二步（写凭证）中途失败或并发时，资产台账已经累计了折旧，重放或并发会基于「已被累加过的值」再提一次——台账记了两遍、凭证只有一张甚至没有，账实背离。

证据：functions/api/fixed-assets/depreciate.ts:92-107（select-then-act 无锁幂等）； :185（资产表 batch）与 :190（凭证 batch）跨 batch 非原子。 对照组：凭证写入 functions/_shared/voucherWriter.ts:141 与改凭证 vouchers/[id].ts:115-145 都用同一批量原子写——团队知道原子写法，唯独折旧这条链没做。

P1-A 汇率「生效日期」列建了没接，且结构上存不下多行历史，缺失时静默按 1 处理

声称「补上汇率表缺失的生效日期列」属实（列加了、索引也建了），但全代码库没有任何一处查询按这个日期取数，索引是死索引；且唯一约束没改，同一币种对永远只能存一行、每次刷新覆盖，「取期末最后一条汇率」这条口径在数据模型层面根本不成立。该币种没有汇率记录时，前端直接按 1 算（静默放行，不是拦住）。

证据：migrations/0081_finance_config_tables.sql:71（加列）+ :79-80（死索引）vs 0014:11（UNIQUE 未改）； 全库 grep「按汇率表查询」仅 2 处、均不带日期条件；缺失静默按 1：src/stores/financeExtensionStore.ts:72、src/pages/Finance/PeriodClosing.tsx:96。

P1-B 预算闸门「累计口径」跨期错位，读预算不按期间取数，异常时按 0 放行

预算判定取预算值时不带期间条件、直接取一条（不确定取到哪个期间的）；而「已发生额」是跨全部期间累计的凭证借方，却拿它去比「某一期的预算」——时间维度错位，长期运行必误判超预算。更隐蔽的是：当已发生额这条统计查询失败时，直接按 0 计算后放行，等于给了一笔大额付款开绿灯。

证据：functions/_shared/paymentGate.ts:174-182（读 fin_budgets 无 period 过滤 + LIMIT 1）； :217-220（已发生额跨全期累计）；:222-225（查失败按 0 放行，注释自认）。 对照：真正的「累计已付+本次」口径在发票超付检查 :391 是写对的，但预算这条没复用对。

P1-C 结账期间锁定的「未初始化」回退路径仍是放行，与声称的「拦住」自相矛盾

读「结账期间表」失败时确实改成了拦住（放行改拦截），这点做对了。但「新表还没初始化的组织」不是读失败、是「成功但一行都没有」，会回退到旧的键值存储；而这条回退路径在键不存在或解析失败时一律放行——即「期间锁」对这类组织静默失效，和文件头注释承诺的「宁可拦住也不给错误的安全感」直接冲突。

证据：functions/_shared/appState.ts:58-78（新表空→回退旧键；旧键缺/解析失败→return false 放行）；头部注释 :31-33 与实现矛盾。

P2 BOM 叶子展开工具「建了没人用」，且无深度上限、无循环引用保护

为「把嵌套 BOM 摊平成全部实物料」新写了一个展开工具，注释还强调「凡要全部实物料的地方必须走它」，但全项目零个调用方——物料需求计算、成本卷积实际用的都是另一套图遍历（那套有深度上限）。这个工具一旦被接上，遇到脏数据的循环 BOM 会因无环保护、无深度上限直接栈溢出白屏。

证据：src/utils/bomResolver.ts:122（flattenBomLeaves 定义，无深度/环保护）全项目仅自身递归、无业务调用；对照 MRPPlan.tsx:250 有 MAX_BOM_DEPTH 上限。

四、改善路线图（按投入产出比排序）

补 P0-A：父子框架接操作守卫。给父子框架的创建/更新/删除加「按模块守卫」，一次接完 9 组端点 + 4 组专用端点，与代码注释承诺对齐。低成本高回报，直接堵住最大越权面。
补 P0-B：敏感字段脱敏扩到三大主通道。把服务端脱敏从「供应商/物料」扩到「客户/销售订单/采购订单」，读侧隐藏、写侧拒改。消除「界面脱敏、接口明文」的绕过。
补 P0-C：过账改条件抢占 + 失败即拦 + 对账作业。用「条件更新（只有未记账才过账）」杜绝标志直写与重复过账；写流水失败改为同生共死（回滚）；新增对账作业比对流水合计与库存余额。根治账实不符。
补 P0-D：折旧原子化 + 抢占式幂等。幂等改用「不存在才插入」的抢占写法，资产台账与凭证合并进同一事务批量。防双计提。
补 P1-A/B/C：财务口径对齐 + 堵住放行后门。汇率表改多行历史并按期末取数、缺失改拦住；预算按期间取数、累计口径与预算期对齐、异常不放行；结账期间「未初始化」回退改拦住。财务数字才对。
P2 收口：删掉或真正接线 BOM 叶子展开工具。要么接进物料需求/成本卷积并补深度上限+环保护，要么删除，避免留一个「地雷级」未用函数。清技术债。
关于「全面测试确认达到金蝶/用友最新水平」的诚实说明： 本报告是静态代码审计，能坐实「哪些闸门没接、哪些口径错位、哪些竞态窗口」，但这些缺陷多数必须连上真实数据库并并发操作才暴露得出来，无法只靠代码阅读 100% 证明「已达成生产可用」。 要达到「可交付真实客户」还需三步：① 修完上述 P0 后跑一遍带并发与负例的端到端守护；② 部署上线后拉生产库核对「流水重建余额 = 库存余额」「无重复折旧凭证」「无越权写记录」；③ 合规红线（数电票真实通道）需企业税号与服务商密钥到位才能验。
