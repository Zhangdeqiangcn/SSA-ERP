零、先看结论（30 秒版）

我的建议：只做「只读」，暂不做「必填」；先把 hasOperation 这个骗人的开关处置掉。

理由一句话：「可见/不可见」已在 V3.21.0 落地，而「看得见但不该改」这块目前完全空白——这是当前最大的真实缺口；「必填」则是最容易挡住真人干活的一类规则，而系统已有的逐字段校验基本够用，通用化收益低、误伤风险高。

一、为什么不能「顺便加上」——三个维度的默认方向是相反的

「可见 / 不可见」「只读」「必填」看起来是同一类东西（都是「这个角色对这个字段能干什么」），但它们的出错方向完全不同，因此不能用同一套开关、同一种默认值：

维度它回答的问题判断失误的后果安全的默认值应该是
可见 / 不可见
已完成		 这个角色该不该知道这个数字 泄密——银行账号、授信额度被无权的人拿到 宁可多遮（读不到配置就按最严来）
只读
建议做		 这个角色该不该改这个数字 挡住正常干活——库管改不了自己该改的字段，会立刻来找你 一律放开（没登记就允许改）
必填
建议暂缓		 这个字段能不能空着 单据存不下去——历史数据本来就缺这个字段时，那张单永远保存不了 一律放开（没登记就允许空）
★ 这是本方案最要紧的一条

V3.21.0 里「不可见」的实现是 fail-safe（读不到配置就按最严遮）——这个方向对「保密」是对的，但如果照着抄给「只读」，一上线就会全员改不了字段。三个维度的默认方向必须分别定，不能复用同一套「读不到配置怎么办」的逻辑。

为什么现在才提这件事

因为「只读」和「不可见」有重叠但不相等。已经被「不可见」覆盖的组合（例如库管看不到授信额度），再配「只读」是多余的——看不见自然改不了。所以只读真正要解决的问题是这一种：字段看得见、但不该由这个角色改。

举个系统里真实存在的例子：库管能看到物料的 price（采购价），也能改它。这个组合现在没有任何管控——这才是缺口。

二、「只读」建议怎么做

2.1 语义定义（先说清，避免后面扯皮）

场景字段可见？允许提交修改？拦截方式
字段对该角色「只读」是，正常显示值否值有变化 → 403，并说明是哪个字段
字段对该角色「不可见」否（键不返回）否同 V3.21.0，先于只读判定
未登记是是（默认放开）不拦

判定顺序：先看可见性（不可见直接拦），再看只读。理由是不可见更严，且能给出更准确的原因（「这个字段你看不到」比「这个字段你是只读」更贴切）。

2.2 判定沿用同一个「值确有变化」原则

和 V3.21.0 一样：字段出现了不算违规，值真的变了才算。否则编辑页保存时回传整个对象，会把只读字段原值一起带上，正常改动会被误拦——一个「改动联系电话都被拦」的规则，下场一定是被要求关掉。

2.3 需要你拍板的核心：只读清单

下面是我按「业务口径应该由谁维护」推出来的一份建议清单。这类口径我不能替你定（涉及你们实际分工），但可以给一个可以直接改的起点：

模块字段建议只读的角色理由（业务口径归属）是否已被「不可见」覆盖
物料price 采购价库管、质检、班长、物流进价是采购谈下来的结果未覆盖（真缺口）
物料standardPrice 标准价库管、质检、班长、物流、供应商成本口径由财务/采购维护已不可见（配了也是冗余）
物料movingAvgPrice 移动平均价同上系统按出库自动算，本就不该手改已不可见
物料currentStock 当前库存全部业务角色（含采购员）库存只能通过单据变动，不能手改数字——手改会让账实不符且无凭证未覆盖（真缺口，且风险最高）
采购unitPrice 单价库管、质检、班长、物流单价属采购口径已不可见
销售unitPrice / orderAmount库管、质检、班长、物流报价属销售口径已不可见
供应商 / 客户creditLimit 授信额度库管、质检、班长、物流授信属财务口径已不可见
财务voucherAmount 凭证金额工程、质检、库管、物流、采购、班长、供应商凭证金额只有财务能改（且已过账的更不许改）已不可见
这份清单里真正新增价值的只有两行

物料采购价与物料当前库存。其余各行都已经被「不可见」覆盖了，配上只读只是把规则写得更完整（不影响行为）。

其中「当前库存」这一行我特别建议纳入：库存数字如果能被手工改写，账实就不一致、又找不到是哪张单造成的。系统里库存本该只由入库/出库/调整/倒冲这些单据驱动。

三、「必填」为什么建议暂缓

3.1 必填其实是两件事，风险差别很大

类型含义现状我的判断
创建时必填 建单时这个字段不能空 已有：逐端点上写了针对性校验（如物料编码与名称必填、必填参数缺失返回 400） 不建议通用化 各端点的必填项本来就不一样，做成一套通用开关反而要挨个去核对口径，收益低、漏改风险高
更新时不可清空 原来是 A，不允许改成空 没有（这是新能力） 窄做可以考虑 只挑几个「天然不该空」的字段，不做成全员可配
必填最危险的地方：它会把「历史数据缺失」变成「单据永远存不了」

举个真实场景：某张历史工单的仓库字段是空的（当年建单时没这个要求）。某天你给「仓库」配了必填，这张单从此再也保存不了——而且改的是别的字段也会被一起拦下。这种情况在业务现场很常见。

相比之下「只读」出事最多是「某个字段改不了，去找管理员放开」；「必填」出事是「这张单一动就报错」，排查起来更绕。

3.2 如果要做，建议这样收窄

  • 只做「更新时不可清空」，不做创建时必填的通用化；
  • 只挑「不该空」的字段，例如：已过账凭证的金额、已有库存的物料编码、已完工工单的完工数量；
  • 灰度顺序：先只在「可编辑的常规单据」上启用，历史单据与已锁定单据不受影响；
  • 报错要能看懂：直接说「凭证金额不能清空，因为该凭证已过账」，而不是一句「参数不合法」。

四、三条路径的代价对比

路径内容改动面主要风险我的评价
A · 只做只读 加 readOnly 维度 + 服务端拦截 + 配置界面三选 + 套件扩充 后端 1 模块 / 试点域 4 端点 / 1 个配置页 低：默认全放开，不主动勾就不改变任何现有行为 推荐
B · 只读 + 必填（窄做） A + required 维度（仅「更新不可清空」）+ 逐字段口径确认 A + 各字段口径梳理 中：口径定错会把历史单据卡死 有需求再做
C · 全做（含创建必填） B + 创建时必填通用化 + 全表单梳理 大：要过一遍全部表单与端点 高：几乎必然出现「该填的没拦住、不该拦的拦住了」 不建议
为什么推荐 A 而不是「一次做完」

因为 A 的收益已占这三个维度总收益的大部分（它填的是完全空白的「可见但不可改」），而它的风险又是最低的（默认放开 + 不勾不生效）。先把便宜又安全的那块拿到手，再按真实需求决定要不要往下走，比一次铺开然后回头收拾误伤要划算。

五、顺带说一个「骗人的开关」：hasOperation

摸底时发现系统里有一个模块级操作权限矩阵（hasOperation），意思是「谁能建单、谁能删除、谁能审批」这类权限。它在配置界面上可以勾选，但——

全项目零调用点

这个函数只有定义、没有任何地方调用它。也就是说：你在界面上勾的每一个权限，都不会被执行。

这比「没有这个功能」更糟——没有它，你会去用别的方式管控；有了它，你会以为已经管住了。两个选项：

选项做法代价适合什么情况
① 标注为「未启用」 界面上把这块明确标成未启用（或直接隐藏），等有明确需求再接 小（改界面文案/显隐） 我建议先这样做 诚实优先，避免误以为有管控
② 真正接上 把模块级权限接进各端点的写操作判定（建单/删除/审批） 中～大（要过一遍写端点，且要定「哪个角色能建哪种单」的口径） 当你确实需要「限制某些角色建单/删除」时

注意选项 ② 要拍的口径，和「只读」是同一类问题（「哪个角色能对这个数据做什么」），所以如果打算接，建议和只读一起做，一次把口径定齐，避免分两次打扰业务部门。
