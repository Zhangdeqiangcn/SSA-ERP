## 零、这份计划怎么用

1. **第 0 期先做**，其余期次按第 0 期实测结果再定。
2. 每项都带**验收口径**，不验收不进入下一期——这是本项目一贯纪律。
3. 排期按**单人全职**估算；两人可并行第 1 与第 2 期（制造与财务互不冲突）。
4. 全部结论可用报告附录 A 的命令原样复跑。

**总量**：约 102–134 人天 ｜ **建议历时**：4 个月（两人并行）／5.5 个月（单人串行）

### ★ V3.113.3 实测复验修正（2026-10-27）

> 本节记录对上方第 0 期 P0 结论的**实测复验**结果。原表基于静态代码检索（grep）推断，
> 复验发现 **1 条被推翻、1 条比原报告更严重、2 条属实但范围需细化**。
> 结论：**任何基于单点 grep 的「断链」结论，必须端到端实测后才能写进计划。**

| 编号 | 原结论 | 实测结果 | 修正动作 |
|---|---|---|---|
| P0-1 | 委外发料**不过账**，库存不减、借贷必不平 | **推翻**。实测链路：`subcontractStore.issueMaterials` → 通用出库端点 `POST /api/outbound-orders`（type=subcontract）→ 服务端扣库存 + 写流水 + 生成凭证 `OUT-{outboundNo}`，借 1408 委托加工物资 / 贷 1403 原材料。**7/7 断言全过**（库存 100→60、存货价值 0→600、凭证借贷平衡）。<br>原报告根因：只 grep 了 `functions/api/subcontracts/*.ts`，未追通用出库端点 | 降级为 P2-6「委外凭证可追溯性」（当前凭证 `source='inventory'`、无委外单号回溯标记；委外单与过账无强绑定） |
| P0-2 | 合并报表无账簿条件，两套账混算 | **属实，但需细化**。`vouchers.ledger_book` / `voucher_items.ledger_book` 列**本就存在**（迁移 0065 加、0068 重建保留），生产实测每个组织确有 0000 法定 + 1000 管理两套账。真实缺陷是**聚合 SQL 抹平了账簿维度**（GROUP BY 不含 ledger_book）+ 抵消跨账簿进行 | 已修：聚合按账簿分组、抵消只在同一账簿内、账簿白名单入参、结果带账簿清单；前端账簿多选 + 分列 + 账套切换 + 导出带账套列 |
| P0-3 | 质量扣留不写冻结量，判废料可出库 | **属实，且发现更深层问题**。① `inventory_records.frozen_quantity` 全链路无人写无人读；② **既有质量拦截（V3.63.0）只查 `status IN ('pending','active')`，漏掉 `rejected`** → 「已判不合格但未处置（未报废/返工/退货）」的料照样能出库（这才是真正的漏洞）；③ 前后端状态词表分裂（前端把后端 `released` 当扣留中 → 物料永久锁死） | 已修：冻结量落台账 + 同步扣 `available_quantity`；放行/删除回冲（实际解冻量防虚增）；出库按可用量硬拦截；状态词表前后端统一为共享词表 `qualityHoldStatus.ts`；**拦截补上 rejected** |
| P0-4 | 供应商门户无审核激活入口，整模块归零 | **属实，且比原报告更严重**（生产复验又发现第四处断裂：**注册组织归属靠「公司码前 3 位 LIKE + LIMIT 1」猜**，生产同前缀组织 762 个 → 供应商被静默落到别的组织，管理端永远查不到 → 已加归属歧义守卫，多候选时 409 明确拒绝）。除缺审核端点外，实测发现三处额外断裂：① 前端调用的 6 个端点（`pending-approvals`/`approve`/`reject`/`blacklist`/`unblacklist`/`ratings`）**后端全部不存在**；② **双供应商表断裂**——`vendors`（门户账号表）与 `vendor_master`（主数据表）生产实测各 15 / 90 行，按 id 与 vendor_code **均零匹配**，审核操作作用在主数据表、登录读的是账号表，状态永不同步；③ 自助注册只写账号表 → 管理端根本看不到申请 | 已修：补齐 7 个端点；新增共享 `vendorApproval.ts` 做两表状态同步与状态归一（`active` → `approved` 幂等自愈）；注册同时双写两表；评级落 `vendor_performance` 并还原前端契约 |

## 第 1 期 · 制造工艺可计算（4 周 · 25–32 人天）

> 目标：从「能演示制造」变成「能算准成本」。这是对标用友 U9 cloud 2026 的可验收能力，也是赢单的关键。

| 编号 | 事项 | 内容 | 工作量 | 验收口径 | 状态 |
|---|---|---|---|---|---|
| M-1 | 工序级成本 | 区分「上序转入」与「本序投入」；工序表加在制结转字段；工单实际成本由**凭证派生**（领料 + 收货 + 报工 + 差异过账） | L（8–10 天） | 多工序工单：材料差异能**拆出价差与量差**，不与标准成本重复计算 | ☐ |
| M-2 | 废品成本多算法分摊 | 按数量/金额/工时/固定比例四种分摊可配置；废料入库与损耗差异分开 | M（4 天） | 同一工单换算法 → 总成本**恒等不变**，仅科目间结构变化 | ☐ |
| M-3 | MRP 供应侧补全 | 在制工单/计划订单/委外在制纳入供应；统一现有量口径（扣冻结）；独立需求 vs 相关需求标记 | M（4 天） | 自制件在制 100 件 → **不再建议再生产 100 件** | ☐ |
| M-4 | 批次成本差异分析 | 批次层标准 vs 实际差异分析 | M（3 天） | 某批次出库能回溯到该批次**自身**的标准与实际成本 | ☐ |
| M-5 | 智能裁切（一维） | 余料最少化一维裁切算法（条料排布），输出母材需求与切割方案 | M–L（5–7 天） | 给定订单长度组合 → 利用率**优于贪心顺序排布**，母材需求与实际出库量一致 | ☐ |

**依赖**：M-1 依赖第 0 期 P0-1（委外过账）与 P0-3（冻结量）先落地，否则实际成本仍然算不准。

## 第 2 期 · 合规与资金（5 周 · 30–40 人天）

> 目标：拿到「进候选名单」的门票。银行对账是资金管理入场券；电子凭证是 2026 中国市场的一票否决项。

| 编号 | 事项 | 内容 | 工作量 | 验收口径 | 状态 |
|---|---|---|---|---|---|
| F-1 | 电子凭证全流程 | 接收 → 解析 → 验签 → 入账 → 归档；支持 GB/T 46971-2026 与 GB/T 25500（XBRL） | L（8–10 天） | 银行电子对账单自动下载、验签、入账、归档**全通**，可过财政部应用验证自检 | ☐ |
| F-2 | 数电票开具与红冲 | 对接第三方通道的蓝票开具/红冲/作废 | M（4–5 天） | 业务单据可开票，红冲生成反向凭证 | ☐ |
| F-3 | 银行对账 | 流水导入（CSV/OFX）+ 自动匹配 + 未达账项调节 + 余额由凭证派生 | L（8–10 天） | 导入 3 个月流水 → 未达账**全部自动匹配或有据可查**；余额不可手工改 | ☐ |
| F-4 | 电子会计档案 | 凭证/发票/附件归档与检索、影像关联 | M（4 天） | 2026 已全面普及，缺此项在国企/上市客户直接出局 | ☐ |
| F-5 | 多币种报表折算 | 三路径（标准/管理/重估），与期末汇兑损益一致 | M（4 天） | 外币资产负债按指定路径折算，**与汇兑损益结转金额自洽** | ☐ |

**可并行**：F-1/F-2/F-4 走外部通道对接，F-3/F-5 走内部数据模型，两者互不阻塞。

## 第 3 期 · 智能体平台化（7 周 · 34–44 人天）

> 目标：把已有的工具层从「ChatBI 一个页面在用」升级为「平台化能力」。抄金蝶灵基的连接器形态，不抄它的平台叙事。

| 编号 | 事项 | 内容 | 工作量 | 验收口径 | 状态 |
|---|---|---|---|---|---|
| A-1 | 统一工具注册表 | 把 ChatBI 现有 9 个只读 SQL 工具 + 关键业务动作（建单/审批/过账/发运）抽成治理化工具层：统一鉴权、参数校验、幂等键、可回溯 | L（8 天） | 任一业务动作可被工具调用，**且不绕过既有权限与审计** | ☐ |
| A-2 | 业务本体 | 关键实体/关系/指标口径的结构化定义（物料、客户、供应商、单据、成本要素） | L（10 天） | 智能体问「本月各客户毛利」→ 口径**与报表页一致**（同一指标注册表） | ☐ |
| A-3 | 调用治理与成本核算 | 每工具调用记 token/时长/成本/成功率；按用户与场景归集 | M（4 天） | 能出「本月 AI 调用账单」 | ☐ |
| A-4 | 效果评测基线 | 财务/供应链/制造三套题集，回归每次改动 | M（4 天） | 每次发布跑分，**智能体改动有量化回归保护** | ☐ |
| A-5 | 制造 AI 场景落地 | 在已具备的 APS/预测/AQL/成本数据之上做插单模拟、排产建议、呆滞预警 | L（8 天） | 插单模拟给出**延误天数与瓶颈工序**，与实际排程偏差可解释 | ☐ |

## 资源取舍建议

| 场景 | 建议 | 理由 |
|---|---|---|
| **只做一件事** | 第 0 期（13–18 人天） | 生产可用率 62% → 约 75%，投入产出比最高 |
| **目标是赢单** | 第 0 期 + M-1/M-2/M-5（约 30–40 人天） | 工序级成本 + 废品分摊 + 智能裁切，是对标用友最有杀伤力的三件套 |
| **目标是进国企/上市候选名单** | 第 0 期 + 第 2 期（约 45–60 人天） | 银行对账 + 电子凭证 + 电子档案，缺任一项直接出局 |
| **讲长期故事** | 全部四期（102–134 人天） | 但**不建议本轮启动** |

**明确不推荐本轮做的事**：追智能体平台化叙事（A-1~A-4）。本项目当前瓶颈是**生产可用率与制造工艺深度**，不是智能化。先让系统敢上生产、能在制造客户现场算出准确成本，再谈智能体。

## 待强哥拍板的三件事

1. **第 0 期是否立即开工？** 4 项 P0 中，「委外不过账」和「合并无账簿口径」涉及业务数据口径，需确认业务方对正确算法的期望。
2. **生产沙箱租户的 4 条 `V31132` 验证数据**是否清理？（与本计划无关，顺带一问）
3. **旧版 4 份对标文档**（V2.29 / V2.50 / V2.56 / V3.44.0）是否按「同一事项只保留一个最新文件」原则归档或删除？本报告已声明取代它们。
