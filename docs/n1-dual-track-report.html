一、问题背景（为什么要在服务端算库存）

入库单、出库单保存时，系统原本在浏览器里当场算一遍库存数量、移动加权平均价、库存金额，再把结果写回物料表。三处隐患：
隐患后果
算完两边各写各的前端算一遍、后端又存一遍，两处逻辑对不齐时账悄悄错
绕开界面就没人算直接调接口、批量导入、脚本对接时浏览器算法不参与，库存账不更新或半更新
超发被算成负数旧算法「库存维度」用 Math.min 夹 0，但「物料主数据维度」允许负数——两套账对不上，月底盘点发现「库存账说有货、财务账说欠货」
这是对标评测定的「演示级 vs 生产级」真正分界（编号 N1，架构级）。判断标准：绕开界面，这条规则还成不成立？不成立，就等于没算。

二、双轨比对（落地前的安全验证，V3.15.10 阶段）

动手前先用测试组织做「前端现状算法」与「独立写的服务端算法」双轨比对，确认口径一致、可直接复用，并定位唯一真矛盾：
比对项结果
移动加权平均价 / 库存金额 / 库存数量 六组场景6 / 6 自洽一致
发现的唯一矛盾超发时 inventory_records.quantity 夹 0 与 materials 维度允许负，两策略冲突（仓库维度 warehouseStore.ts 与成本维度 cost.ts）
结论前端 cost.ts 口径正确、可原样下沉服务端；矛盾列为下沉时必须统一的点

三、本次改动清单（V3.16.0）

新增 functions/_shared/inventoryPosting.ts 改 入库单 POST+PUT 端点 改 出库单 POST+PUT 端点 前端去 materials 双写 超发两维度统一卡 0
文件改动
functions/_shared/inventoryPosting.ts（新增）服务端权威过账：rollIn/rollOut（移动均价口径对齐 cost.ts）、按「物料+仓库+库位」查/建 inventory_records、upsert materials.current_stock/stock_value/moving_avg_price；金额 2 位、单价 4 位小数
入库单 / 出库单 端点（POST + PUT）状态变 completed 且 inventory_posted=0 时触发过账（幂等）；PUT 只传状态不带明细时从库读明细再算；过账异常只记日志、不阻断建单
src/utils/cost.tsrollOutMovingAverage 改为 Math.max(0, …)，与物料维度同口径夹 0（落实强哥拍板）
src/stores/warehouseStore.ts删 materialStore.updateMaterial 双写调用（避免前端回写覆盖服务端权威值），保留乐观预览与凭证单价/金额来源

超发策略（强哥拍板）：两套账统一 Math.max(0, …) 夹 0，不采用「允许负数 + 告警」。理由：负数会在两维度间制造矛盾、直接误导采购与生产决策；「实际欠多少」交给业务侧超发提示处理，而非让财务账自己演负数。
