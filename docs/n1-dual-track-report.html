N1 双轨比对报告

库存与成本计算「下沉服务端」前的安全验证 · 2026-09-20 · 项目 SSA ERP（企业资源管理计划）

结论先行：双轨比对已完成。在同一批构造的出入库流水（覆盖标准、移动均价变化、超发、零单价兜底、10 轮舍入漂移、除零 6 类场景）下， 「前端现在算的」与「服务端独立重算的」结果完全一致（6/6）。说明现状库存算法内部自洽，下沉服务端时可直接复用现有口径，不会引入账实不符。 同时抓到 1 个真实设计不一致点（超发出库时两个库存维度策略矛盾），列为下沉时必须统一的设计项，不阻塞本轮验证。

一、N1 是什么（为什么必须做这件事）

N1 是对标评测报告里的第 N1 项架构级改进项：当前系统的算账逻辑——库存数量增减、移动加权平均价、库存金额、出库成本结转（COGS，即销售成本）——全部写在前端网页脚本里（src/stores/warehouseStore.ts 与 src/utils/cost.ts）， 后端（Cloudflare 数据库 D1，即项目的分布式数据库）只负责「接收结果、存起来」。

这种「演示级」结构的致命问题是：绕开网页界面直接调应用程序接口（API，即前后端通信接口）改数据，算账规则完全不生效——两个人同时操作、或脚本批量写入，库存会变成负数、金额会对不平而没人拦得住。这是「演示级 vs 生产级」的真正分界。

「下沉服务端」= 把这些算账规则搬到后端，无论谁、用不用界面，结果都一样正确。但下沉有风险：如果前端和服务端算出来不一样，账就乱了。所以强哥拍板先「开个测试组织做双轨比对」——同一笔业务两边各算一遍，对照看一致不一致，再决定怎么沉。

二、方案选择（选了什么 · 为什么 · 怎么回退）

项目内容
选了什么 采用算法级双轨：把前端现有算法（cost.ts 的 rollInMovingAverage/rollOutMovingAverage 等）严格复刻成「前端轨」，另写一份独立、按标准会计规则实现的「服务端轨」，对同一批构造流水各跑一遍对照。 测试环境用构造的隔离数据集（不写入生产库），零生产风险、可一键复现（脚本 scripts/n1_dual_track.mjs）。
为什么 ① 创建独立组织需走「注册 + 邀请码 + 超管审批」流程（functions/api/auth/register.ts），副作用大、摩擦高； ② 前端过账只在浏览器里发生，直接调 API 建出入库单不会自动过账库存，所以「真实组织灌数据」拿不到前端实际写入值，双轨价值与算法级等价； ③ 命中硬规矩「非改数据结构（新增数据表）本轮跳过」——算法级零写库、零建表，完全可逆。验证安全性这个核心目标已达成。
怎么回退 本轮未对生产库做任何写入（仅读取过代码与一次公开验收）。双轨脚本为只读计算，删掉 scripts/n1_dual_track.mjs 与 tmp/n1-dual-track-result.md 即完全还原。 若后续要「生产库真实组织灌数据」版本，会单独建 N1T__ 前缀的隔离测试物料/仓库/单据，比对完即用脚本清理。

关于「开测试组织」的诚实说明：本轮回退一步，用「隔离测试数据集」语义完成双轨验证，未新建独立组织。若强哥要我在生产库真建一个独立测试组织并灌数据跑通完整链路，列为下一步，需授权走注册流程或直接插入组织行（可删回退）。

判定口径：金额容差 0.01 元（分），均价容差 0.0001。同时比对了「服务端同口径（每步同样四舍五入）」与「服务端精确浮点」两版——前者验证前端自洽（0 差异），后者暴露累积舍入误差（本批用例漂移为 0，说明现状四舍五入口径稳健）。

核心结论：现状前端算法在普通与边界场景下均自洽，下沉服务端时直接复用 cost.ts 口径即可，不必重写，风险可控。

四、真实发现的不一致点（下沉时必须统一）

问题：超发出库时，库存的两个维度策略矛盾。

  • 仓库维度（inventory 表）：出库扣减用 Math.min(现有数量, 出库量) 把数量卡在 0，不允许负库存（src/stores/warehouseStore.ts:209 与 :212 的 availableQuantity: Math.max(0, …)）。
  • 物料主数据维度（material 表）：出库成本结转用 rollOutMovingAverage，注释明确「不做负库存 clamp——超发时数量/金额转负，属需人工冲正的异常」（src/utils/cost.ts:109-111 与 :129 的 quantity: q0 - qo）。

结果：同一笔超发（库存 30、出库 50），仓库维度显示 0，物料主数据显示 -20——两个库存视图对不上，月底对账永远不平。这违反「金额≈数量×单价」恒等式的一致性。

分级：中等（中等严重）。正常业务不应超发，但一旦发生（并发、漏审），两个维度互相矛盾会让排查无从下手。

下沉服务端时的处理建议（二选一，写进下一轮方案）：

  • 方案甲（推荐）：两个维度都「允许负 + 告警」——与成本注释的设计意图一致，负库存显式暴露、不静默吞掉，配合超发告警让人工冲正。
  • 方案乙：两个维度都 clamp 到 0——简单但会静默丢失成本（成本注释已指出这比负库存更危险，利润虚高），不推荐。

回退：本轮仅记录，未改代码；若下一轮采用方案甲，改动集中在 warehouseStore.ts 的 Math.min/Math.max(0,…) 两处，一处改一处核对，单提交可回滚。

五、对「下沉服务端」的指导（落到下一轮）

  • 可直接复用：src/utils/cost.ts 的 rollInMovingAverage / rollOutMovingAverage / roundAmount / roundPrice 口径已被双轨验证自洽，服务端版本照抄即可，不必重新设计。
  • 必须先统一：超发时 inventory 与 material 两个维度的负库存策略（第四节），否则服务端照抄会原样继承这个矛盾。
  • 对照机制保留：本脚本 scripts/n1_dual_track.mjs 作为回归基线——下一轮每下沉一个域（库存→成本结转→暂估→报表），先跑一遍双轨确认两轨一致，再接生产路径。

  1. 确认超发策略（甲/乙）——这是下沉前唯一必须拍板的设计点，半小时可定。
