一、审批中心新增三个动作

此前审批只有"提交"和"通过 / 拒绝"三种状态：单子填错了撤不回来，只能等对方拒绝；审批人忘了处理没有任何提醒；审批人出差，单子就卡死。本版补齐三件事：

动作谁可以做具体做了什么
撤回 提交人本人或管理员 把单据收回来，同时把它退回草稿——不是只改一个状态字段，业务单据真的回到未提交状态，并可重新提交
催办 提交人本人或管理员 提醒当前审批人，系统记录催过几次、什么时候催的；同一单据 30 分钟内只能催一次，避免变成刷屏骚扰
委托 任何审批人 出差 / 请假期间把审批权交给同事，可限定只管某一类单据、也可管全部；委托期内轮到你审批的单子自动转给对方，单子上标注"代某某批"

几处刻意的设计取舍

  • 审批通过 / 驳回只能由当前节点的审批人本人操作，管理员也不能代办。审批是责任动作，代价是纠错要走"撤回"而不是让管理员直接批——换来的是"谁批的"永远可追溯。
  • 委托关系单独建表，而不是在用户资料上加一个"代理人"字段。加字段只能表达"谁代理谁"，表达不了"代理到哪天"和"只代理采购类"这两件事。
  • 新增了一个只返回姓名、部门、角色的轻量名录接口。委托时要选人，而唯一能列出用户的接口只有管理员能用——那结果就是"委托功能对普通主管不可用"。名录不返回邮箱和手机号：办事只需要知道找谁。
  • 撤回不是只改标记。如果只把审批记录标记为"已撤回"，而采购申请单本身还挂着"审核中"，采购同事看到的仍是"在审"、审批人待办里也还在——用户以为撤回了，实际没有。

侧边栏"审批中心"新增"我提交的"分组（可催办 / 可撤回）与"审批委托"入口。另外，原先把侧边栏的 ✓ / ✕ 两个按钮点下去是没有反应的（代码里是待办占位），现在会真的审批，或者在单据不支持快捷审批时明确提示"请到某某页面处理"，不再假装成功。

二、导出数据的管控（真 Bug 修复）

任何登录用户此前都能把任意列表全量导出为表格，没有权限要求、没有记录、文件里也没有标识。本版：导出前检查权限；每次导出都写一条审计日志（谁、什么时候、在哪个页面、导出了多少条）；导出的文件名和表格末尾带上导出人与时间戳。

⚠ 这块"看起来早就做了"，实际上一条记录都没落库 上一轮已经写了导出留痕的代码，但那段代码发请求时没有携带登录令牌，后端一律判定为"未登录"、直接拒绝；而这个错误又被一个空捕获吞掉了，界面上完全看不出来。 结果就是：留痕代码写得很像样，服务端一条日志都没有。本版新增了一个"带令牌请求头"的统一出口，把两处同类问题一起修掉。

这类缺陷正是"合规意义上等于零"的典型——功能开关显示为开，实际上没有任何数据产生。

三、单位换算规则进入正式数据库

换算规则（如 1 箱 = 12 个）此前只存在浏览器本地，换台电脑就不一样、也不进备份。现已迁入服务端数据库，全公司口径统一，改动有审计记录。

⚠ 上一轮只建了仓库，没人往里搬货 上一轮确实建好了数据表和接口，但前端仍然读写浏览器本地那份——新表从头到尾没被用过一次。更麻烦的是，建表的那条数据库迁移从来没有应用到生产库，也就是说线上接口查的是一张不存在的表。

本版把前端主源切到数据库、并补上了漏掉的那条迁移。另有"恢复默认"按钮的语义被修正：它原先会连带抹掉公司自定义的换算率，属破坏性操作，已改为"重新加载"。

四、随本轮一并收口的遗留缺陷

这几项不是新功能，是复查时发现"上次说修了、其实没修好"的地方。共同特征是：代码语法完全正确、编译门禁一个都抓不到，但用户看到的/拿到的就是错东西。

位置原来的毛病现在
质检抽样方案
（按 GB/T 2828.1 标准）		 显示出来的"字码"与"样本量"可能对不上——455 种"批量 × 检验水平 × AQL"组合里有 124 种互相矛盾。例如显示"字码 B、样本量 2"，而字码 B 对应的样本量是 3。检验员照着执行会抽错数量，而质量判定直接建立在抽错的数量上。 字码与样本量始终取自同一行；实测 455 种组合零矛盾。
采购比价页的评分条 一句本该"鼠标悬停才显示"的提示，被写成了页面上的正文，于是每条评分条旁边都多印出一行 title="已计算分数" 的字。 提示恢复正常，悬停才显示。
采购比价页的"评分权重"按钮 引用了不存在的图标名，该页面直接编译失败——打开就是白屏。 换成实际存在的图标，页面恢复正常。
财务报表页 只能打印，不能导出 PDF。 新增"导出 PDF"按钮。
凭证 / 报表 PDF 导出函数 自建的临时元素没设编号，而打印函数是按编号去找元素的——永远找不到，然后静默返回。表现是"点了没反应、也不报错"。 补上编号，导出可正常触发打印预览。

其中第一项特别值得说明："字码与样本量矛盾"属于"界面上看着正常、其实给人错数字"的类型，任何类型检查都抓不到（代码语法完全正确），只有把全部组合跑一遍、做交叉核对才会暴露。这也是本轮把"同类判定必须放在同一屏对比"列为常规检查项的原因。

五、★ 一项失实的"已修"结论被更正

"三单匹配"目前不能当作付款的自动闸门 系统里有一个"采购订单 / 收货单 / 发票三者一致才能付款"的控制点。上一版把它标记为已修复——超差时会返回一个"应阻断"的标记，供付款流程拦截。

本轮复查发现：这个标记从来没有任何人读过。
  • 后端那个接口前端从来没调用过，而且它连读取接口都没有（只有"创建"没有"查询"）；
  • 界面上的三单匹配是前端自己另算的一套，跟后端那个接口没有数据往来；
  • 三个付款相关页面没有一处在付款前检查这个标记。
也就是说：闸门造好了，但没有人接线，付款实际仍不会被拦。

复查中还发现更基础的一层：那个接口的地址本身就是错的——文档和代码注释里写的地址实测返回"方法不允许"（405），必须带后缀才能进去。也就是说，即使有人照文档去调用，也调不通。

本版如实记录了这一点（写进使用说明书的注意事项与代码注释），避免下一个人继续按"已修"理解；正式整改列入下一轮。在此期间，付款前的一致性核对仍需人工完成。

新增常驻套件"审批实例"，共 50 条断言，全部通过。关键几条已实证：

  • 撤回后业务单据真的退回草稿（不是只改标记），且可重新提交；
  • 委托期内待审批单据自动改派给受委托人，原审批人信息被保留（用于标注"代批"）；

  • 单位换算接口返回 200 且带真实数据（坐实"表已上生产库"）；
  • 组织成员名录只返回 id / 姓名 / 部门 / 角色，不含邮箱手机号；
  • 未登录访问审批接口返回 401。

本轮抓出的两个"只有真跑才会暴露"的故障

两个新接口的列表查询在管理员名下会返回 500——原因是查询条件的占位符数量与绑定参数数量不一致（SQL 里有 1 个占位符、却绑定了 2 个参数）。这类问题本地构建、类型检查都不会暴露，只有对真实生产端点发起一次请求才会出现。已修复。

七、两条固化下来的工程教训

教训一：类型检查的"基线快照"会无差别吸收新引入的真错误 项目为后端函数维护了一份"已知问题基线"，检查时只报新增。本轮发现那个恒为假的表达式其实早就被类型检查报了出来，只是在一次"刷新基线"时被当成"历史遗留噪声"一起收了进去——从此门禁再也看不见它。

这与"把安全网上的破洞剪掉补成平的"是同一件事。新规则：刷新基线前，必须先把当前问题清单与旧基线按"文件 + 错误内容（不含行号）"做一次差集审查，确认新增为 0 才允许写入。
教训二："后端有、前端没调用"的端点不能默认当作无害预留 一致性核对的输出里有一句"后端有但前端未调用 = 66 条（预留 / 后台端点，通常无害）"。本轮证明这个桶里至少藏着一个"声称已修但实际没接线"的能力（就是上面第五节那个付款闸门）。

新规则：凡声称"已修 / 已上线"的能力，必须回答"谁在调用它、绕过界面是否仍然成立"，不能凭"端点存在"判定功能成立。
