## 0. 执行摘要

### 0.1 三句话结论

**第一，功能差距已经不是主要矛盾了。** V2.50 报告判定的"功能缺失"在 V2.51–V2.56 期间被大量填补：现有 191 个页面覆盖 12 个业务模块，源码 9.1 万行。更重要的是，抽查 24 个关键页面，**13 项是真算法实现**——MRP 做到了 BOM 多级展开＋净需求＋MOQ＋提前期偏置；库存做到了移动平均价滚动；成本做到了递归多级卷积；三大报表真的从凭证借贷汇总并做平衡校验；业财一体化甚至做到了 **GR/IR 暂估应付冲销**（收货借存货/贷暂估，发票校验时冲暂估确认应付，避免重复入账）这种 SAP 标准口径。这个深度超出了"演示系统"的范畴。

**第二，短板性质发生了转移：从"功能少"变成"地基浅 + 智能化断层 + 合规空白"。** V2.56 上线了后端，但后端只有 5 张表（组织/用户/会话/状态/供应商），业务数据是把整个前端状态序列化成一个 JSON 大字段存进 `app_state` 表——没有业务实体表、没有服务端校验、没有事务、没有按字段查询能力。同时，2026 年三家标杆的竞争焦点已经全面转向 **Agentic AI（智能体）**，而 SSA 这块基本为零。国产化合规（金税/数电票/电子会计档案/会计准则）为零实现，这在中国市场是一票否决项。

**第三，"初步跑通"这个结论需要打折。** 类型检查实测发现 **418 个类型错误、涉及 144 个文件**，其中 **3 个详情页存在确定的运行时白屏崩溃**——用户点进去就是白屏。这三个页面分别是销售项目详情、出库单详情、生产工单详情，都是主流程上的核心页面。建议在做任何对标改进之前先修这个。

## 2. 阻断性缺陷清单（测试首要发现）

按项目的测试验收纪律，缺陷优先于对标。以下是本次类型检查实测发现的问题，**建议先修再谈对标**。

### 2.1 P0 阻断级：3 个页面运行时白屏崩溃

这三个页面用到了未 import / 未定义的**值**，JS 运行时会抛 `ReferenceError`，React 渲染中断 → 白屏。

| # | 页面 | 文件:行号 | 根因 | 影响 |
|---|------|----------|------|------|
| **BUG-01** | 销售项目详情 | `src/pages/Sales/ProjectDetail.tsx:124,159,161,224,225,228` | MUI import 缺 `Button`；图标 import 缺 `Edit` | 打开任一销售项目详情即白屏 |
| **BUG-02** | 出库单详情 | `src/pages/Warehouse/OutboundDetail.tsx:178,186,189,197,200,208,211,218` | MUI import 缺 `Button`（8 处引用） | 打开任一出库单详情即白屏 |
| **BUG-03** | 生产工单详情 | `src/pages/Production/WorkOrderDetail.tsx:207` | 变量 `sourceItems` 未定义（在 PrintPreviewButton 的 record 属性内被求值） | 打开任一工单详情即白屏 |

**证据**：`ProjectDetail.tsx:3-7` 的 MUI 导入清单为 `Box, Typography, Paper, Chip, Grid, LinearProgress, Stack, Divider, TextField, Dialog, DialogTitle, DialogContent, DialogActions, IconButton, Alert, Snackbar, Step, StepLabel, Stepper, MenuItem` —— 有 `IconButton`，**没有 `Button`**；`:8-10` 图标清单为 `Warning, Add, CheckCircle, Error, Timer, TrendingUp, Share` —— **没有 `Edit`**。

**为什么构建没拦住**：Vite 用 esbuild 转译，**不做类型检查**。`npm run build` 成功 ≠ 代码正确。项目的 `npm run lint` 配置了 `--max-warnings 0`，但 CI 流程里未强制执行。

**修复成本**：极低，补 import + 定位 `sourceItems` 数据源，预计 30 分钟内可全部修完。

**建议**：立即修复，并把 `tsc --noEmit` 加入构建前置检查，防止回归。

### 2.2 P1 严重级：418 个类型错误 / 144 个文件

| 错误码 | 数量 | 含义 | 风险等级 |
|--------|------|------|---------|
| TS2322 | 156 | 类型不可赋值 | 中 |
| TS2345 | 102 | 参数类型不匹配 | 中 |
| TS2339 | 45 | 属性不存在 | **高**（可能运行时 undefined） |
| TS2769 | 25 | 无匹配重载 | 中 |
| **TS2304** | **24** | **找不到名称** | **高**（值引用即崩溃） |
| TS2305 | 18 | 模块无此导出 | 中 |
| TS2739 / TS2741 | 24 | 缺少必需属性 | 中 |
| 其他 | 24 | — | 低 |

**两个集中的技术债**（占 100 个错误，24%）：

1. **`StateStorage` vs `PersistStorage<T>` 类型不兼容（63 处）** —— 这是 V2.56 后端化改造留下的债。`persistStorage.ts` 的 `backendStorage` 实现了 `StateStorage` 接口，但 zustand `persist` 的 `storage` 选项要求 `PersistStorage<T>`（两者 `getItem` 返回类型不同：`string` vs `StorageValue<T>`）。**当前靠类型不安全的方式工作**，一旦 zustand 升版可能整体失效。
   - 修法：用 `createJSONStorage(() => backendStorage)` 包装，或显式声明为 `PersistStorage<T>`。

2. **`partialize` 返回类型签名错误（37 处）** —— 各 store 的 `partialize` 只返回数据字段（正确做法），但类型签名被推断为必须返回完整 `State`（含所有 action 函数）。
   - 修法：`partialize: (state) => ({...}) as unknown as XxxState`，或在 persist 泛型上显式指定持久化子集类型。

3. **类型未导出（TS2305，18 处）** —— 供应商门户相关类型（`VendorStatement`、`VendorInvoiceRequest`、`DeliveryShipment`、`VendorQualityIssue`、`VendorImprovementReport`、`VendorOrderConfirm`）在 `@/types` 中未导出，但 6 个页面 + `flowStore` 在 import。运行时不崩（类型擦除），但 IDE 无提示、重构不安全。

4. **`src/utils/aql.ts:118`** —— `code` 属性被指定两次，后者覆盖前者。这是**潜在业务逻辑 Bug**，AQL 抽样方案的 code 可能取错值，建议人工核对。

## 7. 架构与非功能差距

### 7.1 后端化真相（V2.56 最大变化的准确评估）

Git 提交声称"V2.56.0: 后端上线(D1+Pages Functions) + 真实账号登录 + 多人数据共享"。逐条核实：

| 声称 | 实际 | 判定 |
|------|------|------|
| 后端上线 | 8 个 Functions 文件、405 行；**只有认证 + 一个通用 KV 接口** | ⚠️ 部分成立 |
| D1 数据库 | **5 张表**：`orgs`/`users`/`sessions`/`app_state`/`vendors` | ⚠️ 仅基础设施表 |
| 真实账号登录 | ✅ 真实：SHA-256+盐、token 会话、30 天有效 | ✅ 成立 |
| 多人数据共享 | ✅ 登录后整个前端状态按 `org_id` 共享 | ✅ 成立 |
| 业务 API 后端 | ❌ **不存在**。无物料/订单/库存/凭证等实体接口 | ❌ 不成立 |

**核心事实**：业务数据的持久化路径是 `zustand persist` → `backendStorage`（`persistStorage.ts:34-100`）→ `PUT /api/state/:key` → D1 表 `app_state(org_id, key, value)`。也就是**把整个 store 序列化成 JSON 存进一个大字段**。

这带来五个结构性问题：

1. **无法按字段查询** —— D1 里存的是 JSON 文本，SQL 无法 `WHERE vendor_id = ?`。所有查询必须把全量数据拉到浏览器再过滤。
2. **无服务端业务校验** —— 所有业务规则（信用检查、库存扣减、审批权限）都在前端。**改浏览器 JS 就能绕过全部管控**。对 ERP 这是致命的。
3. **无事务** —— "出库 + 生成凭证 + 更新库存"这三步没有原子性。中途失败会产生账实不符。
4. **并发覆盖风险** —— 两个人同时操作，后保存的整块覆盖前者。**多人共享的实现方式本身会丢数据**。
5. **数据量天花板** —— 单条记录存全量数据，随业务增长会撞上 D1 单值大小限制与传输性能墙。

另外，`src/services/apiService.ts`（68KB）和 `src/services/api.ts` 是**死代码**——设计了完整的 REST 层但 UI 未接入（`api.ts:2` 自陈"模拟 RESTful 风格，桥接 Zustand Store"）。`services/material.ts:45` 打向 `/materials/import`，该接口不存在。

|------|-----------|----------|------|------|
| 部署 | Cloudflare Pages + D1（边缘） | 云原生多租户 SaaS | 同 | 同 |
| 后端 | 8 文件 405 行 Functions | ABAP Cloud + BTP | 苍穹 PaaS + Java/Go 微服务 | iuap + Java 微服务 |
| 数据库 | D1（SQLite）5 张表 | HANA 内存列式 | 分布式集群 | 分布式集群 |
| 业务数据模型 | **JSON blob in KV** | 完整关系模型 | 完整关系模型 | 完整关系模型 |
| 服务端校验 | ❌ | ✅ | ✅ | ✅ |
| 事务 | ❌ | ✅ | ✅ | ✅ |

## 9. 改善建议路线图

### 9.1 一个必须先说的判断

**不要把"补齐三家的功能清单"作为目标。**

理由很直接：SAP 有 50 年积累，金蝶 2026 上半年 AI 原生产品一项收入就 2.96 亿，用友 U9C 深耕制造 18 年。SSA 是 9.1 万行前端 + 405 行后端。在功能广度上打军备竞赛，投入无底、结果必输，而且会持续制造"建了页面没接线"的技术债——本次测试已经发现 4 个壳、7 个半实现，都是这个模式的产物。

V2.56 真正的问题不是"功能比人家少"，而是**"能不能交给一个真实客户用"**：

- 3 个主流程详情页点开白屏
- 418 个类型错误没治理，构建不拦类型问题
- 业务规则全在前端，改浏览器 JS 就能绕过审批和信用控制
- 数据存成 JSON blob，两人同时操作会互相覆盖
- 没有备份，数据丢了没有回滚点
- 供应商注册了永远登录不上
- 猜到公司码就能进别人的组织看全部数据
- 不能开数电票、不对接金税，在中国做不了真账

这些和"有没有 AI Agent"不在一个层次上。**先把系统变成"能用"，再谈"能卖"，最后才谈"能赢"。**

## 10. 结论

### 10.1 对"初步跑通"的判定

**部分成立，但有条件。**

- 主干流程确实跑通了：P2P、O2C、Plan2Produce、R2R 四条核心流程主干贯通，且关键算法（MRP 净需求、移动平均计价、多级成本卷积、三大报表从凭证汇总、GR/IR 暂估冲销、三单匹配、有限产能排程）都是真实现，不是演示壳。这个完成度值得肯定，也修正了 V2.50 报告对财务和生产模块的低估。
- 但"跑通"目前只在**单人、演示数据、不追求正确性保障**的条件下成立。3 个主流程详情页点开白屏；业务规则可被前端绕过；多人同时用会互相覆盖数据；数据没有备份。

### 10.2 差距的真实结构

对标三家，SSA V2.56 的差距**不在功能清单**，而在三个层次：

1. **地基层**（最紧急）：后端只有认证+KV，无业务表、无服务端校验、无事务、无备份。这决定了系统能不能承载真实业务。
2. **合规层**（商业化红线）：金税/数电票/电子会计档案/会计准则零实现。这决定了能不能卖给中国企业做真账。
3. **智能层**（战略差距）：2026 年三家已进入 Agentic AI（SAP 自主财务/供应链 Agent、金蝶灵基 40+ 智能体、用友 YonClaw），SSA 为零。这决定了三年后还有没有位置。

好消息是：SSA 已有的规则引擎、预测算法、差异校验逻辑，正是 Agent 需要的"工具层"。缺的是数据结构化 + 大模型编排这两步。**追赶智能层的成本，取决于地基层做得多好。**

### 10.3 一句话建议

**别追功能，先修地基。** 用 13 人日把系统变成"能用"（修崩溃、堵越权、加备份、类型门禁），再用 4 个月把地基关系化并跨过合规红线，然后选采购寻源或钢材垂直一个战场做深——而不是在 12 个模块上和三家做军备竞赛。
