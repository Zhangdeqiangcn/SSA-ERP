核心结论

四域表单流转的整体设计是完整的——单据状态机、行级权限、金额校验、过账中枢、审计留痕一应俱全，采购域的失败回滚甚至做到位。但存在三类系统性缺陷，它们不是 88 个孤立问题，而是少数几个根因在四域重复出现：

  • 有一处功能完全不可用：生产域建工单必然返回 400（后端要一个系统里根本不存在的字段），已打真实接口坐实。这是本次最严重的问题。
  • 有两处管控实际失效：销售信用额度闸门（授信 1000 可无限超额下单，已坐实）、销售员可见并改动他人订单（行级权限失效）。
  • 有一类问题反复出现：历次整改（并发防重、金额复核、原子化）都只覆盖了「新建单据」，系统性漏掉了「修改单据」这条路径。这是最值得改的方法论问题。

三、根本原因：6 个系统性缺陷

这是本报告最有价值的部分。88 条问题收敛为 6 个根因——修根因比逐条修补更有效，而且能解释为什么同一个毛病反复出现。

根因 A · 修复只覆盖「新建」，系统性漏掉「修改」影响 8 条 P0/P1

此前三轮整改（并发防重、多表原子化、金额复核）都是按「创建路径」实施的，修改单据的路径被系统性遗漏。同一份能力，新建做对了、修改没做。

典型：并发抢占做了新建、漏修改；金额按明细复核做了新建、漏修改；多表原子化做了新建、漏修改。
教训：整改必须按「同一能力的两条路径成对核查」，不能再按端点逐个修。

根因 B · 行级权限「登记了但数据侧没填」销售/项目/发货/意向客户

这几张表在权限登记表里设的是「只看本人」，但建单时从不记录「这张单是谁建的」。规则里又有「无归属人 = 全员可见」的历史兼容分支，于是失效方向是放行而不是拒绝。

危害：销售员能看到并修改、删除他人的订单，权限形同虚设。这是本次发现的唯一「越权」类问题。

根因 C · 前端传了、后端静默丢弃9 个字段·涉及三域

请求里带了但后端没实现的字段，被默默丢掉并且返回成功——不报错、不告警、无任何痕迹。受影响的包括：供应商确认交期、订单行关联、报工进度、领料明细、附件、质量标准等。

为什么危险：比直接报错更难发现。用户看到「保存成功」，实际数据没落库，事后也查不出原因。

根因 D · 守卫取数漏字段，导致静默失效最隐蔽的一类

状态机校验时，查询语句少取了一个「状态」字段，传给校验函数的是空值，校验规则查不到对应规则就直接跳过——整套状态机等于没生效。已完成、已取消的订单可以被改回任意状态。

同类：盘点任务的权限映射目录为空，同样导致守卫失效。
教训：守卫的入参必须「缺什么就报错」，绝不能让空值流进守卫后静默放行。

根因 E · 金额与成本口径多处实现，前后端漂移6 处不一致

同一个口径在不同地方各算一遍：毛利有三套算法、BOM 版本选取前后端是两套算法、多层成本卷积一处连乘一处不连乘、税额舍入两边规则不同、匹配容差界面 0.01 元而服务端 1%。

后果：界面显示的毛利和财务账上的利润对不上，且没人知道该信哪个。

根因 F · 失败反馈不闭环「界面成功、实际没成」

多个后端端点过账失败时只往服务器日志写一行字，仍然返回「成功」；前端因此显示完成，用户以为做完了。采购域做对了（失败回滚+红条告警），但这个正确做法没推广到其他三域。

涉及：入/出库修改过账失败、调拨、报工完工入库、工单删除、销售订单提交等 6 处。

四、16 条严重问题（P0）

以下每条都是「不修就会造成错误数据或功能不可用」。

P0F-01生产域：工单建不出来（界面完全不可用）
后端建单必填校验要求「生产物料」，但数据库表里只有「产品编码 / 产品名称」，前端表单也没有这个字段。无论怎么操作，建工单必然被拒绝。
为什么测试没发现：端到端测试脚本自己传了这个不存在的字段，与界面真实调用不是同一条路。
真实接口已坐实：返回 400 MISSING_REQUIRED_CORE · field=materialId「请填写『生产物料』后再提交」
修复：字段对齐即可（改动很小，见第六节第一批）。
P0S-07销售域：信用额度闸门实际失效，可无限超额下单
服务端检查信用额度时读客户「已用额度」，但这个字段全系统只有一处会写，而销售单从不回写。于是闸门读到的占用恒为 0，可用额度永远是满额。
真实接口已坐实：授信 1000 的客户连下 3 单各 900（累计 2700，超额 170%），三单全部 201 放行
修复：销售单确认/发货时回写占用额度，并让闸门读服务端值（前端此前自报，已在上一版改过一半）。
P0S-16销售域：行级权限失效，销售员可修改/删除他人订单
销售订单在权限规则里设为「只看本人」，但建单时不记录归属人；规则里「无归属人 = 全员可见」的兼容分支又让失效方向变成放行。结果：任何销售员都能看到并改动别人的订单。
同样问题的还有：发货单、项目、意向客户。
修复：建单统一写入归属人；并考虑把「无归属人全员可见」限定为只对存量数据生效。
P0S-01销售域：订单状态机守卫完全失效（漏取状态字段）
改订单时查询只取了「编号、归属人」，漏取「状态」，导致状态校验收到空值、整套规则直接跳过。已完成、已取消的订单可被改回任意状态。
对照：采购订单的同类守卫写法正确，属孤立回归。
修复：补取状态列；并让守卫在入参缺失时拒绝而非跳过。
P0S-12销售域：明细为空时金额复核失效 + 明细数量金额无校验
上一版已做「按明细合计复核订单头金额」，但条件是「有明细行」。明细为空时会回退采信前端自报金额，等于绕过复核；且明细的数量、金额、交期均无校验。
修复：把「明细为空」改为拒绝；明细行数量金额纳入非负校验。
P0WH-16仓储域：修改单据缺并发抢占 → 重复过账、流水翻倍
入库单、出库单的新建路径已做「条件更新抢占」（谁抢到谁过账），但修改路径仍是「先读是否已过账 → 过账 → 再标记」，两次并发修改都会读到「未过账」→ 都去过账 → 库存流水翻倍。
销售端同类问题一并存在（上版并发整改只覆盖了新建）。
修复：把新建路径的抢占写法搬到修改路径（修复范式就在隔壁文件，可直接照搬）。
P0WH-17仓储域：过账失败仍返回「成功」
入/出库修改单据时若过账失败（库存没动），系统只往服务器日志写一行错误，仍返回成功。界面显示「已完成」，实际库���没扣没加。
调拨、库存调整两个端点已做对（会回滚并回传原因），未推广到入/出库。
修复：失败回滚过账标志 + 返回非 200 + 前端红条告警。
P0WH-01仓储域：已过账的单据仍可改数量 → 单据/库存/流水三者脱钩
入库单、出库单一旦过账，修改单据时仍允许改明细数量，但不重算金额、不回滚库存、不改历史流水。结果是单据上的数量、库存余额、流水三者永久对不上，且无法自愈。
修复：已过账单据禁止改明细数量；若确需调整，走「红冲 + 重做」正规流程。
P0WH-03仓储域：调拨被过账两次（双路径重复）
调拨确认时前端自己建了出库单和入库单（都标记为已完成），随后又调用后端修改接口触发双边过账——同一次调拨被扣两次、增两次。过账标志拦不住，因为走的是两条不同的单据路径。
修复：调拨只保留一条过账路径（建议走后端统一双边过账）。
P0WH-02仓储域：出库无负库存拦截，超发后成本仍按真实量结转
出库数量超过库存时，系统把库存夹到 0 继续执行，无任何告警；而成本结转、凭证仍按真实出库量计算。后果：库存为 0、成本照结、账实不符且无人知晓。
修复：超发改为拒绝（与入库的负数守卫、金额退化守卫同一策略）。
P0F-02生产域：未下达的工单可直接完工并触发倒冲扣料
状态机只锁了「已完成」不允许再改，但草稿 → 已完成是允许的。绕过界面直接调接口，就能让一张还没下达的工单完工并触发倒冲扣料。
修复：状态机补全合法流转路径（草稿→已下达→生产中→已完工）。
P0F-18生产域：重复领料 / 倒冲双扣
领料时先扣库存、再逐条写领料台账（不等待、失败不处理）；防重复的判断依赖内存变量，刷新页面即失效。后果：重复领料、倒冲时二次扣料。
修复：防重落到服务端唯一约束/抢占，不能依赖前端内存。
P0PO-01采购域：入库完成后不回写采购订单 → 订单永远显示「未交」
采购入库单完成后完全不回写采购订单的已交数量与状态（已确认代码中无任何引用）。采购员看到订单永远是未交齐，实际货已入库，订单与入库单永久脱钩。
修复：入库过账后按订单号回写已交量并推进订单状态。
P0PO-02 / PO-03采购域：已收货订单可被改回、可被删除
订单「编辑保存」会无条件把状态打回初始态，已收货的订单能被改回并重写明细；已收货订单还可以被直接删除，导致三单匹配与付款闸门的比对基准消失。
修复：状态回写按当前状态条件更新；已收货订单禁止删除（应走取消/关闭流程）。
P0PO-04采购域：采购申请审批只靠前端判断
审批动作的合法性完全由前端判断，后端没有任何审批权限校验。绕过界面直接调接口，任何人可审批通过。
修复：审批权下沉到服务端（与项目已有的操作权限守卫同一范式）。

五、跨域衔接：单域审计看不到的问题

各域内部审得再好，域与域的衔接处最容易出问题。本次发现 7 处跨域断链：

断链涉及域后果
入库不回写采购订单采购 ↔ 仓储订单永远显示未交，无法判断是否交齐
发货单 ↔ 出库单零联动销售 ↔ 仓储发货单建完不出库单；出库单可凭空创建，发货台账与实际出库永远对不上
报工完工绕过成品入库生产 ↔ 仓储料扣了、成品没入账；且两者非原子，入库失败仍报成功
倒冲幂等守卫非原子生产 ↔ 仓储并发完工可双扣料（与仓储并发问题同源，未一并修复）
BOM 无快照生产内部BOM 一改，历史工单成本被追溯改写，去年成本今年变
工单成本 ≠ 出库成本生产 ↔ 销售成本归集用标准价、COGS 用移动均价，两套口径打架
采购订单状态被无条件重置采购内部已收货订单可回到初始态，下游三单匹配基准动摇

六、值得肯定的部分

审计不是为了找茬——这些做对了

  • 采购域的失败处理是四域标杆：乐观更新 → 失败回滚快照 → 全局红条告警，完整落实「界面点得动 ≠ 已落库」。生产域的工单建单/更新也做对了。
  • 入库金额退化守卫设计扎实：有数量无金额时拒绝而不是静默记 0，且正确区分「数量为 0 的占位行不拦」。
  • 行级权限的默认方向是安全的：未登记的表默认拒绝并留告警（问题出在已登记但数据侧没填，不在机制本身）。
  • 父子表字段登记有明确纪律，上一版还顺手修过框架级缺陷（子表写入不注入组织字段导致插入失败）。
  • 单号生成规则前后端一致，服务端做了查重。
  • 上一版的三处修复方向都对（金额按明细复核、金额退化拒绝、盘点真过账），只是都只覆盖了新建路径——方向对、覆盖面不足。

七、建议修复顺序

按「先止功能不可用 → 再止越权与数据错 → 再补方法论缺口」排序。不按单个问题排，避免修完一处漏一处。

第一批止「功能不可用」改动最小
修复工单建单字段错配（F-01）。预计改动 1-2 个文件，修完生产域立刻可用。这是投入产出比最高的一批，建议立刻做。
第二批止「越权 + 额度失控」
归属人字段补写（S-16 等 4 张表）、状态机补取状态列（S-01）、信用额度回写并读服务端值（S-07）。三条都已坐实，对外风险最高。
第三批止「假成功」统一纪律
过账失败必须返回失败 + 前端告警，覆盖 WH-17/WH-18/F-04/F-20/S-19 等 6 处。把采购域的正确做法推广到四域——项目里已有现成范式，无需新设计。
第四批成对补齐「修改路径」方法论修正
按「同一能力的新建 + 修改两条路径成对核查」原则，一次性过完并发抢占、金额复核、原子化三类共 8 条。这是根治根因A 的关键批次，务必整批做、不要拆，否则会重演本轮遗漏。
第五批收敛 5 处口径
毛利口径、BOM 版本选取、成本卷积、税额舍入、匹配容差 → 各自收敛为单一权威实现，前后端共用，消除漂移。
第六批补跨域闭环
入库回写订单、发货联动出库、倒冲幂等抢占、工单 BOM 快照。做完前五批后打通链路，让四域真正串起来。
一句话总结：系统的骨架是对的，问题是「守卫建了但没建到最后一公里」——建单路径都做到了，改单路径漏了；权限登记了但数据没填；守卫写了但取数漏字段。建议按批次整批推进，尤其第四批务必一次做完，零散修会继续重演同样的遗漏。
